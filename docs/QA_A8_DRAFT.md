# A8 QA 초안: MVP 인수조건 검증 전략

## 1. 문서 목적

이 문서는 이제너두 전사 CRM OS MVP의 P0/P1 모듈을 운영 품질 관점에서 검증하기 위한 QA 기준선이다. 기능 존재 여부보다 운영자 처리량 증가, 오류 감소, 회귀 자동화 가능성, 감사 대응 가능성을 우선 검증한다.

인당 생산성/마진 기여: QA 기준을 처리량과 오류 비용 중심으로 고정해 개발 완료 후에도 운영 인력이 늘어나는 결과를 방지한다.

## 2. 검증 원칙

1. 모든 P0/P1 스토리는 목적, 입력, 출력, 인수조건, 의존성, 담당, KPI 영향을 가진 경우에만 인수 후보가 된다.
2. 심사, 정산, 포인트, CS는 MVP 단계부터 회귀 자동화 대상 플로우로 분류한다.
3. 개인정보 처리범위, 외부계약, 예산, 아키텍처 확정은 PM 김권일 승인 전 QA 통과 조건으로 확정하지 않는다.
4. E2E 테스트는 운영자의 실제 처리 경로를 검증하고, API/데이터 테스트는 대량 처리와 정합성 리스크를 검증한다.
5. 보안/권한 테스트는 기능 테스트의 후행 검사가 아니라 모든 핵심 플로우의 기본 통과 조건이다.
6. 영업활동에서 매출인식까지 이어지는 전체 프로세스는 단계별 부분 기능이 아니라 단일 E2E 업무 흐름으로 검증한다.

인당 생산성/마진 기여: 초기부터 반려 기준을 명확히 해 불완전한 기능이 운영 현장으로 넘어가며 발생하는 재처리 비용을 줄인다.

## 3. 가정

- 가정: 레거시 시스템, 베네카페, 결제, 온누리 연동의 상세 API 문서는 아직 제공되지 않았다.
- 가정: MVP QA는 실제 운영 데이터 원본이 아닌 비식별 샘플 데이터와 계약/정산/포인트 시뮬레이션 데이터로 먼저 수행한다.
- 가정: 개인정보 및 민감정보 항목, 보관기간, 위탁/재위탁 범위는 PM 김권일 승인 후 확정한다.
- 가정: "자동심사"는 MVP에서 무검토 자동 승인보다 후보 추천, 예외 분류, 사람 검토 큐 연결을 우선 검증한다.
- 가정: 영업이익 MVP 산식은 PM 승인 전까지 `salesAmount - (salesAmount * 0.5) - (salesAmount * 0.5)`를 기준 테스트 값으로 사용하되, 산식 확정으로 간주하지 않는다.
- 가정: 택배사 실시간 위치 연동은 계약/API/비용 승인 전까지 mock 응답과 수동 송장/상태 보정 큐로 검증한다.

인당 생산성/마진 기여: 불확실성을 가정으로 분리해 잘못된 데이터와 연동 전제에 따른 재작업을 줄인다.

## 5. 핵심 플로우별 테스트 시나리오

### 5.1 심사 플로우

목적: 신청 접수부터 자동심사 후보 분류, 사람 검토, 승인/보류/반려, 이력 저장까지 운영 누락 없이 처리되는지 검증한다.

입력: 신청 ID, 고객사 ID, 임직원 ID, 증빙 상태, 심사 규칙 결과, 담당자 역할.

출력: 심사 상태, 담당자 배정, 승인/보류/반려 사유, 감사로그, CS 전환 가능 이력.

인수조건:

- 접수된 신청은 운영 큐에 1건만 생성된다.
- 자동심사 후보, 보류, 반려 추천은 근거 코드와 함께 저장된다.
- 담당자가 상태를 변경하면 변경 전후 값, 사용자, 시각, 사유가 감사로그에 남는다.
- 권한 없는 사용자는 타 고객사 신청을 조회하거나 처리할 수 없다.
- 반려된 신청은 재접수 또는 CS 문의 전환 경로가 명확하다.

반려 기준:

- 동일 신청이 중복 큐로 생성된다.
- 반려 사유 없이 상태가 반려로 변경된다.
- 자동심사 결과의 근거가 저장되지 않는다.
- 개인정보 접근 로그 없이 증빙 또는 임직원 정보가 조회된다.

의존성: CRM Core, Operations Console, Security & Audit Baseline, Automation/RPA Workbench.

담당: A8 검증, A2 운영 큐, A5 자동심사, A7 개인정보 기준, A9 보안 구현.

KPI 영향: 평균 심사 처리시간, 심사자 1인당 처리 건수, 반려 후 재문의율, 자동분류율.

인당 생산성/마진 기여: 심사 기준과 예외를 회귀 테스트로 고정해 신규 신청 증가에도 심사 인력 증가를 억제한다.

### 5.2 정산 플로우

목적: 거래/포인트/공급사/고객사 기준으로 정산 금액과 증적이 일치하고 예외가 운영 큐로 분리되는지 검증한다.

입력: 거래 ID, 공급사 ID, 고객사 ID, 정산 기간, 수수료율, 취소/환불, 포인트 사용/복원 이벤트.

출력: 정산 배치, 공급사별 정산 금액, 예외 목록, 회계 증적, 변경 감사로그.

인수조건:

- 같은 정산 배치를 재실행해도 중복 지급 또는 중복 차감이 발생하지 않는다.
- 거래 합계, 취소/환불, 포인트 사용/복원 금액이 정산 결과와 대사된다.
- 정산 예외는 원인 코드, 담당자, SLA, 재처리 버튼 또는 수동 보정 경로를 가진다.
- 정산 결과의 원천 데이터와 계산 버전을 추적할 수 있다.
- 회계 증적 다운로드 또는 조회 시 권한과 접근로그가 적용된다.

반려 기준:

- 정산 재실행 시 결과가 달라지는데 원인 추적이 불가능하다.
- 취소/환불 거래가 정산 금액에서 누락된다.
- 예외 건이 큐에 남지 않고 단순 실패로 종료된다.
- 금액 반올림, 세금, 수수료 기준이 명시되지 않았다.

의존성: Settlement & Point Ops, CRM Core, Profitability Dashboard, Integration Hub.

담당: A8 검증, A4 지표/대사, A6 연동, A7 회계/감사 기준.

KPI 영향: 정산 오류율, 정산 문의 건수, 월마감 소요시간, 외감 증적 준비시간.

인당 생산성/마진 기여: 정산 오류와 월마감 수작업을 줄여 재무/운영 인력의 반복 검산 비용을 낮춘다.

### 5.3 포인트 플로우

목적: 포인트 지급, 차감, 사용, 취소, 복원, 만료가 잔액과 정산 근거에 정확히 반영되는지 검증한다.

입력: 임직원 ID, 고객사 ID, 포인트 정책, 지급 이벤트, 사용 거래, 취소/복원 이벤트, 만료일.

출력: 포인트 원장, 현재 잔액, 거래별 포인트 이력, 정산 참조값, 예외 큐.

인수조건:

- 모든 포인트 변화는 원장 이벤트로 기록되고 현재 잔액은 원장 합계와 일치한다.
- 지급/차감/취소/복원/만료 이벤트는 멱등 키를 가진다.
- 음수 잔액, 중복 지급, 만료 후 사용은 차단되거나 예외 큐로 분리된다.
- 고객사별 포인트 정책 차이가 테스트 데이터로 검증된다.
- 포인트 원장 조회는 역할과 테넌트 격리를 통과해야 한다.

반려 기준:

- 잔액만 변경되고 원장 이벤트가 남지 않는다.
- 동일 이벤트 재처리로 포인트가 중복 변동된다.
- 고객사 정책이 다른데 같은 규칙으로 처리된다.
- 포인트 변경이 정산 참조값과 연결되지 않는다.

의존성: Settlement & Point Ops, Security & Audit Baseline, CRM Core.

담당: A8 검증, A4 원장/지표, A6 외부 이벤트, A9 권한 통제.

KPI 영향: 포인트 오류율, 잔액 문의 건수, 수동 보정 건수, 정산 대사 시간.

인당 생산성/마진 기여: 포인트 원장 회귀를 자동화해 잔액 문의와 수동 보정에 들어가는 운영 시간을 줄인다.

### 5.4 CS 플로우

목적: 고객사, 임직원, 공급사 문의가 기준 데이터와 업무 큐에 연결되어 중복 응대와 누락을 줄이는지 검증한다.

입력: 문의 ID, 문의자 유형, 고객사/공급사/임직원 참조 ID, 카테고리, SLA, 관련 거래/신청/정산 ID.

출력: CS 티켓, 담당자 배정, 관련 업무 링크, 답변/보류/이관/완료 상태, 활동 이력.

인수조건:

- 문의는 관련 고객사/공급사/임직원/거래/신청 중 최소 하나의 기준 데이터와 연결된다.
- 동일 문의의 중복 접수 후보가 표시된다.
- SLA 초과 위험 건은 필터와 우선순위로 확인 가능하다.
- CS 처리 이력은 CRM 활동 이력과 감사로그에 남는다.
- 개인정보 포함 문의는 마스킹, 접근권한, 접근로그 기준을 따른다.

반려 기준:

- 티켓이 기준 데이터 없이 독립 메모로만 저장된다.
- 담당자 변경 또는 이관 이력이 남지 않는다.
- SLA 상태가 계산되지 않거나 필터링되지 않는다.
- 개인정보가 권한 없는 역할에 노출된다.

의존성: CRM Core, Operations Console, Security & Audit Baseline.

담당: A8 검증, A2 운영 콘솔, A3 CS 화면, A7 개인정보 기준.

KPI 영향: 평균 응답시간, SLA 준수율, 중복 문의율, 담당자 1인당 처리 건수.

인당 생산성/마진 기여: CS를 기준 데이터와 연결해 반복 확인 시간을 줄이고 동일 인력의 처리량을 높인다.

### 5.5 전체 프로세스 E2E: 영업활동에서 매출인식

목적: 영업활동, 파이프라인, 견적, 계약, 주문, 출고, 배송/입출고, 세금계산서/거래명세표, 매출인식, 영업이익 확인이 단일 추적 가능한 흐름으로 연결되는지 검증한다.

입력: 고객, 담당자, 활동내용, 상품, 판매가격, 할인, 수량, 계약기간, 납기, 배송지, 송장번호, 공급가, 세액, 매출인식 기준.

출력: 활동 타임로그, 파이프라인, 견적서, 결재 문건, 계약 레코드, 주문 레코드, 출고 상태, 배송 상태, 세금계산서/거래명세표 발행 로그, 매출 레코드, 영업이익 지표.

인수조건:

- 영업활동 저장 시 활동 타임로그와 파이프라인 후보가 생성된다.
- 파이프라인에서 견적을 발행할 때 상품, 수량, 판매가격, 할인, 유효기간이 견적 버전에 남는다.
- 견적, 계약, 세금계산서/거래명세표, 매출인식 조정은 결재 대상 후보로 생성될 수 있다.
- 계약 기반 주문은 고객, 상품, 수량, 납기, 배송지를 참조하고 출고 요청으로 이어진다.
- 출고 완료 후 배송/입출고 상태가 조회 가능하며 배송 지연, 오배송, 반송, 미출고는 운영 콘솔 예외 큐에 남는다.
- 세금계산서와 거래명세표 발행 상태, 발행 이력, 첨부/전송 결과가 타임로그와 감사로그에 남는다.
- 매출인식 레코드는 주문, 출고, 청구, 회계 기준 중 어떤 기준으로 확정되었는지 추적 가능하다.
- 최종 영업이익 대시보드는 동일 프로세스의 매출 레코드와 원가/판관비 산식을 기준으로 계산된다.

반려 기준:

- 단계 간 참조 ID가 끊겨 영업활동부터 매출인식까지 추적할 수 없다.
- 견적 또는 상품 화면에서 판매가격이 별도 컬럼이나 강조 영역으로 확인되지 않는다.
- 결재 상태 변경, 출고/배송 상태 변경, 발행, 매출인식 변경 중 하나라도 타임로그가 누락된다.
- 배송 예외가 운영 콘솔 예외 큐로 전환되지 않는다.
- 매출인식 기준 또는 원천 주문/출고/청구 데이터를 확인할 수 없다.

의존성: CRM Core, Operations Console, Profitability Dashboard, Integration Hub, Security & Audit Baseline, PROCESS_REQUIREMENTS.

담당: A8 검증, A2 프로세스 API, A3 화면/메뉴, A4 산식/데이터, A6 배송 연동, A7 결재/로그/통제.

KPI 영향: 부서 간 재입력 건수, 견적-주문 전환 시간, 배송 문의 건수, 매출인식 지연 건수, 이익 저하 원인 식별 시간.

인당 생산성/마진 기여: 영업부터 매출인식까지 끊김 없는 검증으로 재입력, 누락, 수기 검산 시간을 줄이고 낮은 이익 원인을 빠르게 찾는다.

### 5.6 영업이익 산식 검증

목적: MVP 대시보드의 영업이익과 영업이익률이 기준 산식에 따라 일관되게 계산되고, 이익 저하 원인 지표가 함께 표시되는지 검증한다.

입력: `salesAmount`, 할인, 반품, 배송비, 처리시간, 결재 지연, 정산 지연, 예외 처리 건수.

출력: `costAmount`, `sgnaAmount`, `operatingProfit`, `operatingProfitRate`, 고객별/상품별/담당자별/파이프라인별 이익률, 이익 저하 원인 후보.

인수조건:

- `costAmount = salesAmount * 0.5`로 계산된다.
- `sgnaAmount = salesAmount * 0.5`로 계산된다.
- `operatingProfit = salesAmount - costAmount - sgnaAmount`로 계산된다.
- `operatingProfitRate = operatingProfit / salesAmount`로 계산되며 `salesAmount = 0`인 경우 표시 정책이 정의된다.
- 고정 산식상 기본 영업이익이 0이 되는 케이스와 할인/반품/배송비/처리시간 등 원인 지표가 함께 검증된다.
- 슈퍼바이저만 전사 영업이익 산식, 산식 변경 이력, 상세 로그 메뉴에 접근할 수 있다.

반려 기준:

- 산식 결과가 기준값과 다르거나 반올림/0 나누기 정책이 없다.
- 산식 변경 또는 조회 로그가 남지 않는다.
- 일반 직원이 전사 영업이익 산식 또는 전사 로그를 조회할 수 있다.
- 이익 저하 원인 지표 없이 영업이익 숫자만 표시된다.

의존성: Profitability Dashboard, A4 KPI 정의, Security & Audit Baseline.

담당: A8 검증, A3 대시보드 UI, A4 산식/데이터, A7/A9 권한/로그.

KPI 영향: 저마진 고객/상품 식별 시간, 가격/할인 정책 조정 속도, 경영 보고 수작업 감소.

인당 생산성/마진 기여: 산식과 원인 지표를 함께 검증해 단순 매출 증가가 아닌 실제 마진 개선 판단을 빠르게 만든다.

### 5.7 화면, 권한, 저장, 결재, 타임로그 검증

목적: 운영자가 목록과 입력 화면에서 맥락을 잃지 않고, 역할에 맞는 메뉴만 사용하며, 주요 저장/승인/변경 이력이 추적되는지 검증한다.

입력: 일반/관리자/슈퍼바이저 계정, 고객 신규 정보, 고객 수정 정보, 상품 판매가격, 결재 문건, 임직원 결재라인, 로그 조회 조건.

출력: 권한별 메뉴, 고정 헤더 목록, 고객 신규/수정 저장 결과, 판매가격 표시, 결재라인 순서, 사용자 정보 표시, 타임로그/감사로그.

인수조건:

- 모든 목록 화면은 스크롤 또는 드래그 중에도 필드 헤더가 상단에 고정된다.
- 고객 등록 저장은 신규 고객 레코드를 생성하고, 고객 수정 저장은 기존 고객 레코드를 변경한다.
- 고객 신규/수정 저장 모두 생성자/수정자, 시각, 변경 전후 값이 타임로그에 남는다.
- 판매상품 등록 또는 견적 화면에서 판매가격은 별도 컬럼 또는 강조 영역으로 즉시 확인 가능하다.
- 설정 메뉴 옆에는 로그인 사용자의 소속, 이름, 권한이 표시된다.
- 일반, 관리자, 슈퍼바이저는 PROCESS_REQUIREMENTS의 권한별 메뉴 차등 기준에 따라 보이는 메뉴와 진행 가능한 업무가 다르다.
- 결재 문건 작성자는 현재 로그인한 임직원으로 자동 지정되고, 결재라인은 임직원 목록에서 추가/순서 변경 가능하다.
- 결재 상태, 결재라인 변경, 최종 결재권자 지정은 타임로그와 감사로그에 남는다.
- 설정 메뉴에는 로그기록 확인 메뉴가 있고 권한 있는 사용자만 조회 가능하다.

반려 기준:

- 스크롤 후 필드 헤더가 사라져 컬럼 의미를 알 수 없다.
- 신규 고객 저장과 기존 고객 수정 저장이 구분되지 않는다.
- 판매가격이 목록/견적/상품 등록 화면에서 즉시 보이지 않는다.
- 권한별 메뉴 제한이 화면에서만 적용되고 API에서 차단되지 않는다.
- 결재 작성자를 임의 사용자로 변경할 수 있거나 결재라인 변경 이력이 남지 않는다.
- 생성, 수정, 삭제, 승인, 상태 변경, 발행, 조회 중 핵심 로그가 누락된다.

의존성: CRM Core, Security & Audit Baseline, A3 UI, A7 결재/통제 기준.

담당: A8 검증, A2 저장/API, A3 UI, A4 타임로그 데이터, A7 권한/감사, A9 로그 보존.

KPI 영향: 화면 탐색 시간, 저장 오류율, 승인 대기 추적 시간, 권한 관련 운영 문의, 감사 대응 시간.

인당 생산성/마진 기여: 화면 맥락 유지와 권한/로그 검증으로 반복 처리 속도를 높이고 승인·감사 확인 비용을 줄인다.

### 5.9 임직원-거래처 담당 배정 검증

목적: `/specs/employee/customer-assignment.md` 기준으로 직원과 거래처의 다대다 담당 배정, 대표 담당자 표시, 권한 없는 변경 차단, 배정 변경 로그를 검증한다.

입력: 임직원 ID, 거래처 ID, 담당 역할, 대표 담당자 여부, 배정 시작일, 배정 종료일, 배정 사유, 배정 변경 권한 계정.

출력: 임직원별 담당 거래처 목록, 거래처별 담당자 목록, 대표 담당자 표시, 담당 역할 표시, 배정 이력, 변경 타임로그/감사로그.

인수조건:

- 직원 1명에게 여러 거래처를 배정할 수 있다.
- 거래처 1개에 여러 담당자를 표시할 수 있다.
- 거래처 상세 화면에는 담당자 목록, 담당 역할, 대표 담당자가 표시된다.
- 거래처 목록에는 대표 담당자가 표시된다.
- 임직원 상세 화면에는 해당 임직원의 담당 거래처 목록이 표시된다.
- 대표 담당자는 거래처별 1명만 지정되는 기준으로 검증하되, 최종 제한 정책은 PM 승인 항목으로 둔다.
- 담당자 검색, 다중 선택, 역할 지정, 저장 전 변경 내용 확인이 가능하다.
- 권한 없는 사용자는 담당자 배정 생성, 변경, 종료를 수행할 수 없다.
- 담당자 배정 생성, 변경, 종료는 변경 전후 값, 변경자, 시각, 배정 사유와 함께 타임로그/감사로그에 남는다.

반려 기준:

- 직원 1명과 거래처 1개의 1:1 배정만 가능하다.
- 거래처 상세 또는 목록에서 대표 담당자를 확인할 수 없다.
- 거래처 1개에 여러 담당자를 표시하지 못하거나 담당 역할이 누락된다.
- 권한 없는 사용자가 UI 또는 API로 배정 변경을 수행할 수 있다.
- 담당자 배정 변경 로그 또는 배정 사유가 남지 않는다.

의존성: CRM Core, Security & Audit Baseline, `/specs/employee/customer-assignment.md`, A2 배정 API, A3 임직원/거래처 화면, A4 배정 데이터, A7 권한/감사 기준.

담당: A8 검증, A2/A3/A4/A7 수정.

KPI 영향: 담당자 확인 시간, 거래처 인수인계 시간, 중복 문의, 담당 공백으로 인한 처리 지연.

인당 생산성/마진 기여: 다대다 배정과 대표 담당자 가시성을 검증해 거래처별 책임자를 빠르게 찾고 담당 공백에 따른 처리 지연을 줄인다.

### 5.10 결재 버튼 의미와 액션 상태 검증

목적: `/specs/workflow/approval-action-semantics.md` 기준으로 결재, 승인, 반려, 보류 버튼의 의미와 상태 표시, 사유 필수, 권한 차단, 로그 생성을 검증한다.

입력: 결재 문건 ID, 로그인 사용자, 현재 결재자, 다음 결재자, 최종 결재권자, 대상 업무, 승인 의견, 반려 사유, 보류 사유.

출력: 현재 결재 상태, 결재 타임라인, 상신자, 현재 결재자, 다음 결재자, 최종 결재권자, 승인/반려/보류 이력, 사유, 대상 업무의 다음 가능 상태, 타임로그/감사로그.

인수조건:

- 결재 버튼 클릭 시 상태를 임의 변경하지 않고 결재 상세 또는 처리 화면으로 진입하며 현재 결재 상태와 타임라인을 즉시 확인할 수 있다.
- 승인, 반려, 보류 버튼 근처에는 버튼 의미와 처리 결과 상태가 표시된다.
- 승인 클릭 시 현재 결재자가 승인 처리되고 다음 결재자가 있으면 다음 결재자 대기 상태가 표시된다.
- 최종 승인 후 견적, 계약, 세금계산서/거래명세표, 매출인식 조정의 다음 가능 상태가 표시된다.
- 반려 클릭 시 `rejected` 상태가 되며 반려 사유가 필수다.
- 보류 클릭 시 `on_hold` 상태가 되며 보류 사유가 필수다.
- 반려 또는 보류 사유 없이 처리 요청을 보내면 UI와 API 모두 차단한다.
- 승인, 반려, 보류 처리는 사용자, 시각, 대상 업무, 이전 상태, 이후 상태, 의견/사유와 함께 타임로그/감사로그에 남는다.
- 권한 없는 사용자는 승인, 반려, 보류 버튼을 사용할 수 없고 API 직접 호출도 차단된다.

반려 기준:

- 결재 버튼 클릭 후 현재 결재 상태와 타임라인을 즉시 확인할 수 없다.
- 승인/반려/보류 버튼의 의미 또는 결과 상태 설명이 화면에 없다.
- 반려/보류가 사유 없이 처리된다.
- 승인 후 다음 결재자 대기 또는 최종 승인 후 대상 업무 상태가 표시되지 않는다.
- 권한 없는 사용자가 결재 액션을 수행할 수 있다.
- 승인/반려/보류 타임로그 또는 감사로그가 누락된다.

의존성: Operations Console, Security & Audit Baseline, `/specs/workflow/approval-action-semantics.md`, A2 결재 API, A3 결재 UI, A7 감사/권한 기준.

담당: A8 검증, A2/A3/A7/A9 수정.

KPI 영향: 승인 지연, 결재 상태 문의, 반려 후 재상신 오류, 매출/발행/계약 처리 대기 시간.

인당 생산성/마진 기여: 버튼 의미와 상태 표시를 검증해 결재 오처리와 상태 확인 문의를 줄이고 후속 업무 전환 속도를 높인다.

### 5.11 입사등록 결재 승인 검증

목적: `/specs/hr/employee-onboarding-approval.md` 기준으로 입사등록 승인상태가 결재문건 상태와 일치하고, 최종 승인 전 계정 활성화와 권한 부여가 차단되는지 검증한다.

입력: 입사등록 대상자 정보 후보, 입사 예정일, 소속/부서 후보, 직무/권한 후보, 상신자, 결재라인, 상신 사유, 승인 의견, 반려 사유, 보류 사유.

출력: 입사등록 문건, 연결된 결재문건, 결재라인, 현재 승인상태, 승인/반려/보류 이력, 계정 활성화 대기 상태, 타임로그/감사로그.

인수조건:

- 입사등록 저장만으로 승인 완료 또는 계정 활성화가 되지 않는다.
- 결재라인 설정 전에는 상신 버튼 또는 상신 API가 차단된다.
- 결재라인 설정 후에는 상신 가능하며 상신자, 결재자 목록, 결재 순서, 최종 결재권자가 표시된다.
- 입사등록의 승인상태는 연결된 결재문건 상태와 항상 일치한다.
- 최종 결재 승인 전에는 임직원 계정 활성화와 권한 부여가 완료되지 않는다.
- 최종 승인 후에는 `employee_activation_pending` 상태가 표시되고 자동 활성화 또는 관리자 확인 활성화 여부는 PM 승인 전 가정으로 둔다.
- 승인, 반려, 보류 처리에는 의견 또는 사유가 필요하며 반려/보류 사유는 필수다.
- 입사등록 생성, 수정, 상신, 승인, 반려, 보류, 최종 승인 반영, 계정 활성화 시도는 타임로그/감사로그에 남는다.

반려 기준:

- 결재라인 없이 입사등록 상신이 가능하다.
- 최종 승인 전 계정이 활성화되거나 권한이 부여된다.
- 입사등록 승인상태와 결재문건 상태가 다르게 표시된다.
- 반려/보류가 사유 없이 처리된다.
- 입사등록 생성, 수정, 상신, 승인, 반려, 보류, 활성화 관련 로그가 누락된다.

의존성: Security & Audit Baseline, Operations Console, `/specs/hr/employee-onboarding-approval.md`, A2 HR/결재 API, A3 입사등록 UI, A7 권한/감사 기준, A9 로그 보존.

담당: A8 검증, A2/A3/A7/A9 수정.

KPI 영향: 입사 승인 누락, 계정 활성화 오류, 권한 오부여, HR 승인 확인 문의.

인당 생산성/마진 기여: 입사등록과 계정 활성화 사이에 결재 게이트를 검증해 권한 오부여와 HR 재처리 비용을 줄인다.

### 5.12 메뉴별 로그기록 검증

목적: `/specs/audit/menu-log-records.md` 기준으로 설정 메뉴의 로그기록에서 메뉴별 로그 조회와 필터가 가능하고, 메뉴 진입부터 반출까지 주요 사용자 행위가 메뉴 ID와 함께 기록되는지 검증한다.

입력: 메뉴 ID, 메뉴명, 라우트 ID, 사용자 ID, 사용자 권한, 대상 엔티티, 이벤트 유형, 이벤트 결과, 사유 코드, 로그 조회 필터.

출력: 메뉴별 로그 목록, 메뉴별 사용자 활동 이력, 생성/수정/삭제/조회/결재/반출 집계, 권한 없는 접근 시도 목록, 로그 상세, 로그 조회 감사로그.

인수조건:

- 상단 메인 설정 메뉴 하위 `로그기록`에서 메뉴별 로그 탭 또는 메뉴별 필터를 사용할 수 있다.
- 메뉴명, 기간, 사용자, 권한, 이벤트 유형, 결과, 대상 엔티티로 로그를 필터링할 수 있다.
- 각 주요 메뉴 진입 시 `menu_opened` 로그가 메뉴 ID, 사용자, 권한, 시각과 함께 남는다.
- 목록 조회는 `list_viewed`, 상세 조회는 `detail_viewed`, 신규 생성은 `created`, 수정 저장은 `updated`로 기록된다.
- 삭제 또는 비활성은 `deleted`, 승인은 `approved`, 반려는 `rejected`, 보류는 `on_hold`로 기록된다.
- CSV/Excel/API 반출 요청은 `export_requested`, 필터/보기 저장은 `filter_saved`로 기록된다.
- 권한 없는 메뉴 접근 또는 버튼 실행 차단은 `permission_denied`로 기록된다.
- 개인정보 포함 로그는 기본 마스킹되며 로그 조회와 로그 상세 조회 자체도 감사로그에 남는다.

반려 기준:

- 설정 메뉴 로그기록에서 메뉴별 로그 조회 또는 필터가 불가능하다.
- 메뉴 진입, 목록, 상세, 수정, 결재, 반출 중 하나라도 메뉴 ID 없이 기록된다.
- 권한 없는 접근 차단이 `permission_denied`로 남지 않는다.
- 로그 상세 조회 자체의 감사로그가 남지 않는다.
- 개인정보 포함 로그가 기본 마스킹되지 않는다.

의존성: Security & Audit Baseline, `/specs/audit/menu-log-records.md`, A3 설정 UI, A7 감사 기준, A9 로그 수집/보존.

담당: A8 검증, A3/A7/A9 수정.

KPI 영향: 장애 조사 시간, 권한 점검 시간, 외감 대응 시간, 메뉴 개선 우선순위 판단.

인당 생산성/마진 기여: 메뉴별 사용자 행위 로그를 검증해 장애 조사와 권한 점검을 DB 수작업 없이 처리하게 한다.

### 5.13 수익성 비용 입력 권한 검증

목적: `/specs/settings/profit-cost-permission.md` 기준으로 제원원가, 판관비, 일반관리비 입력 권한을 `Master`와 `ProfitCostInputManager`로 제한하고, 비용 변경이 대시보드 산식에 승인 없이 반영되지 않도록 검증한다.

입력: 사용자 권한, 제원원가, 판관비, 일반관리비, 적용일, 적용 범위, 산식 버전, 변경 사유, 결재 대상 여부, 승인 상태.

출력: 수익성 비용 입력 화면 접근 허용/차단, 저장 결과, 변경 전후 값 로그, 산식 버전, 대시보드 반영 여부, 권한 차단 로그.

인수조건:

- `Master`와 `ProfitCostInputManager`만 제원원가, 판관비, 일반관리비를 입력, 수정, 삭제할 수 있다.
- 일반과 관리자는 비용 입력 메뉴 저장 액션이 차단되며 API 직접 저장 요청도 차단된다.
- 권한 없는 사용자가 비용 입력 URL에 직접 접근하면 접근이 차단되고 `permission_denied` 로그가 생성된다.
- 비용 변경 저장 시 변경 사유, 적용일, 적용 범위, 산식 버전, 변경자가 필수다.
- 변경 전후 값은 감사로그와 메뉴별 로그에 남는다.
- 입력 화면에는 현재 적용 중인 산식 버전과 마지막 변경자가 표시된다.
- 저장 전 예상 영향 범위와 변경 전후 값을 확인할 수 있다.
- 비용 변경이 결재 대상이면 최종 승인 전 영업이익 대시보드에 반영되지 않는다.
- 최종 승인 후 반영되는 경우 대시보드에는 마지막 갱신 시각과 적용 산식 버전이 표시된다.

반려 기준:

- 일반 또는 관리자 권한이 제원원가, 판관비, 일반관리비를 저장할 수 있다.
- 권한 없는 URL 직접 접근 또는 API 저장 요청이 차단되지 않는다.
- 변경 사유, 적용일, 적용 범위, 산식 버전 중 하나라도 없이 저장된다.
- 변경 전후 값, 변경자, 시각 로그가 남지 않는다.
- 결재 대상 변경이 최종 승인 전 영업이익 대시보드에 반영된다.
- 대시보드가 어떤 산식 버전을 기준으로 계산됐는지 표시하지 않는다.

의존성: Profitability Dashboard, Security & Audit Baseline, `/specs/settings/profit-cost-permission.md`, A3 설정 UI, A4 산식/지표, A7 권한/감사, A9 로그 보존.

담당: A8 검증, A3/A4/A7/A9 수정.

KPI 영향: 영업이익 지표 오류, 경영 판단 재검산 시간, 비용 입력 오남용, 감사 대응 시간.

인당 생산성/마진 기여: 비용 입력 권한과 승인 전 미반영을 검증해 잘못된 산식 변경으로 인한 경영 판단 오류와 재검산 비용을 줄인다.

### 5.14 외주 인력 외부 접속 검증

목적: `/specs/devops/external-vendor-access.md` 기준으로 외주 인력 접속이 PM 승인, 개인별 계정, 만료일, 허용 IP 또는 접속 정책, 최소권한, 로그, 기간 종료 후 회수 기준을 통과하는지 검증한다.

입력: 외주 업체명, 외주 담당자 이름/이메일/연락처, 접속 목적, 접속 대상 환경, 접속 필요 기간, 외주 고정 IP 후보, 필요한 메뉴/권한 범위, 데이터 접근 범위, PM 승인 상태.

출력: 외주 접속 승인 기록, 개인별 외주 계정, 접속 가능 환경, 허용 IP 또는 접속 정책, 만료일, 접속/메뉴별 로그, 권한 차단 로그, 계정/허용 IP 회수 기록.

인수조건:

- PM 승인 전에는 외주 접속 계정, 임시 URL, VPN/허용 IP/Zero Trust 정책이 활성화되지 않는다.
- 외주 접속 대상은 `dev` 또는 `staging`으로 제한되며 운영 환경 접속은 별도 PM/A7 승인 없이는 차단된다.
- 외주 계정은 개인별로 발급되어야 하며 공유 계정은 허용되지 않는다.
- 외주 계정에는 만료일, 접속 목적, 허용 메뉴/권한 범위, 데이터 접근 범위가 필수로 연결된다.
- 허용 IP 또는 접속 정책이 적용되어 승인되지 않은 네트워크/정책 조건에서는 접속이 차단된다.
- 권한 없는 메뉴, 개인정보, 운영 데이터, 다운로드/반출 접근은 차단된다.
- 접속, 로그인 실패, 메뉴 진입, 데이터 조회, 변경, 다운로드/반출 시도는 접속 로그와 메뉴별 로그에 남는다.
- 개인정보/운영 데이터는 외주 접속 환경에서 마스킹 또는 샘플 데이터로 대체된다.
- 접속 기간 종료 후 외주 계정, 임시 URL, 허용 IP 또는 접속 정책은 회수되고 회수 기록이 남는다.

반려 기준:

- PM 승인 전 외주 접속이 활성화된다.
- 외주 계정이 공유 계정이거나 개인별 담당자/만료일이 없다.
- 허용 IP 또는 접속 정책 없이 외부 인터넷에서 접속 가능하다.
- 권한 없는 메뉴, 개인정보, 운영 데이터, 다운로드/반출 접근이 차단되지 않는다.
- 접속, 메뉴 진입, 조회, 변경, 다운로드/반출 시도 로그가 남지 않는다.
- 만료일 이후에도 외주 계정, 임시 URL, 허용 IP 또는 접속 정책이 유지된다.

의존성: Security & Audit Baseline, Integration/DevOps 운영 기준, `/specs/devops/external-vendor-access.md`, A7 보안 검토, A9 접속 환경/로그 보존.

담당: A8 검증, A7/A9 수정.

KPI 영향: 외주 검수 지연, 권한 회수 시간, 보안 사고 대응 비용, 개인정보 노출 리스크.

인당 생산성/마진 기여: 외주 접속을 승인·계정·기간·로그로 검증해 협업 속도를 유지하면서 보안 사고와 권한 방치 비용을 줄인다.

### 5.15 메뉴별 설정 통합 화면 검증

목적: 상단 메인 설정 메뉴 안에서 메뉴별 설정 카드가 실제 설정 팝업 또는 패널로 연결되고, 설정 누락과 오조작 없이 저장·로그·상태 피드백이 동작하는지 검증한다.

입력: 설정 메뉴 권한 계정, 메뉴별 설정 카드, 메뉴별 설정 필드, 토글, 권한 옵션, 저장 버튼, 기존 활성 상태, 변경 사유 후보.

출력: 메뉴별 설정 팝업/패널, 필드/토글/권한/저장 버튼, 활성 상태 표시, 저장 결과, 토스트 또는 로그 안내, 감사로그.

대상 메뉴:

- 대시보드/재무
- 고객관리
- 판매상품
- 배송/입출고
- 영업 파이프라인
- 결재/입사등록
- 로그기록

인수조건:

- 각 대상 메뉴의 설정 카드를 클릭하면 해당 메뉴명과 목적이 일치하는 실제 설정 팝업 또는 패널이 표시된다.
- 팝업/패널에는 해당 메뉴 설정에 필요한 필드, 토글, 권한 옵션, 저장 버튼이 존재한다.
- 현재 설정의 활성/비활성 상태가 카드와 팝업/패널 안에서 식별 가능하게 표시된다.
- 저장 버튼은 권한 있는 사용자에게만 활성화되고, 권한 없는 사용자는 저장할 수 없다.
- 저장 성공 시 변경 대상, 변경 결과, 적용 범위가 토스트 또는 로그 안내로 표시된다.
- 저장 시 변경 전후 값, 사용자, 시각, 메뉴 ID, 변경 사유 후보가 감사로그 또는 메뉴별 로그에 남는다.
- 설정 메뉴 단일화 원칙에 따라 각 업무 화면 우측 상단의 개별 시스템 설정 버튼이 아니라 상단 메인 설정 메뉴 안에서만 접근된다.
- 화면별 보기 옵션은 `보기 설정` 또는 `필터 저장`으로 분리되어 시스템 설정 카드와 혼동되지 않는다.

대상 메뉴별 최소 검증:

| 대상 메뉴 | 최소 확인 항목 | 승인 조건 | 반려 조건 |
|---|---|---|---|
| 대시보드/재무 | 지표 표시, 산식/비용 권한, 갱신 주기 또는 산식 버전 표시 | 필드/토글/권한/저장 버튼과 활성 상태가 보이고 저장 로그가 남는다 | 산식/비용 설정이 권한 없이 저장되거나 저장 후 대시보드 버전 안내가 없다 |
| 고객관리 | 고객 필드 표시, 담당자/권한, 정렬/필터 기본값 | 고객관리 설정 패널이 열리고 저장 후 토스트/로그 안내가 표시된다 | 고객관리 카드가 더미 화면이거나 필드/토글/저장 버튼이 없다 |
| 판매상품 | 판매가격 표시, 상품 필드, 가격 권한 | 판매가격 관련 설정이 별도 항목으로 보이고 저장 로그가 남는다 | 판매가격 표시 설정이 없거나 상품 설정과 무관한 패널이 열린다 |
| 배송/입출고 | 배송 상태, 현재 위치, 예외 큐, 수동 보정 권한 | 배송/입출고 설정 패널에서 상태/예외/권한 토글과 저장 버튼을 확인한다 | 배송 설정이 외부 연동 또는 예외 큐와 연결되지 않는다 |
| 영업 파이프라인 | 단계, 확률, 예상마감일, 견적 전환 권한 | 파이프라인 설정 패널이 단계/권한/저장 로그를 제공한다 | 단계 설정 저장 후 활성 상태 또는 로그 안내가 없다 |
| 결재/입사등록 | 결재라인, 승인/반려/보류, 입사등록 상신/활성화 게이트 | 결재와 입사등록 설정이 구분되고 저장 로그가 남는다 | 결재/입사등록 설정이 섞여 의미가 불명확하거나 사유/권한 설정이 없다 |
| 로그기록 | 로그 이벤트, 메뉴별 필터, 반출 권한, 마스킹 | 로그기록 설정 패널에서 이벤트/필터/권한/마스킹 설정과 저장 로그를 확인한다 | 로그기록 설정 저장이 감사로그 없이 처리되거나 반출 권한 설정이 없다 |

반려 기준:

- 대상 메뉴 카드 클릭 시 실제 설정 팝업/패널이 열리지 않는다.
- 열린 팝업/패널이 선택한 메뉴와 무관하거나 더미/공통 빈 화면이다.
- 필드, 토글, 권한 옵션, 저장 버튼 중 하나라도 없다.
- 현재 활성 상태를 카드 또는 패널에서 확인할 수 없다.
- 권한 없는 사용자가 설정을 저장할 수 있다.
- 저장 후 토스트 또는 로그 안내가 없다.
- 저장 감사로그 또는 메뉴별 로그가 남지 않는다.
- 업무 화면 우측 상단의 개별 시스템 설정 버튼으로 설정 기능에 접근된다.

승인 조건:

- 7개 대상 메뉴 카드가 모두 실제 메뉴별 설정 팝업/패널을 연다.
- 각 패널에 필드, 토글, 권한 옵션, 저장 버튼, 활성 상태 표시가 존재한다.
- 권한 있는 사용자의 저장은 성공하고 토스트 또는 로그 안내가 표시된다.
- 권한 없는 사용자의 저장은 차단되고 차단 로그가 남는다.
- 저장 성공 시 변경 전후 값, 사용자, 시각, 메뉴 ID가 감사로그 또는 메뉴별 로그에 남는다.

의존성: Role Menu & UI Controls, Menu Log Records, Security & Audit Baseline, A3 설정 UI, A7 권한/감사 기준, A9 로그 보존.

담당: A8 검증, A3/A7/A9 수정.

KPI 영향: 설정 누락, 오조작, 운영 오류, 재작업 시간, 감사 추적 시간.

인당 생산성/마진 기여: 메뉴별 설정의 실제 연결과 저장 피드백을 검증해 설정 누락과 오조작을 줄이고 운영 오류와 재작업 시간을 낮춘다.

### 5.16 팀 채팅방 검증

목적: 팀원 선택 기반 DM과 단톡방 기존 방 전환 또는 신규 생성, 채팅방 목록/활성방/참여자/메시지 UI/파일 첨부 동작, 생성·전환·전송 로그를 검증해 협업 오류와 전달 누락을 줄인다.

입력: 로그인 사용자, 팀원 목록, 선택한 참여자, 기존 DM, 기존 동일 참여자 단톡방, 채팅방 유형, 메시지 본문, 메시지 시간, 감사로그 ID, 첨부 파일, 권한 계정.

출력: 기존 DM 전환 또는 신규 DM, 기존 동일 참여자 단톡방 전환 또는 신규 단톡방, 채팅방 목록, 활성 채팅방, 참여자 표시, 전송 메시지, 보낸 사람 이름 라벨, 내/상대 메시지 좌우 배치, 메시지 시간, 감사로그 ID, 첨부 파일 상태, 채팅방 생성/전환 로그, 메시지 전송 로그 또는 감사로그.

인수조건:

- 팀원 1명을 선택하면 해당 팀원과의 기존 DM이 있으면 즉시 활성 채팅방으로 전환되고, 기존 DM이 없으면 신규 DM이 생성된다.
- 동일 팀원을 다시 선택해도 중복 DM이 생성되지 않고 기존 DM으로 전환된다.
- 여러 팀원을 선택하면 동일 참여자 조합의 기존 단톡방이 있으면 즉시 활성 채팅방으로 전환되고, 기존 단톡방이 없으면 신규 단톡방이 생성된다.
- 동일 참여자 조합을 다시 선택해도 중복 단톡방이 생성되지 않고 기존 단톡방으로 전환된다.
- 참여자를 선택하지 않은 상태에서는 DM 또는 단톡방 생성이 차단된다.
- 채팅방 생성 또는 기존 방 전환 후 채팅방 목록의 최신 순서, 활성방 표시, 참여자 표시가 갱신된다.
- 신규 채팅방 안내 메시지는 `DM을 생성했습니다` 같은 유형명 단독 문구가 아니라 대상 직원명 또는 단톡방명을 포함한다.
- 활성 채팅방에는 참여자 목록 또는 참여자 수가 표시된다.
- 메시지 입력 후 전송 버튼을 누르거나 Enter 키를 누르면 메시지가 활성 채팅방에 표시된다.
- 모든 메시지에는 보낸 사람 이름이 메시지 본문과 분리된 별도 라벨로 표시된다.
- 현재 사용자가 보낸 메시지도 보낸 사람 이름 라벨이 표시된다.
- 내 메시지는 우측, 상대 메시지는 좌측에 배치되어 발신자를 시각적으로 구분할 수 있다.
- 메시지 본문, 전송 시간, 감사로그 ID는 각각 분리 표시되어 본문과 추적 정보가 혼동되지 않는다.
- DM과 단톡방은 동일한 메시지 구조로 보낸 사람 이름, 본문, 시간, 감사로그 ID를 표시한다.
- 파일 첨부 버튼은 파일 선택/첨부 대기/첨부 완료 또는 실패 상태를 표시한다.
- 채팅방 생성, 기존 방 전환, 메시지 전송은 사용자, 시각, 참여자, 채팅방 ID, 이벤트 결과와 함께 로그 또는 감사로그에 남는다.
- 권한 없는 사용자는 초대 대상이 아닌 채팅방 목록, 메시지, 첨부 파일에 접근할 수 없다.

반려 기준:

- 팀원 1명 선택 시 기존 DM 전환 또는 신규 DM 생성이 동작하지 않는다.
- 팀원 체크박스 또는 팀원 행을 클릭해도 기존 방 전환 또는 신규 방 생성이 동작하지 않는다.
- 동일 팀원 재선택 시 중복 DM이 생성된다.
- 여러 팀원 선택 시 기존 동일 참여자 단톡방 전환 또는 신규 단톡방 생성이 동작하지 않는다.
- 동일 참여자 조합 재선택 시 중복 단톡방이 생성된다.
- 참여자 미선택 상태에서 채팅방이 생성된다.
- 채팅방 생성/전환 후 채팅방 목록, 활성 채팅방, 참여자 표시, 로그 갱신 중 하나라도 동작하지 않는다.
- 신규 채팅방 안내 메시지가 대상 직원명 또는 단톡방명 없이 유형명만 표시된다.
- 메시지 전송 또는 파일 첨부 버튼이 동작하지 않거나 상태 피드백이 없다.
- 보낸 사람 이름 라벨이 없거나 현재 사용자 메시지에서 이름이 생략된다.
- 내 메시지와 상대 메시지의 좌우 배치가 구분되지 않는다.
- 메시지 본문, 전송 시간, 감사로그 ID가 같은 텍스트 블록으로 섞여 표시된다.
- DM과 단톡방의 메시지 표시 구조가 달라 동일 기준으로 검증할 수 없다.
- 채팅방 생성, 기존 방 전환, 메시지 전송 로그 또는 감사로그가 남지 않는다.
- 초대되지 않은 사용자가 채팅방 또는 첨부 파일에 접근할 수 있다.

승인 조건:

- 1명 선택 시 기존 DM 전환 또는 신규 DM 생성, 동일 팀원 재선택 시 중복 DM 생성 금지가 모두 통과한다.
- 여러 명 선택 시 기존 동일 참여자 단톡방 전환 또는 신규 단톡방 생성, 동일 참여자 조합 재선택 시 중복 단톡방 생성 금지가 모두 통과한다.
- 참여자 미선택 생성 차단이 통과한다.
- 채팅방 목록, 활성 채팅방 전환, 참여자 표시, 로그 갱신, 메시지 전송 버튼, Enter 전송, 파일 첨부 버튼 상태가 모두 확인된다.
- DM과 단톡방의 모든 메시지에서 보낸 사람 이름 라벨, 현재 사용자 이름 표시, 내 메시지 우측/상대 메시지 좌측 배치, 본문/시간/감사로그 ID 분리 표시가 확인된다.
- 채팅방 생성, 기존 방 전환, 메시지 전송 로그 또는 감사로그가 확인된다.
- 권한 없는 채팅방/메시지/첨부 파일 접근이 차단되고 차단 로그가 남는다.

의존성: CRM Core 임직원 기준 데이터, Security & Audit Baseline, Menu Log Records, A2 채팅 API, A3 채팅 UI, A7 권한/감사 기준, A9 로그 보존.

담당: A8 검증, A2/A3/A7/A9 수정.

KPI 영향: 전달 누락, 협업 확인 시간, 파일 공유 오류, 권한 관련 재처리.

인당 생산성/마진 기여: 팀 채팅방 생성과 메시지/파일 전달을 검증해 협업 오류와 전달 누락을 줄이고 반복 확인 시간을 낮춘다.

## 8. MVP 공통 반려 기준

다음 항목 중 하나라도 해당하면 MVP QA는 해당 스토리를 반려한다.

- 목적, 입력, 출력, 인수조건, 의존성, 담당, KPI 영향 중 하나가 누락된 스토리.
- 운영 상태 변경이 감사로그 없이 수행되는 기능.
- 권한 없는 사용자가 타 고객사 또는 민감 데이터에 접근 가능한 기능.
- 포인트/정산/연동 처리에서 멱등성 기준이 없는 기능.
- 실패 또는 예외가 운영 큐로 남지 않아 사람이 추적할 수 없는 기능.
- 대시보드 지표의 원천 데이터와 계산 기준이 추적되지 않는 기능.
- 자동화 후보 기능이 오탐/오처리 시 수동 보정 경로를 제공하지 않는 기능.
- 영업활동부터 매출인식까지 참조 ID가 끊기는 기능.
- 영업이익 산식, 권한별 메뉴, 고정 헤더, 고객 신규/수정 저장, 판매가격 표시, 결재라인, 배송상태, 타임로그 중 팀장 지시 항목을 검증할 수 없는 기능.
- 권한 제한이 메뉴 표시만 제어하고 API 또는 데이터 접근을 차단하지 않는 기능.
- 고정 헤더/가로스크롤, 고객 신규/수정 저장, 판매가격 표시, 권한별 메뉴, 설정 옆 사용자 정보, 로그기록 메뉴, 배송/입출고 현재 위치, 슈퍼바이저 대시보드 권한 중 하나라도 시나리오로 검증할 수 없는 기능.
- 각 업무 메뉴 우측 상단에 시스템 설정 버튼이 남아 있거나, 설정 기능이 상단 메인 설정 메뉴가 아닌 개별 화면에서 접근되거나, 화면별 보기 옵션이 설정 버튼과 혼동되는 기능.
- 직원 1명에 여러 거래처 배정, 거래처 1개에 여러 담당자 표시, 대표 담당자 표시, 권한 없는 배정 변경 차단, 배정 변경 로그 중 하나라도 검증할 수 없는 기능.
- 결재 버튼 클릭 시 상태 즉시 확인, 승인/반려/보류 버튼 의미 표시, 반려/보류 사유 필수, 결재 액션 로그 생성 중 하나라도 검증할 수 없는 기능.
- 입사등록 결재라인 설정 전 상신 차단, 결재라인 설정 후 상신 가능, 최종 승인 전 계정 활성화 금지, 입사등록 승인상태와 결재문건 상태 일치, 승인/반려/보류 사유 및 로그 생성 중 하나라도 검증할 수 없는 기능.
- 설정 메뉴 로그기록에서 메뉴별 로그 조회/필터, 메뉴 진입/목록/상세/수정/결재/반출 로그 생성, 권한 차단 로그, 로그 조회 감사로그 중 하나라도 검증할 수 없는 기능.
- Master/ProfitCostInputManager만 제원원가/판관비/일반관리비 입력 가능, 일반/관리자 저장 차단, 권한 없는 URL 접근 차단, 변경 사유/적용일/산식 버전 필수, 변경 전후 값 로그, 결재 대상의 승인 전 대시보드 미반영 중 하나라도 검증할 수 없는 기능.
- PM 승인 전 외주 접속 비활성, 개인별 외주 계정/만료일, 허용 IP 또는 접속 정책, 권한 없는 메뉴/개인정보/다운로드 차단, 접속/메뉴별 로그 생성, 기간 종료 후 계정 회수 중 하나라도 검증할 수 없는 기능.
- 메뉴별 설정 통합 화면에서 대상 메뉴 카드 클릭 시 실제 설정 팝업/패널이 열리지 않거나, 필드/토글/권한/저장 버튼/활성 상태/저장 피드백/감사로그 중 하나라도 검증할 수 없는 기능.
- 팀원 1명 선택 시 기존 DM 전환 또는 신규 DM 생성, 동일 팀원 재선택 시 중복 DM 생성 금지, 여러 명 선택 시 기존 동일 참여자 단톡방 전환 또는 신규 단톡방 생성, 동일 참여자 조합 재선택 시 중복 단톡방 생성 금지, 채팅방 목록/활성 채팅방/참여자 표시/로그 갱신, 참여자 미선택 생성 차단 중 하나라도 검증할 수 없는 기능.
- 팀 채팅방 메시지에서 보낸 사람 이름 별도 라벨, 현재 사용자 이름 표시, 내 메시지 우측/상대 메시지 좌측 배치, 메시지 본문과 시간/감사로그 ID 분리 표시, DM/단톡방 동일 메시지 구조 중 하나라도 검증할 수 없는 기능.

인당 생산성/마진 기여: 반려 기준을 명시해 운영 비용을 키우는 불완전한 기능의 릴리즈를 차단한다.
