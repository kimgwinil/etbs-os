# 이제너두 전사 CRM OS A2 백엔드 초안

## 1. 문서 목적

이 문서는 이제너두 전사 CRM OS의 A2 백엔드 관점 초안으로, `/docs/PRD.md`의 P0 모듈과 `/docs/PROCESS_REQUIREMENTS.md`의 유통회사형 표준 업무 흐름을 구현 가능한 도메인, API, 상태, 권한, 감사로그 경계로 정리한다.

본 문서는 개발 확정안이 아니며, 예산, 외부계약, 개인정보 처리범위, 회계 기준, 택배사/세금계산서 연동, 최종 아키텍처는 PM 김권일 승인 전 확정하지 않는다.

인당 생산성/마진 기여: 영업활동부터 매출인식까지 단일 상태 흐름으로 연결해 부서 간 재입력, 누락 확인, 수기 검산 시간을 줄인다.

## 3. A2 백엔드 범위

### 3.1 포함

- 고객사, 공급사, 임직원, 담당자, 상품, 계약의 기준 API 경계
- 임직원-거래처 다대다 담당 배정 API 경계
- 입사등록 결재문건, 결재라인, 승인상태, 최종 승인 후 계정 활성화 API 경계
- 제원원가, 판관비, 일반관리비 설정 입력과 수익성 산식 버전 관리 API 경계
- 영업활동, 타임로그, 파이프라인, 견적, 결재라인, 계약 전환 API 경계
- 계약 기반 주문, 출고 요청, 출고 완료, 배송상태 조회/보정 API 경계
- 세금계산서, 거래명세표 발행 상태와 외부 연동 어댑터 호출 경계
- 출고/검수/청구 기준 매출인식 후보 API와 조정 결재 경계
- 운영 업무 큐, 예외 큐, SLA, 일괄 처리 API 경계
- 테넌트 격리, 권한 검사 지점, 개인정보 접근로그, 감사로그, 타임로그 기준

인당 생산성/마진 기여: 업무 단계별 API 책임을 고정해 프론트, 데이터, 연동, QA가 병렬로 개발 가능한 기준을 제공한다.

### 3.2 제외 및 PM 승인 필요

| 항목 | 상태 | 승인 전 원칙 |
|---|---|---|
| 개인정보/민감정보 상세 필드 | PM 승인 필요 | ID 참조, 마스킹, 최소 필드 후보만 사용 |
| 택배사 실시간 위치 API, 비용, 계약 조건 | PM 승인 필요 | `deliveryAdapter` 경계와 수동 보정 큐까지만 정의 |
| 세금계산서/거래명세표 외부 발행 벤더 | PM 승인 필요 | 발행 요청/상태/증적 API만 정의 |
| 공식 회계 매출인식 기준 | PM 승인 필요 | MVP 후보 상태와 승인 기반 조정 API만 정의 |
| 원가 50%, 판관비/일반관리비 50% 산식의 공식 사용 | PM 승인 필요 | 수익성 대시보드 후보 산식으로만 반영 |
| `제원원가`의 정확한 회계 의미 | PM 승인 필요 | 제조원가, 상품원가, 기타 원가 중 확정 전 용어 후보로만 사용 |
| 비용 입력 권한 범위 | PM 승인 필요 | `Master`, `ProfitCostInputManager` 후보 권한으로 정의 |
| 비용 변경 결재 필수 여부 | PM 승인 필요 | 전사 영업이익 영향 변경은 결재 대상 후보로 정의 |
| DBMS, 메시지큐, 검색엔진, BI, IAM 제품 | PM 승인 필요 | 논리 계약만 정의 |
| 거래처별 대표 담당자 1명 제한 여부 | PM 승인 필요 | 기본 후보는 거래처별 활성 대표 담당자 1명 |
| 결재 `on_hold` 공식 상태 채택 여부 | PM 승인 필요 | API에는 보류 상태 후보와 로그 조건을 정의 |
| 입사등록 결재 필수 여부 | PM 승인 필요 | 기본 후보는 결재라인 최종 승인 전 계정 활성화 금지 |
| 최종 승인 후 계정 활성화 방식 | PM 승인 필요 | 자동 활성화 또는 관리자 확인 후 활성화는 후속 결정 |

인당 생산성/마진 기여: 불확정 외부계약과 정책을 구현 확정으로 오인하지 않게 해 폐기될 개발비를 줄인다.

## 4. 핵심 결정 초안

| 결정 ID | 결정 | 상태 | 인당 생산성/마진 기여 |
|---|---|---|---|
| `D-A2-001` | 모든 업무 리소스는 `tenant_id`, `tenant_type`, `tenant_scope`, `owner_user_id`, `status`를 가진다. | 초안 | 테넌트/담당자/상태 기준 필터를 표준화해 운영자가 다음 처리 대상을 찾는 시간을 줄인다. |
| `D-A2-002` | 영업활동, 파이프라인, 견적, 계약, 주문, 출고, 배송, 발행, 매출인식은 같은 `business_flow_id`로 연결한다. | 초안 | 부서별 단절된 ID 매칭과 수기 추적을 줄여 리드타임과 오류를 낮춘다. |
| `D-A2-003` | 견적, 계약, 세금계산서/거래명세표, 매출인식 조정은 `approval_request`를 선택 또는 필수 결재 경계로 둔다. | 초안 | 승인 누락과 책임소재 확인 시간을 줄이고 금액 오류 손실을 예방한다. |
| `D-A2-004` | 모든 핵심 상태 변경은 `time_log`와 `audit_log`를 함께 남긴다. | 초안 | 처리시간과 변경근거를 자동 축적해 생산성 측정과 외감 대응 수작업을 줄인다. |
| `D-A2-005` | 배송과 발행 외부 연동 실패는 `work_item` 예외 큐로 승격한다. | 초안 | 담당자가 장애 건을 별도 시스템에서 찾지 않게 해 처리 누락과 문의 대응 시간을 줄인다. |
| `D-A2-006` | 목록 API는 기본적으로 커서 페이지네이션과 서버 측 테넌트 필터를 사용한다. | 초안 | 260만 명 이상 임직원 규모에서도 화면 지연과 대량 조회 사고를 줄인다. |
| `D-A2-007` | 개인정보 원문, 마스킹 해제, 다운로드, 외부 전송은 별도 접근 목적과 접근로그 없이는 허용하지 않는다. | 초안 | 불필요한 개인정보 노출과 감사 대응 비용을 줄인다. |
| `D-A2-008` | 매출인식 API는 공식 회계 확정 전 `candidate`, `approved`, `recognized`, `reversed` 상태만 정의한다. | PM 승인 필요 | 회계 기준 미확정 상태에서도 운영 손익 후보 지표를 만들되 재작업 위험을 낮춘다. |
| `D-A2-009` | 고객 신규 등록 화면의 저장은 `POST /client-companies` 성공으로 신규 고객 생성 완료로 본다. | 초안 | 고객 등록 완료 기준을 명확히 해 중복 저장, 저장 여부 재확인, 담당자 문의를 줄인다. |
| `D-A2-010` | 고객 수정 화면의 저장은 `PATCH /client-companies/{client_company_id}` 성공과 변경 이력 생성으로 변경 완료로 본다. | 초안 | 변경 완료 기준과 이력을 고정해 고객정보 불일치와 사후 확인 시간을 줄인다. |
| `D-A2-011` | 상품 등록/수정 API는 `sale_price`를 필수 판매가격 필드로 관리하고 목록/견적 응답에 별도 노출한다. | 초안 | 견적 담당자의 가격 확인 시간을 줄이고 잘못된 판매가격 적용으로 인한 마진 손실을 낮춘다. |
| `D-A2-012` | 결재문건 상신자는 요청 본문이 아니라 로그인 세션의 `actor_user_id`로 자동 지정한다. | 초안 | 대리/오입력으로 인한 승인 책임 혼선을 줄이고 결재 추적 시간을 단축한다. |
| `D-A2-013` | 타임로그는 영업활동 생성, 파이프라인 단계 변경, 결재 상신/승인/반려, 업무 시작/보류/완료, 출고 완료, 발행 실패/재처리, 매출인식 확정/조정 시 생성 또는 갱신한다. | 초안 | 사람이 별도 시간을 입력하지 않아도 핵심 처리시간이 축적되어 생산성 분석 비용을 줄인다. |
| `D-A2-014` | 임직원과 거래처는 `employee_customer_assignment`로 다대다 배정하며 직원 1명은 여러 거래처, 거래처 1곳은 여러 담당자를 가질 수 있다. | 초안 | 실제 업무 분담을 반영해 담당자 공백과 거래처별 중복 문의를 줄인다. |
| `D-A2-015` | 담당자 배정 생성, 역할 변경, 대표 담당자 변경, 종료는 권한 검사, 사유 입력, 타임로그, 감사로그 대상이다. | 초안 | 담당 변경 이력을 자동 축적해 인수인계와 책임 확인 시간을 줄인다. |
| `D-A2-016` | 결재 버튼은 상태 변경이 아니라 상세/처리 화면 진입으로 정의하고, 승인/반려/보류/회수 버튼만 결재 상태를 변경한다. | PM 승인 필요 | 버튼 오처리로 인한 재상신과 승인 지연을 줄인다. |
| `D-A2-017` | 승인은 승인 의견 후보, 반려/보류는 사유 필수, 회수는 사유 후보를 요구하며 모든 액션은 권한 검사와 타임로그/감사로그를 수행한다. | 초안 | 결재 처리 사유와 결과 상태를 표준화해 후속 업무 지연과 감사 확인 시간을 줄인다. |
| `D-A2-018` | 입사등록의 `approval_status`는 별도 수동 표시값이 아니라 연결된 `approval_request.status`의 투영값으로 관리한다. | 초안 | 승인상태 불일치와 승인 누락으로 인한 계정/권한 재작업을 줄인다. |
| `D-A2-019` | 입사등록 결재라인이 없으면 상신 API는 `409 approval_line_required`로 차단한다. | 초안 | 결재자 없는 상신과 승인 대기 누락을 막아 HR 처리 지연을 줄인다. |
| `D-A2-020` | 입사등록은 최종 승인 전 `employee_account` 활성화와 권한 부여 완료를 금지하고, 최종 승인 후 `employee_activation_pending`으로 전환한다. | PM 승인 필요 | 승인 없는 계정 활성화와 권한 오부여에 따른 보안/운영 비용을 줄인다. |
| `D-A2-021` | 제원원가, 판관비, 일반관리비 입력/수정/삭제 API는 `Master` 또는 `ProfitCostInputManager` 후보 권한만 허용한다. | PM 승인 필요 | 영업이익 지표를 바꾸는 입력 권한을 제한해 경영 판단 오류와 재검산 시간을 줄인다. |
| `D-A2-022` | 비용 입력 변경은 변경 사유, 적용일, 적용 범위, 산식 버전, 변경 전후 값을 필수 감사 메타데이터로 저장한다. | 초안 | 잘못된 비용 입력의 원인과 영향 범위를 빠르게 추적해 수익성 지표 신뢰도를 유지한다. |
| `D-A2-023` | 권한 없는 비용 입력 저장 시도는 차단하고 보안/감사 로그를 남긴다. | 초안 | 임의 비용 변경을 막고 이상 시도를 추적해 지표 훼손 리스크를 줄인다. |
| `D-A2-024` | 전사 영업이익에 영향을 주는 비용/산식 변경은 결재 대상 후보로 두며 최종 승인 전 대시보드 공식 반영을 차단한다. | PM 승인 필요 | 승인 없는 산식 변경으로 인한 의사결정 오류와 대시보드 재계산 비용을 줄인다. |

인당 생산성/마진 기여: 견적 승인과 발행 상태를 분리해 할인 승인 누락과 재발행 혼선을 줄인다.

### 7.3 계약 상태

| 상태 | 의미 | 허용 액션 |
|---|---|---|
| `draft` | 등록 중 | `submit_approval`, `activate`, `void` |
| `approval_required` | 결재 필요 | `approve`, `reject` |
| `active` | 유효 계약 | `amend`, `suspend`, `create_order`, `expire`, `terminate` |
| `amended` | 변경 계약 | `activate`, `terminate` |
| `suspended` | 일시 중지 | `resume`, `terminate` |
| `expired` | 기간 만료 | 읽기 전용 |
| `terminated` | 해지 | 읽기 전용 |

인당 생산성/마진 기여: 계약 상태를 주문 가능 여부와 연결해 잘못된 주문과 청구 오류를 줄인다.

인당 생산성/마진 기여: 주문, 출고, 배송 상태를 분리해 어느 단계에서 지연되는지 즉시 파악할 수 있다.

인당 생산성/마진 기여: 발행과 매출인식의 확정 상태를 분리해 월마감 누락과 오류 수정 시간을 줄인다.

### 7.6 결재 상태

| 상태 | 의미 | 허용 액션 |
|---|---|---|
| `draft` | 문건 작성 중 | `submit` |
| `submitted` | 상신 완료 | `approve_step`, `reject`, `withdraw` |
| `in_progress` | 결재 진행 중 | `approve_step`, `reject` |
| `on_hold` | 현재 결재자가 추가 확인을 위해 보류 | `approve_step`, `reject`, `withdraw` 후보 |
| `approved` | 최종 승인 | 대상 업무 후속 액션 |
| `rejected` | 반려 | 대상 업무 수정 또는 종료 |
| `withdrawn` | 회수 | 재상신 가능 |

인당 생산성/마진 기여: 결재 단계를 데이터로 관리해 승인 대기와 병목 담당자를 자동 식별할 수 있다.

### 7.7 결재 버튼별 API 의미

| 버튼 | API 의미 | 결과 상태 | 필수 입력 | 권한 검사 | 로그 |
|---|---|---|---|---|---|
| 결재 | 결재 상세 또는 처리 화면 조회 | 상태 변경 없음 | 없음 | 결재 대상 조회 권한 또는 현재 결재자 여부 | 조회 로그 후보 |
| 승인 | 현재 결재자가 현재 단계를 승인 | 다음 결재자 있으면 `in_progress`, 최종이면 `approved` | 승인 의견 후보 | 현재 결재자, 대리권한 후보, 테넌트 범위 | 타임로그, 감사로그 |
| 반려 | 현재 결재자가 문건을 반려 | `rejected` | 반려 사유 필수 | 현재 결재자, 테넌트 범위 | 타임로그, 감사로그 |
| 보류 | 현재 결재자가 추가 확인을 위해 보류 | `on_hold` | 보류 사유 필수 | 현재 결재자, 테넌트 범위 | 타임로그, 감사로그 |
| 회수 | 상신자가 승인 전 문건을 회수 | `withdrawn` | 회수 사유 후보 | 상신자 본인, 아직 최종 승인 전 | 타임로그, 감사로그 |

인당 생산성/마진 기여: 버튼별 결과 상태와 필수 사유를 고정해 잘못된 결재 처리와 상태 확인 문의를 줄인다.

### 7.8 결재 결과의 대상 업무 반영

| 대상 업무 | 최종 승인 시 | 반려 시 | 보류 시 |
|---|---|---|---|
| 견적 | `quote.approved`, 발행 또는 계약 전환 가능 | `quote.rejected`, 수정 필요 | `quote.approval_required` 유지, 검토 대기 |
| 계약 | `contract.active` 후보, 주문 등록 가능 | `contract.draft` 또는 수정 필요 | `contract.approval_required` 유지 |
| 세금계산서/거래명세표 | 발행 요청 가능 | 발행 요청 반려 | 발행 보류 |
| 매출인식 조정 | 조정 반영 가능 | 조정 요청 반려 | 조정 검토 대기 |
| 입사등록 | 입사 승인 완료, `employee_activation_pending` 전환 | 입사등록 반려, 수정 필요 | 입사등록 검토 대기, 계정 활성화 차단 유지 |

인당 생산성/마진 기여: 결재 결과가 후속 업무 가능 여부와 바로 연결되어 매출, 발행, 주문 지연을 줄인다.

### 7.9 입사등록 상태

| 상태 | 의미 | 다음 가능 상태 |
|---|---|---|
| `draft` | 입사등록 초안 | `submitted`, `withdrawn` |
| `submitted` | 결재 상신 완료 | `in_review`, `withdrawn` |
| `in_review` | 결재 진행 중 | `approved`, `rejected`, `on_hold` |
| `on_hold` | 추가 확인 보류 | `in_review`, `rejected`, `withdrawn` |
| `rejected` | 반려 | `draft` 또는 종료 |
| `approved` | 최종 결재 승인 | `employee_activation_pending` |
| `employee_activation_pending` | 계정 활성화 대기 | `activated` |
| `activated` | 입사등록 최종 반영 | 종료 |

입사등록의 `approval_status`는 위 상태를 별도 저장값으로 임의 변경하지 않고 연결된 결재문건 상태와 활성화 상태를 기준으로 계산 또는 투영한다.

인당 생산성/마진 기여: 입사승인과 계정 활성화 단계를 분리해 승인 없는 권한 부여와 사후 회수 작업을 줄인다.

## 10. 백엔드 인수조건

1. 모든 도메인 요구사항은 목적, 입력, 출력, DoD, 의존성, 담당, KPI 영향을 가진다.
2. API 스펙은 리소스, 행위, 상태, 권한 검사, 감사로그 대상을 포함한다.
3. 영업활동부터 매출인식까지 `business_flow_id`로 연결 가능해야 한다.
4. 견적, 계약, 발행, 매출인식 조정은 결재라인과 연결 가능해야 한다.
5. 고객 신규 저장은 생성 완료, 고객 수정 저장은 변경 완료로 볼 수 있는 API 성공 기준과 변경 이력을 가져야 한다.
6. 상품 API와 견적 API는 `sale_price`를 별도 필드로 취급해 판매가격 확인이 가능해야 한다.
7. 결재문건 상신자는 로그인 사용자로 자동 지정되고 클라이언트 입력으로 변경할 수 없어야 한다.
8. `employee_customer_assignment`로 직원 1명 대 여러 거래처, 거래처 1곳 대 여러 담당자 배정이 가능해야 한다.
9. 담당자 배정 생성/변경/종료는 권한 검사, 사유 입력, 타임로그, 감사로그를 요구해야 한다.
10. 승인/반려/보류/결재/회수 버튼별 결과 상태, 사유 입력, 권한 검사, 로그 생성 조건이 명시되어야 한다.
11. 입사등록의 `승인상태`는 연결된 결재문건 상태와 일치해야 하며 결재라인 설정 전 상신이 차단되어야 한다.
12. 입사등록 최종 승인 전에는 임직원 계정 활성화와 권한 부여 완료가 금지되어야 한다.
13. 제원원가, 판관비, 일반관리비 입력/수정/삭제는 `Master` 또는 `ProfitCostInputManager` 후보 권한으로 제한되어야 한다.
14. 비용 입력 변경은 변경 사유, 적용일, 적용 범위, 산식 버전, 변경 전후 값, 변경자를 감사로그로 남겨야 한다.
15. 권한 없는 비용 저장 시도는 차단되고 로그로 남아야 한다.
16. 비용 변경이 결재 대상 후보이면 최종 승인 전 대시보드 공식 반영이 차단되어야 한다.
17. 타임로그 생성 조건은 고객 저장, 담당자 배정, 입사등록, 비용 입력, 영업활동, 파이프라인, 결재, 계약, 주문, 출고, 발행, 매출인식, 운영 업무 처리에 대해 명시되어야 한다.
18. 주문, 출고, 배송, 발행 실패는 운영 업무 큐 또는 예외 큐로 전환 가능해야 한다.
19. 개인정보 상세, 다운로드, 마스킹 해제, 외부 전송은 PM 승인 필요 항목과 접근로그 요구가 표시되어야 한다.
20. 공식 회계 기준, 택배사 연동, 세금계산서 발행 벤더, 개인정보 처리범위는 `PM 승인 필요`로 표시되어야 한다.

인당 생산성/마진 기여: 인수조건을 구현 가능성과 검증 가능성 중심으로 고정해 후속 개발과 QA 재해석 비용을 줄인다.
