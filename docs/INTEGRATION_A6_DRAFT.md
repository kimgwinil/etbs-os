# A6 통합/연동 초안

## 1. 문서 목적

이 문서는 이제너두 전사 CRM OS의 P1 범위인 Integration Hub와 Settlement & Point Ops를 대상으로 외부 연동 현황 파악 질문지, 어댑터 스펙 초안, 장애/예외 큐 운영 기준을 정의한다.

본 문서는 개발 확정안이 아니라 A6 통합/연동 담당자의 초안이며, 예산, 외부계약, 개인정보 처리범위, 아키텍처 확정은 PM 김권일 승인 후 진행한다.

인당 생산성/마진 기여: 연동별 예외 처리와 재처리 기준을 표준화해 장애 대응 시간을 줄이고 정산/포인트 오류로 인한 재작업과 손실을 낮춘다.

## 2. 기준 범위

### 포함 범위

| 영역 | 포함 항목 | 설명 |
|---|---|---|
| 베네카페 연동 | 회원/고객사/복지포인트/주문 상태 연동 | 상세 API 문서 미제공으로 가정 기반 초안 |
| 결제 연동 | 승인, 취소, 부분취소, 환불, 웹훅, 대사 | PG/간편결제/가상계좌 여부 PM 승인 필요 |
| 온누리 연동 | 상품권/포인트성 결제 또는 정산 상태 연동 | 연동 주체와 API 제공 범위 확인 필요 |
| 외부 공급사 API | 상품, 주문, 배송, 정산, 클레임 상태 | 공급사별 프로토콜 차이를 어댑터로 흡수 |
| 정산/포인트 시스템 | 지급, 차감, 만료, 회수, 정산 근거 추적 | Settlement & Point Ops 예외 큐와 연결 |
| Integration Hub | 멱등성, 재시도, 실패 큐, 폴백, 모니터링 | 모든 외부 연동 공통 계약 |

인당 생산성/마진 기여: 연동 후보를 동일한 처리 단위로 묶어 담당자별 개별 대응과 중복 개발을 줄인다.

### 제외 범위

- 상세 API별 필드 확정
- 외부 계약 조건 또는 요금제 확정
- 개인정보 항목, 보관기간, 위탁/재위탁 범위 확정
- 정산 회계 전표 생성 방식 확정
- 특정 벤더 SDK 또는 클라우드 메시징 제품 확정

인당 생산성/마진 기여: 확정되지 않은 외부 조건을 구현 범위로 오인하지 않게 해 불필요한 개발비와 계약 리스크를 줄인다.

## 3. 핵심 원칙

| 원칙 | 기준 | PM 승인 필요 여부 |
|---|---|---|
| 멱등성 우선 | 모든 쓰기성 외부 요청은 `idempotencyKey`를 가져야 한다. | 아키텍처 확정 전 최종 승인 필요 |
| 상태 전이 기록 | 외부 연동 요청/응답/재시도/수동 보정은 감사 가능한 이벤트로 남긴다. | 보존기간 PM 승인 필요 |
| 실패 큐 기본화 | 자동 복구 불가 또는 반복 실패 건은 운영 콘솔 예외 큐로 이동한다. | 운영 권한 범위 PM 승인 필요 |
| 안전 폴백 | 외부 시스템 장애 시 중복 지급/중복 승인보다 보류와 수동 검토를 우선한다. | 업무 정책 PM 승인 필요 |
| 개인정보 최소화 | 어댑터에는 식별자와 업무 처리에 필요한 최소 필드만 전달한다. | 개인정보 처리범위 PM 승인 필요 |
| 대사 가능성 | 결제, 포인트, 정산은 원천 거래와 내부 원장의 비교 기준을 가진다. | 회계 기준 PM 승인 필요 |

인당 생산성/마진 기여: 중복 처리와 추적 불가 상태를 막아 장애 한 건당 확인 인력과 보정 비용을 줄인다.

## 4. 연동 현황 파악 질문지

### 4.1 공통 질문

| 연동 목적 | 조회, 등록, 상태 변경, 정산, 알림 중 어떤 업무를 처리하는가? | 업무 담당자 | 목적/입출력 |
| 호출 방향 | CRM OS가 호출하는가, 외부 시스템이 웹훅을 보내는가, 배치 파일을 교환하는가? | 개발/운영 | 어댑터 타입 |
| 프로토콜 | REST, SOAP, SFTP, CSV, DB Link, 메시지 큐 중 무엇인가? | 개발/벤더 | 계약 방식 |
| 인증 | API Key, OAuth2, mTLS, IP allowlist, 세션 인증 중 무엇인가? | 보안/벤더 | 보안 요구 |
| 식별자 | 고객사, 임직원, 주문, 결제, 포인트 거래의 원천 ID는 무엇인가? | 운영/개발 | 멱등성/대사 |
| 처리량 | 일평균/피크 요청 수와 배치 파일 크기는 어느 정도인가? | 운영/개발 | 성능 기준 |
| SLA | 응답시간, 장애 공지, 복구 목표, 정기 점검 시간이 있는가? | 벤더/운영 | 모니터링 |
| 실패 응답 | 에러 코드표, 재시도 가능 여부, 중복 요청 처리 방식이 문서화되어 있는가? | 벤더/개발 | 실패 큐 |
| 개인정보 | 연동에 포함되는 개인정보/민감정보 항목은 무엇인가? | 보안/법무 | PM 승인 필요 |
| 감사/보관 | 요청/응답 원문, 마스킹 로그, 정산 증적 보존기간은 얼마인가? | 재무/보안 | 감사 기준 |
| 수동 처리 | 장애 시 현재 담당자가 어떤 화면/엑셀/메일로 보정하는가? | 운영 | 예외 큐 |

인당 생산성/마진 기여: 질문지를 표준화해 연동 분석 회의 시간을 줄이고 누락된 조건으로 인한 재작업을 방지한다.

| 복지포인트 지급/차감/만료가 API로 제공되는가? | 지급/차감 내역 조회 API가 있다고 가정 | API 문서 필요 |
| 주문, 취소, 반품, 클레임 상태를 실시간으로 받을 수 있는가? | 웹훅 또는 배치 동기화가 있다고 가정 | 연동 방식 확인 필요 |
| 임직원 식별자는 사번, 회원번호, 내부 사용자 ID 중 무엇인가? | 외부 회원번호와 내부 `employeeId` 매핑 필요 | 개인정보 범위 PM 승인 필요 |

인당 생산성/마진 기여: 베네카페와 CRM OS의 기준 데이터 역할을 분리해 중복 입력과 포인트 문의 대응 시간을 줄인다.

인당 생산성/마진 기여: 공급사별 차이를 어댑터 계약으로 흡수해 공급사 추가와 장애 대응에 드는 개발/운영 시간을 줄인다.

## 5. 어댑터 스펙 초안

상세 계약은 `/specs/integration/adapter-contract.md`를 기준으로 한다.

### 5.1 공통 어댑터 목적

외부 시스템별 프로토콜과 데이터 형식 차이를 Integration Hub 내부 표준 계약으로 변환한다. 각 어댑터는 `requestId`, `idempotencyKey`, `externalSystem`, `operationType`, `correlationId`, `tenantId`를 공통으로 처리한다.

인당 생산성/마진 기여: 외부 연동 추가 시 공통 로깅, 재시도, 실패 큐를 재사용해 신규 연동 개발비를 낮춘다.

### 5.2 어댑터별 입력/출력/인수조건

| 어댑터 | 목적 | 입력 | 출력 | 인수조건 | 의존성 | 담당 | KPI 영향 |
|---|---|---|---|---|---|---|---|
| `benefitCafeAdapter` | 베네카페 회원/포인트/주문 상태 동기화 | 내부 고객사/임직원/포인트/주문 이벤트 | 외부 처리 결과, 외부 상태, 실패 사유 | 동일 `idempotencyKey` 재호출 시 중복 지급/중복 상태 변경이 없어야 한다. | 베네카페 API 문서, 개인정보 범위 | A6, A1, A2, A7 | 포인트 문의와 수동 보정 감소 |
| `paymentAdapter` | 결제 승인/취소/환불/대사 처리 | 주문 결제 요청, 취소 요청, 웹훅 이벤트 | 승인번호, 결제 상태, 정산 대사 결과 | 웹훅 중복 수신과 순서 역전에도 내부 상태가 일관되어야 한다. | PG API, 재무 대사 기준 | A6, A2, A4, A7 | 결제 오류 손실과 환불 처리 시간 감소 |
| `onnuriAdapter` | 온누리 거래 승인/취소/정산 상태 처리 | 온누리 거래 요청, 취소 요청, 대사 이벤트 | 외부 승인번호, 사용/취소 상태 | 외부 승인 미확인 시 지급 또는 정산 확정을 보류해야 한다. | 온누리 API, 업무 정책 | A6, A2, A4 | 정산 불일치와 고객 문의 감소 |
| `supplierApiAdapter` | 공급사 상품/주문/배송/클레임/정산 연동 | 상품 동기화 요청, 주문 이벤트, 클레임 이벤트 | 공급사 접수번호, 배송/클레임 상태 | 공급사 장애 시 주문 상태는 보류 또는 확인 필요로 전환되어야 한다. | 공급사 API/SFTP 문서 | A6, A3, A4 | 공급사 문의와 수동 파일 처리 감소 |
| `settlementPointAdapter` | 포인트 원장과 정산 상태 연계 | 포인트 지급/차감/만료/회수 이벤트, 정산 배치 | 원장 반영 결과, 정산 상태, 차이 내역 | 원장 반영 전후 금액 합계가 검증되고 차이 발생 시 예외 큐로 이동해야 한다. | 원장/정산 기준, 외감 요구 | A6, A4, A7 | 외감 대응 시간과 정산 오류 감소 |

인당 생산성/마진 기여: 어댑터마다 성공 기준을 KPI에 연결해 개발 우선순위가 장애 감소와 운영 처리량 향상에 맞춰지게 한다.

## 6. 예외 큐 및 재처리 기준

### 6.1 예외 큐 상태

| 상태 | 의미 | 자동 처리 | 운영자 조치 |
|---|---|---|---|
| `pending_retry` | 일시 장애로 자동 재시도 대기 | 가능 | 모니터링만 수행 |
| `retrying` | 재시도 실행 중 | 가능 | 중복 조치 금지 |
| `needs_review` | 원인 확인 후 재처리 여부 판단 필요 | 불가 | 요청/응답/내부 상태 확인 |
| `manual_correction_required` | 외부 또는 내부 수동 보정 필요 | 불가 | 보정 증적 입력 후 승인 요청 |
| `blocked_by_policy` | 업무 정책 또는 권한상 자동 처리 불가 | 불가 | PM/업무 책임자 승인 필요 |
| `resolved` | 재처리 또는 수동 보정 완료 | 불가 | 감사 로그 확인 |
| `discarded` | 업무상 처리하지 않기로 결정 | 불가 | 사유와 승인자 기록 필수 |

인당 생산성/마진 기여: 예외 상태를 표준화해 담당자가 원인 분류부터 다시 하는 시간을 줄이고 처리 누락을 방지한다.

### 6.2 실패 분류와 처리 기준

| 실패 유형 | 예시 | 재시도 기준 | 폴백 | 수동 보정 기준 | 모니터링 |
|---|---|---|---|---|---|
| 네트워크/타임아웃 | 연결 실패, 5xx, 응답 지연 | 지수 백오프 3회 후 예외 큐 | 내부 상태 `pending_external_confirmation` | 30분 이상 미확인 시 운영자 확인 | 에러율, p95 응답시간 |
| 인증/권한 실패 | 401, 403, 인증서 만료 | 자동 재시도 금지 | 신규 요청 차단 | 보안/개발 담당자 확인 | 인증 실패 카운트 |
| 유효성 오류 | 필수 필드 누락, 포맷 오류 | 자동 재시도 금지 | 내부 데이터 수정 전 보류 | 데이터 소유자 수정 후 재처리 | 유효성 실패율 |
| 중복 요청 | 동일 거래 재전송 | 멱등 응답 반환 | 기존 외부 상태 조회 | 외부 상태 불일치 시 수동 대사 | 멱등 충돌 수 |
| 상태 충돌 | 취소 후 승인 웹훅 도착 | 상태 머신으로 차단 | 최신 확정 상태 보류 | 업무 책임자 승인 후 보정 | 상태 충돌 수 |
| 금액 불일치 | 내부 결제금액과 외부 정산금액 차이 | 자동 재시도 금지 | 정산 확정 보류 | 재무 확인 후 차이 조정 | 대사 차이 금액 |
| 외부 정책 제한 | 취소 가능 기간 만료, 부분취소 불가 | 자동 재시도 금지 | 고객/운영 안내 필요 | PM/업무 책임자 승인 | 정책 차단 건수 |

인당 생산성/마진 기여: 자동 재시도와 수동 보정의 경계를 명확히 해 불필요한 반복 확인과 금전 오류 확산을 줄인다.

### 6.3 재처리 원칙

1. 동일 업무 이벤트는 동일 `idempotencyKey`로만 재처리한다.
2. 외부 요청 성공 여부가 불명확하면 상태 조회를 먼저 수행하고 쓰기 요청을 재전송하지 않는다.
3. 결제, 포인트, 정산 금액이 관련된 건은 자동 폐기할 수 없다.
4. 운영자 수동 보정은 사유, 증적, 승인자, 변경 전후 상태를 기록해야 한다.
5. 개인정보가 포함된 요청/응답 원문은 마스킹 저장을 기본으로 하며 원문 보관 여부는 PM 승인 필요이다.

인당 생산성/마진 기여: 재처리 원칙을 통일해 중복 지급/중복 취소 같은 금전 손실과 감사 대응 비용을 줄인다.
