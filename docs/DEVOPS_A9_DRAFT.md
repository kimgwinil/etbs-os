# 이제너두 전사 CRM OS DevOps A9 초안

## 1. 문서 목적

이 문서는 이제너두 전사 CRM OS MVP의 CI/CD, 환경 분리, 시크릿 관리, 로그/메트릭/알림, 운영 KPI 관측성 기준을 정의하는 A9 DevOps 초안이다.

본 문서는 확정안이 아니며 특정 클라우드, 상용 관측성 도구, 배포 플랫폼, 보안 솔루션, 외부 계약은 PM 김권일 승인 후 확정한다.

인당 생산성/마진 기여: 개발, 검증, 배포, 장애 대응을 표준화해 반복 작업과 장애 복구 시간을 줄이고 동일 인력의 릴리즈 처리량을 높인다.

## 2. 기준 입력

| 입력 | 내용 | 상태 |
|---|---|---|
| PRD | `/docs/PRD.md` | 확인 완료 |
| MVP P0 모듈 | CRM Core, Operations Console, Security & Audit Baseline, Profitability Dashboard | 기준 입력 |
| 규제 요구 | ISMS, 개인정보, 외감 대응을 위한 로그와 배포 이력 추적 | 기준 입력 |
| 미확정 항목 | 클라우드, 상용도구, 개인정보 처리범위, 외부계약, 최종 아키텍처 | PM 승인 필요 |

인당 생산성/마진 기여: DevOps 기준을 P0 범위에 맞춰 제한해 초기 구축 비용을 통제하고 고위험 운영 병목부터 줄인다.

## 3. A9 담당 범위

### 포함

- MVP CI/CD 파이프라인 기준
- 한 명령 빌드/테스트/배포 기준
- 개발, 검증, 운영 환경 분리 기준
- 시크릿 수명주기와 접근 통제 기준
- 로그, 메트릭, 트레이스, 알림 기준
- 배포 이력, 변경 이력, 감사 증적 기준
- 운영 KPI와 시스템 관측성 연결 기준

### 제외

- 특정 클라우드 또는 SaaS 도구 확정
- 개인정보 항목, 보관기간, 위탁 범위 확정
- 최종 네트워크, 데이터베이스, 런타임 아키텍처 확정
- 예산 또는 외부계약 확정
- 제품 기능 구현 코드 작성

인당 생산성/마진 기여: A9 범위를 운영 자동화와 증적 기준으로 한정해 개발 에이전트가 같은 기준으로 빠르게 통합되도록 한다.

## 4. MVP DevOps 원칙

| 원칙 | 기준 | 인당 생산성/마진 기여 |
|---|---|---|
| One Command Delivery | 로컬과 CI에서 동일한 명령으로 빌드, 테스트, 배포가 가능해야 한다. | 환경 차이로 인한 디버깅과 배포 대기 시간을 줄인다. |
| Environment Parity | dev, staging, prod는 설정값만 다르고 실행 방식은 동일해야 한다. | 운영 전환 재작업과 장애 가능성을 줄인다. |
| Secret Zero Trust | 시크릿은 코드, 문서, 이미지, 로그에 저장하지 않는다. | 유출 사고와 감사 대응 비용을 줄인다. |
| Audit by Default | 배포, 권한, 개인정보 접근, 주요 데이터 변경은 추적 가능해야 한다. | 외감/ISMS 대응 시간을 줄이고 사후 복구 비용을 낮춘다. |
| Observable Operations | 업무 KPI와 시스템 지표를 같은 시간축으로 조회해야 한다. | 장애가 매출/마진/처리량에 미치는 영향을 빠르게 판단한다. |
| Fail Fast, Roll Back Fast | 배포 전 자동 검증과 배포 후 빠른 롤백 경로를 갖춘다. | 장애 확산 시간을 줄여 운영 인력 투입과 손실을 줄인다. |

## 5. 환경 분리 기준

| 환경 | 목적 | 데이터 기준 | 접근 기준 | 배포 기준 |
|---|---|---|---|---|
| local | 개발자 단위 개발과 빠른 검증 | 실데이터 금지, 샘플/마스킹 데이터만 허용 | 개발자 개인 | 수동 실행 |
| dev | 통합 개발 검증 | 비식별 테스트 데이터 | 개발/QA | main 병합 전후 자동 배포 가능 |
| staging | 운영 전 최종 검증, UAT, 회귀 테스트 | 운영 유사 데이터는 비식별/마스킹 후 사용 | 제한된 개발/운영/보안 담당 | 승인 기반 배포 |
| prod | 실제 운영 | 승인된 개인정보 처리범위 내 데이터 | 최소권한, Break Glass 별도 | 승인 기반 배포와 롤백 필수 |

결정: MVP는 최소 `local`, `dev`, `staging`, `prod` 4단계 환경을 기준으로 문서화한다.

인당 생산성/마진 기여: 환경별 용도를 분리해 운영 장애와 데이터 사고 가능성을 낮추고 재작업 시간을 줄인다.

PM 승인 필요: 운영 유사 데이터의 마스킹 방식, 개인정보 처리범위, 프로덕션 접근자 범위.

## 6. 한 명령 빌드/테스트/배포 기준

MVP 저장소는 다음 명령 인터페이스를 제공해야 한다. 실제 구현 도구는 아키텍처 확정 후 선택한다.

| 명령 | 목적 | 필수 동작 | 실패 조건 |
|---|---|---|---|
| `make setup` | 로컬 개발 환경 준비 | 의존성 설치, 샘플 설정 파일 생성, 헬스체크 | 필수 도구 누락, 설정 파일 오류 |
| `make lint` | 정적 검증 | 포맷, 린트, 타입 체크 | 경고 기준 초과 또는 오류 |
| `make test` | 자동 테스트 | 단위 테스트, 계약 테스트, 핵심 권한 테스트 | 테스트 실패, 커버리지 기준 미달 |
| `make build` | 배포 산출물 생성 | 프론트엔드/백엔드 빌드, 이미지 또는 아티팩트 생성 | 빌드 실패, 취약점 기준 초과 |
| `make migrate` | 스키마 변경 검증/적용 | 마이그레이션 검증, 롤백 스크립트 확인 | 역방향 호환성 실패 |
| `make deploy ENV=dev` | 개발 환경 배포 | dev 배포, smoke test | 헬스체크 실패 |
| `make deploy ENV=staging` | 검증 환경 배포 | 승인된 아티팩트 배포, 회귀 smoke test | 승인 누락, smoke test 실패 |
| `make deploy ENV=prod` | 운영 배포 | 승인, 배포, 헬스체크, 변경 로그 기록 | 승인 누락, SLO 위험 |
| `make rollback ENV=prod VERSION=<version>` | 운영 롤백 | 직전 안정 버전 복구, 롤백 로그 기록 | 복구 검증 실패 |

결정: MVP는 도구가 달라도 위 명령 계약을 유지한다.

인당 생산성/마진 기여: 담당자가 도구별 절차를 외우지 않아도 동일 명령으로 검증과 배포를 수행해 대기와 실수를 줄인다.

PM 승인 필요: 최종 빌드 도구, 컨테이너 레지스트리, 배포 런타임, 배포 승인 체계.

## 7. CI/CD 파이프라인 기준

### Pull Request 검증

| 단계 | 필수 검증 |
|---|---|
| checkout | 의존성 캐시와 잠금 파일 무결성 확인 |
| lint | 포맷, 린트, 타입 체크 |
| test | 단위 테스트, 권한 테스트, API 계약 테스트 |
| build | 배포 산출물 생성 |
| security scan | dependency, secret, container/image 취약점 검사 |
| migration check | 스키마 변경의 적용/롤백 가능성 확인 |
| audit preview | 변경 대상 모듈과 감사로그 영향 표시 |

### main 병합 후

| 단계 | 필수 동작 |
|---|---|
| artifact publish | 버전 태그, 커밋 SHA, 빌드 시간, 빌드 주체 기록 |
| deploy dev | 자동 배포 및 smoke test |
| deploy staging | 승인 후 배포, 회귀 smoke test |
| release note | 변경 이력, 마이그레이션, 롤백 지침 생성 |

### prod 배포

| 단계 | 필수 동작 |
|---|---|
| approval gate | PM 또는 위임된 릴리즈 책임자 승인 |
| change window | 업무 피크 시간 회피 기준 확인 |
| canary/blue-green | 점진 배포 또는 즉시 롤백 가능한 방식 사용 |
| smoke test | 인증, 권한, 핵심 조회, 운영 큐, KPI 대시보드 검증 |
| monitoring window | 배포 후 최소 30~60분 핵심 지표 감시 |
| rollback decision | 오류율, 지연, 업무 실패율 기준 초과 시 롤백 |

결정: MVP부터 배포 이력은 커밋 SHA, 아티팩트 버전, 승인자, 배포자, 배포 시간, 롤백 가능 버전을 기록한다.

인당 생산성/마진 기여: 배포 추적성을 확보해 장애 원인 파악과 외감 증적 준비 시간을 줄인다.

PM 승인 필요: 배포 승인자, 업무 피크 시간, 운영 릴리즈 캘린더, 최종 CI/CD 플랫폼.

## 8. 시크릿 관리 기준

| 영역 | 기준 |
|---|---|
| 저장 | 시크릿은 코드 저장소, `.env` 커밋, 문서, 이슈, 로그에 저장 금지 |
| 주입 | 런타임 또는 CI/CD의 Secret Store에서 환경변수 또는 파일 마운트로 주입 |
| 권한 | 환경별, 역할별 최소권한 부여 |
| 회전 | 외부 API 키, DB 비밀번호, 토큰은 정기 회전 및 사고 시 즉시 회전 |
| 감사 | 조회, 변경, 회전, 삭제 이력을 보존 |
| 스캔 | PR과 main 브랜치에서 secret scan 필수 |
| 노출 대응 | 노출 확인 즉시 폐기, 재발급, 영향 범위 기록, PM/보안 담당 보고 |

시크릿 분류:

| 등급 | 예시 | 처리 기준 |
|---|---|---|
| S1 | 로컬 샘플 키, 더미 토큰 | 실제 시스템 접근 불가 |
| S2 | dev/staging API 키 | 환경 한정, 자동 회전 권장 |
| S3 | prod DB, 결제, 베네카페, 온누리, 인증 키 | 최소권한, 접근 승인, 감사로그 필수 |
| S4 | 개인정보 복호화 키, 마스터 키 | 별도 보안 설계 및 PM 승인 필요 |

결정: MVP는 `Secret Store` 추상 인터페이스를 기준으로 작성하고 특정 제품명은 확정하지 않는다.

인당 생산성/마진 기여: 시크릿 유출로 인한 서비스 중단, 고객 신뢰 손실, 감사 대응 비용을 예방한다.

PM 승인 필요: Secret Store 제품, 키 관리 방식, 회전 주기, S4 키 운영 책임자.

## 9. 로그 기준

### 공통 로그 필드

| 필드 | 설명 |
|---|---|
| `timestamp` | ISO 8601 UTC 기준 |
| `environment` | local, dev, staging, prod |
| `service` | 서비스 이름 |
| `version` | 배포 버전 또는 커밋 SHA |
| `trace_id` | 요청 추적 ID |
| `request_id` | 외부 요청 ID |
| `actor_id` | 사용자 또는 시스템 행위자 ID |
| `tenant_id` | 고객사/테넌트 ID |
| `entity_type` | customer, supplier, employee, contract, operation_task 등 |
| `entity_id` | 대상 엔티티 ID |
| `action` | 조회, 생성, 변경, 삭제, 승인, 반려, 배포 등 |
| `result` | success, failure, denied, timeout |
| `duration_ms` | 처리 시간 |
| `error_code` | 표준 오류 코드 |
| `pii_accessed` | 개인정보 접근 여부 |

### 감사로그 필수 이벤트

| 이벤트 | 필수 기록 |
|---|---|
| 로그인/로그아웃 | actor, IP, user agent, 성공/실패 |
| 권한 변경 | 변경자, 대상자, 이전 권한, 이후 권한, 사유 |
| 개인정보 조회 | actor, tenant, entity, 목적, 결과 |
| 운영 업무 상태 변경 | 이전 상태, 이후 상태, 담당자, 사유 |
| 정산/포인트 관련 변경 | 금액, 이전 값, 이후 값, 승인자, 근거 |
| 데이터 반입/반출 | 파일명, 범위, 건수, 요청자, 승인자 |
| 배포/롤백 | 버전, 승인자, 실행자, 결과 |

결정: 애플리케이션 로그와 감사로그는 목적을 분리하되 `trace_id`, `actor_id`, `tenant_id`, `entity_id`로 연결 가능해야 한다.

인당 생산성/마진 기여: 운영 문의, 장애, 감사 요청에서 원인 추적 시간을 줄여 고숙련 인력의 반복 조사를 줄인다.

PM 승인 필요: 로그 보존기간, 개인정보 로그 마스킹 정책, 외감 증적 보존 기준.

## 10. 메트릭 기준

### 시스템 메트릭

| 메트릭 | 기준 |
|---|---|
| `request_rate` | 서비스별 요청량 |
| `error_rate` | 4xx/5xx 및 업무 오류율 |
| `latency_p50/p95/p99` | API와 주요 쿼리 지연 |
| `availability` | 서비스 가용성 |
| `job_success_rate` | 배치/연동 작업 성공률 |
| `queue_depth` | 운영 큐, 연동 큐, 재처리 큐 적체량 |
| `retry_count` | 외부 연동 재시도 횟수 |
| `deployment_frequency` | 배포 빈도 |
| `change_failure_rate` | 배포 후 장애 또는 롤백 비율 |
| `mean_time_to_recovery` | 장애 복구 시간 |

### 보안/감사 메트릭

| 메트릭 | 기준 |
|---|---|
| `permission_denied_rate` | 권한 거부 비율 |
| `pii_access_count` | 개인정보 조회 건수 |
| `privileged_access_count` | 관리자 권한 사용 건수 |
| `secret_rotation_age` | 시크릿 마지막 회전 후 경과일 |
| `audit_log_delivery_lag` | 감사로그 저장 지연 |

결정: MVP부터 DORA 지표와 운영 큐 지표를 함께 수집한다.

인당 생산성/마진 기여: 개발 생산성과 운영 처리량을 동시에 보아 릴리즈 속도가 실제 업무 효율로 이어지는지 판단한다.

PM 승인 필요: SLO 목표값, 보안 임계값, 최종 메트릭 저장소.

## 11. 알림 기준

| 등급 | 조건 | 채널 | 대응 |
|---|---|---|---|
| P1 Critical | 인증 불가, 전체 장애, 개인정보 로그 저장 실패, 정산/포인트 대량 오류 | 즉시 알림, 전화/메신저 병행 가능 | 온콜 즉시 대응, PM 보고 |
| P2 High | 핵심 API 오류율/지연 임계값 초과, 운영 큐 급증, 외부 연동 실패 지속 | 업무시간 즉시 알림 | 담당 에이전트 확인, 임시 우회 |
| P3 Medium | 배치 지연, 일부 고객사 오류, 배포 후 경고 증가 | 채널 알림 | 다음 업무 주기 내 처리 |
| P4 Low | 용량 증가, 회전 예정, 비용 이상 징후 | 대시보드/일일 리포트 | 계획 반영 |

필수 알림 라우팅:

- CRM Core 장애: A1, A2, A9
- Operations Console 장애: A2, A3, A8, A9
- Security & Audit 장애: A7, A9, PM 보고 필요
- Profitability Dashboard 장애: A3, A4, A9
- Integration 장애: A6, A9

결정: 알림은 시스템 임계값만이 아니라 업무 영향도 기준으로 등급화한다.

인당 생산성/마진 기여: 모든 경고를 같은 수준으로 처리하지 않아 고비용 장애에 먼저 대응하고 알림 피로를 줄인다.

PM 승인 필요: 온콜 운영 방식, 알림 채널, 야간 대응 기준, 고객 공지 기준.

## 12. 운영 KPI와 관측성 연결

| 운영 KPI | 연결 시스템 지표 | 연결 로그/이벤트 | 활용 |
|---|---|---|---|
| 담당자 1인당 처리 건수 | `operation_task_completed_count`, `queue_depth` | 업무 상태 변경 로그 | 인력 배치와 자동화 후보 선정 |
| 평균 처리시간 | `operation_task_duration_p50/p95` | 접수, 배정, 완료 이벤트 | 병목 업무 유형 식별 |
| SLA 준수율 | `sla_breach_count`, `task_age` | SLA 초과 이벤트 | 고객사별 운영 리스크 관리 |
| 정산/포인트 오류율 | `settlement_error_rate`, `point_job_failure_rate` | 정산/포인트 변경 감사로그 | 재무 리스크와 문의 비용 감소 |
| 외부 연동 실패율 | `integration_failure_rate`, `retry_count` | 외부 API 요청/응답 로그 | 재처리 자동화와 공급사/연동사 협의 근거 |
| 고객사/공급사 마진 | `profitability_refresh_lag`, `data_pipeline_success_rate` | 원가/매출 데이터 적재 이벤트 | 저마진 계정 조정 판단 |
| 개인정보 접근 이상 | `pii_access_count`, `privileged_access_count` | 개인정보 조회 감사로그 | ISMS 대응과 내부통제 |
| 배포 안정성 | `change_failure_rate`, `mttr`, `deployment_frequency` | 배포/롤백 이벤트 | 릴리즈 병목 및 품질 개선 |

결정: KPI 대시보드는 업무 이벤트, 감사로그, 시스템 메트릭을 같은 `tenant_id`, `entity_id`, `trace_id`, `time_window` 기준으로 연결한다.

인당 생산성/마진 기여: 장애나 지연이 처리량, SLA, 마진에 미치는 영향을 빠르게 계산해 감이 아니라 데이터로 인력과 우선순위를 조정한다.

PM 승인 필요: 경영 KPI 공식 정의, 마진 계산 원천 데이터, 데이터 접근 권한.

## 13. MVP 인수조건

| 항목 | 인수조건 |
|---|---|
| 목적 | P0 모듈을 안전하게 개발, 검증, 배포, 관측할 수 있는 기준이 문서화되어 있다. |
| 입력 | PRD P0 모듈, 규제 요구, 외부 연동 가정, 미확정 승인 항목이 반영되어 있다. |
| 출력 | CI/CD, 환경, 시크릿, 로그, 메트릭, 알림, KPI 연결 기준이 산출되어 있다. |
| 한 명령 기준 | `make setup`, `make lint`, `make test`, `make build`, `make deploy`, `make rollback` 계약이 존재한다. |
| 환경 분리 | local/dev/staging/prod 목적, 데이터, 접근, 배포 기준이 정의되어 있다. |
| 시크릿 | 저장 금지, 주입, 접근, 회전, 감사, 노출 대응 기준이 정의되어 있다. |
| 관측성 | 로그 필드, 감사 이벤트, 시스템/보안 메트릭, 알림 등급이 정의되어 있다. |
| KPI 연결 | 운영 KPI와 시스템 지표의 매핑이 정의되어 있다. |
| 승인 표시 | 특정 클라우드/상용도구/개인정보/외부계약 확정 항목은 PM 승인 필요로 표시되어 있다. |

인당 생산성/마진 기여: 인수조건을 명확히 해 에이전트 간 재해석 비용과 통합 지연을 줄인다.
