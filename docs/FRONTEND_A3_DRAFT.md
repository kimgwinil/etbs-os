# A3 프론트 초안: Operations Console / Profitability Dashboard

## 1. 문서 목적

이 문서는 이제너두 전사 CRM OS의 P0 모듈 중 A3가 담당하는 Operations Console과 Profitability Dashboard의 초기 화면, 사용자 흐름, 권한 차이, 인수조건을 정의한다. `/docs/PROCESS_REQUIREMENTS.md`의 유통회사형 프로세스 UX 요구사항을 함께 반영한다.

본 문서는 개발 확정안이 아니라 프론트 UX/UI 초안이며, Windows/iOS 지원 방식, 개인정보 처리범위, 외부계약, 아키텍처 확정은 PM 김권일 승인 후 확정한다.

인당 생산성/마진 기여: 운영자가 한 화면에서 조회, 필터, 일괄처리, 예외 대응을 수행하고 경영진이 저마진 원인을 빠르게 식별하게 해 동일 인력의 처리량과 의사결정 속도를 높인다.

## 2. PRD 기준 P0 범위

| P0 모듈 | A3 화면 책임 | 연결 모듈 | KPI 영향 |
|---|---|---|---|
| Operations Console | 업무 큐, 검색, 필터, 배정, 상태 변경, SLA, 예외 큐, 일괄 처리 | CRM Core, Security & Audit Baseline, Settlement & Point Ops | 담당자 1인당 처리 건수 증가, 평균 처리시간 감소 |
| Profitability Dashboard | 고객사/공급사/업무유형별 매출, 원가, 마진, 운영 투입량 시각화 | CRM Core, 데이터/지표 정의, 정산/포인트 | 저마진 고객/업무 식별, 인력 배치 최적화 |

결정: A3 초안은 P0의 운영 처리 화면과 경영 지표 화면에 집중하고, Supplier Portal과 Customer Success Workspace는 P2/P2 후속으로 분리한다.

인당 생산성/마진 기여: 초기 화면 범위를 반복 처리량과 수익성 가시화에 제한해 낮은 ROI 화면 개발을 줄인다.

## 3. 공통 UX 원칙

1. 목록 우선: 운영자는 상세 화면 진입 전 목록에서 상태, SLA, 예외 사유, 담당자, 고객사, 금액 영향도를 확인한다.
2. 필터 저장: 자주 쓰는 조건은 개인/팀 저장 필터로 제공한다.
3. 일괄 처리 기본: 동일 조건의 업무는 선택 후 배정, 보류, 완료, 재시도, 반려 요청을 일괄 수행한다.
4. 개인정보 최소 노출: 목록에는 마스킹된 식별자와 업무상 필요한 최소 필드만 노출한다.
5. 감사 가능성: 상태 변경, 담당자 변경, 개인정보 열람, 일괄 작업은 모두 사유 입력과 로그 보존을 전제로 한다.
6. 경영 지표 드릴다운: 대시보드 수치에서 Operations Console의 원인 업무 목록으로 이동할 수 있어야 한다.
7. 고정 헤더: 모든 목록 화면은 스크롤/드래그 중에도 컬럼 의미를 잃지 않도록 필드 헤더를 상단 고정한다.
8. 사용자 정보 표시: 전역 헤더의 설정 메뉴 옆에 소속, 이름, 권한을 항상 표시한다.
9. 설정 진입점 단일화: 시스템 설정은 상단 메인 메뉴의 `설정` 하나만 유지하고, 각 업무 화면 우측 상단의 개별 설정 버튼은 제거한다.

결정: 기본 화면은 반응형 웹/PWA를 가정하되 Windows 데스크톱과 iOS 태블릿/모바일 최적화는 PM 승인 필요로 둔다.

인당 생산성/마진 기여: 네이티브 앱보다 웹 우선으로 초기 운영 접근성을 확보하면 배포/교육 비용을 낮추고 현장 처리 속도를 빠르게 검증할 수 있다.

결정: 목록형 화면의 컬럼 헤더는 sticky header를 기본 UX 패턴으로 고정한다.

인당 생산성/마진 기여: 긴 목록 처리 중 필드 맥락 상실을 줄여 오입력과 재확인 시간을 낮춘다.

결정: 설정 메뉴 옆 사용자 정보는 `소속 / 이름 / 권한` 순서로 표시하고, 권한 변경은 즉시 화면 메뉴와 액션 가시성에 반영되도록 설계한다.

인당 생산성/마진 기여: 사용자가 자신의 처리 범위와 권한을 즉시 확인해 잘못된 메뉴 진입과 권한 문의 시간을 줄인다.

결정: 화면별 필터, 정렬, 컬럼 선택 같은 보기 옵션은 필요 시 `보기 설정` 또는 `필터 저장`으로 제공하되 시스템 설정처럼 보이는 명칭이나 아이콘을 사용하지 않는다.

인당 생산성/마진 기여: 전역 설정과 화면 보기 옵션을 분리해 사용자가 설정 위치를 헷갈리는 시간을 줄이고 화면 밀도를 낮춘다.

## 4. 권한별 화면 차이

| 역할 | Operations Console | Profitability Dashboard | 개인정보 노출 | 주요 제한 |
|---|---|---|---|---|
| 경영진/PM | 전체 큐 요약, 병목/예외 조회 | 전체 수익성, 고객사/공급사/업무유형 지표 | 원칙적으로 비식별/집계 중심 | 개별 개인정보 상세 열람 제한 |
| 운영 담당자 | 본인/팀 큐 처리, 일괄 상태 변경, 예외 처리 | 본인/팀 처리량 및 SLA 요약 | 업무 처리에 필요한 최소 마스킹 정보 | 고위험 상태 변경은 승인 필요 |
| 운영 리더 | 팀 배정, SLA 재조정 요청, 예외 우선순위 변경 | 팀 생산성, 병목 고객/업무 조회 | 필요 시 제한적 상세 열람 | 개인정보 열람 사유 필수 |
| 재무/정산 담당자 | 정산/포인트 관련 큐 조회 및 증적 확인 | 매출, 원가, 마진, 정산 차이 지표 | 정산 근거 중심 최소 노출 | 임직원 민감정보 열람 제한 |
| 보안/개인정보 담당자 | 개인정보 접근 로그, 권한 위반 의심 건 조회 | 접근 리스크/감사 지표 | 감사 목적의 제한 열람 | 업무 상태 직접 변경 제한 |
| AM/영업 | 담당 고객사 이슈 큐 조회, 고객 상태 확인 | 담당 고객사 수익성/운영 투입량 | 고객사 단위 비식별 중심 | 전체 고객/공급사 지표 제한 |

결정: 역할별 화면은 같은 UI 셸을 공유하되 데이터 범위, 액션 버튼, 개인정보 노출 수준을 권한으로 제어한다.

인당 생산성/마진 기여: 별도 화면을 과다하게 만들지 않으면서도 권한 리스크와 교육 비용을 줄인다.

| R34 | 메뉴별 중복 설정 버튼 제거 | `/specs/frontend/role-menu-user-context.md` | 설정 진입점은 상단 메인 `설정` 하나만 유지하고 각 업무 화면 우측 상단 시스템 설정 버튼은 제거 대상으로 명시 | 업무 화면 우측 상단에 시스템 설정 버튼이 보이면 QA 반려 |

결정: PM 피드백 대응을 위해 A3 `보강 필요` 항목은 요구 ID, 기준 스펙, 반영 내용, 인수조건 단위로 추적 가능하게 문서화한다.

인당 생산성/마진 기여: 누락 여부를 요구 ID로 바로 검증하게 해 PM 리뷰와 재작업 시간을 줄인다.

## 4.1.2 설정 진입점 단일화

| 항목 | 유지/제거 | UX 기준 |
|---|---|---|
| 상단 메인 `설정` 메뉴 | 유지 | 로그기록, 권한 관리, 사용자 정보, 슈퍼바이저 설정 등 시스템 설정 진입점 |
| 업무 화면 우측 상단 개별 설정 버튼 | 제거 | Operations, 고객, 상품, 주문, 배송, 결재, 대시보드 등 각 화면에서 시스템 설정처럼 보이는 버튼을 두지 않음 |

결정: 설정 진입점은 상단 메인 메뉴의 `설정` 하나로 단일화하고 각 업무 화면 우측 상단의 시스템 설정 버튼은 제거 대상으로 명시한다.

인당 생산성/마진 기여: 중복 설정 버튼을 제거해 사용자가 어디에서 설정해야 하는지 고민하는 시간을 줄이고 업무 화면의 시각적 소음을 낮춘다.

## 4.2 권한별 메뉴 차등

| 권한 | 표시 메뉴 | 숨김/제한 메뉴 | 프론트 처리 |
|---|---|---|---|
| 일반 | 내 영업활동, 내 파이프라인, 견적, 주문, 내 결재함 | 전사 영업이익, 전사 로그, 권한 관리 | 내 업무 중심 기본 홈 |
| 관리자 | 고객, 상품, 주문, 출고, 배송/입출고, 세금계산서, 거래명세표, 팀 업무 | 영업이익 산식 변경, 권한 변경 | 팀 운영 큐와 발행/출고 상태 중심 |
| 슈퍼바이저 | 전사 대시보드, 영업이익, 로그, 설정, 권한 관리, 예외 분석 | 승인되지 않은 개인정보 상세 | 슈퍼바이저 대시보드 기본 진입 |
| 경영자/PM | 경영 대시보드, Profitability Dashboard, 병목/예외, 승인 현황 | 개별 개인정보 상세 기본 제한 | 집계 지표와 드릴다운 중심 |

결정: 권한별 메뉴는 숨김 처리와 비활성 처리 기준을 분리한다. 접근 권한이 없는 메뉴는 숨기고, 권한은 있으나 승인/조건이 필요한 액션은 비활성+사유 표시로 처리한다.

인당 생산성/마진 기여: 불필요한 메뉴 노출을 줄여 탐색 시간을 줄이고, 조건부 액션의 사유를 보여줘 권한 문의와 처리 지연을 낮춘다.

## 4.3 고객/상품 저장 흐름

### 고객 신규 등록

1. 사용자가 `고객 등록` 메뉴에 진입한다.
2. 필수 정보를 입력하고 저장한다.
3. 시스템은 신규 고객 레코드를 생성하고 `신규 고객으로 저장되었습니다` 상태를 표시한다.
4. 생성된 고객 상세 화면으로 이동하며 타임로그에 생성 이력이 남는다.
5. 중복 가능성이 있는 고객이 발견되면 저장 전 경고를 표시하되, MVP에서 차단 여부는 PM 승인 필요로 둔다.

인당 생산성/마진 기여: 신규 저장과 수정 저장의 의미를 분리해 중복 고객 생성과 후속 정정 비용을 줄인다.

### 고객 수정 저장

1. 사용자가 고객 상세에서 수정 모드로 전환한다.
2. 변경 필드를 저장한다.
3. 시스템은 기존 고객 레코드를 갱신하고 `변경 완료` 상태를 표시한다.
4. 변경 전후 주요 필드와 수정자가 타임로그에 남는다.
5. 권한 없는 사용자는 수정 저장 버튼을 볼 수 없거나 비활성 상태와 차단 사유를 본다.

인당 생산성/마진 기여: 고객 정보 변경 이력을 명확히 남겨 영업/정산/배송 단계의 오류 추적 시간을 줄인다.

### 판매상품 판매가격 강조

- 상품 목록: `salesPrice` 컬럼을 기본 표시하고 가로 스크롤 시 상품명과 함께 고정한다.
- 상품 상세: 판매가격을 상단 요약 영역에 강조 표시한다.
- 견적/주문: 정가, 할인, 최종 판매가격을 같은 행에서 비교한다.
- 가격 수정: 권한 확인, 변경 사유, 변경 로그를 요구한다.
- 가격 변경: 적용일과 변경 이력을 표시하며, 기존 견적/주문 자동 변경 여부는 PM 승인 필요로 둔다.

결정: 판매가격은 상품/견적/주문 화면에서 일반 텍스트가 아니라 핵심 금액 필드로 시각 강조한다.

인당 생산성/마진 기여: 가격 확인 누락과 할인 오입력을 줄여 마진 훼손을 예방한다.

## 4.4 임직원-거래처 담당 배정

`/specs/employee/customer-assignment.md`를 기준으로 임직원 관리와 거래처 화면에 다대다 담당 배정을 반영한다.

결정: 거래처 화면에는 대표 담당자와 주담당/부담당/승인담당/참조담당 역할을 함께 표시한다.

인당 생산성/마진 기여: 거래처별 책임자와 후속 승인 담당을 즉시 찾아 업무 배정과 문의 응대 시간을 줄인다.

## 5. Operations Console 초안

### 5.1 목적

운영 업무를 접수, 배정, 처리, 보류, 완료, 반려, 실패/재시도 상태로 표준화하고, 담당자가 검색/필터/일괄 처리로 업무 처리량을 높일 수 있게 한다.

인당 생산성/마진 기여: 상태와 액션을 표준화하면 수기 확인, 메신저 확인, 엑셀 재정렬 시간을 줄여 담당자 1인당 처리 건수를 늘린다.

### 5.2 주요 입력

- CRM Core: 고객사, 공급사, 임직원, 계약, 담당자, 활동 이력 ID
- 업무 접수 이벤트: CS, 포인트, 정산, 신청/심사, 연동 실패, 수동 보정 요청
- SLA 정책: 업무유형별 목표 처리시간, 우선순위, 에스컬레이션 기준
- 권한/RBAC: 사용자 역할, 소속 팀, 접근 가능 고객사/공급사 범위
- 감사 기준: 상태 변경 사유, 개인정보 열람 사유, 일괄 처리 로그

### 5.3 주요 출력

- 업무 큐 목록 및 저장 필터
- 업무 상세 패널과 처리 이력
- 일괄 처리 결과와 실패 사유
- SLA 위험/초과 목록
- 예외 큐와 재처리/수동 보정 요청
- 개인정보 접근 및 상태 변경 감사로그

### 5.4 핵심 화면 구성

| 영역 | 구성 | 설명 |
|---|---|---|
| 상단 검색 | 통합 검색, 저장 필터, 날짜 범위, 고객사/공급사 선택 | 고객사명, 공급사명, 계약 ID, 업무 ID, 마스킹 식별자로 검색 |
| KPI 스트립 | 신규, 진행중, SLA 위험, SLA 초과, 예외, 오늘 완료 | 팀 또는 개인 기준 운영량을 즉시 확인 |
| 필터 패널 | 업무유형, 상태, 우선순위, 담당자, SLA, 예외 사유, 금액 영향도 | 고반복 업무를 빠르게 분리 |
| 업무 테이블 | 체크박스, 상태, SLA 배지, 고객사, 업무유형, 담당자, 금액 영향도, 최근 이벤트 | 일괄 처리와 스캔 속도 중심 |
| 상세 드로어 | 입력값, 관련 엔티티, 처리 액션, 이력, 첨부/증적 | 페이지 이동 없이 검토와 처리 수행 |
| 일괄 액션 바 | 배정, 상태 변경, 보류, 재시도, 승인 요청, CSV 내보내기 요청 | 선택 건에 대한 대량 처리 |

결정: Operations Console은 테이블+상세 드로어 구조를 기본으로 하며, 처리 액션은 목록 선택 후 상단 일괄 액션 또는 상세 드로어에서 수행한다.

인당 생산성/마진 기여: 페이지 왕복을 줄이고 다건 처리 흐름을 기본값으로 만들어 동일 시간 내 처리량을 높인다.

### 5.5 상태 모델 초안

| 상태 | 의미 | 허용 액션 | 감사/승인 |
|---|---|---|---|
| `new` | 접수 후 미배정 | 배정, 보류, 반려 요청 | 배정자 로그 |
| `assigned` | 담당자 지정 | 처리 시작, 재배정, 보류 | 담당자 변경 로그 |
| `in_progress` | 처리 중 | 완료, 보류, 승인 요청, 예외 전환 | 변경 사유 |
| `pending_approval` | 고위험/금액/권한 사유로 승인 대기 | 승인, 반려, 보완 요청 | 승인자 로그 필수 |
| `blocked` | 외부 자료/연동/고객 확인 대기 | 보류 해제, 재배정, 반려 요청 | 보류 사유 |
| `exception` | 자동 처리 실패 또는 정책 외 케이스 | 재시도, 수동 보정, 에스컬레이션 | 예외 사유 |
| `completed` | 처리 완료 | 재오픈 요청 | 완료 근거 |
| `rejected` | 처리 불가/반려 | 재오픈 요청 | 반려 사유 |

결정: 상태명은 영문 식별자를 사용하고 화면 표기는 한국어로 제공한다.

인당 생산성/마진 기여: 상태 식별자는 연동/로그/분석과 일관성을 유지하고, 화면 표기는 현장 교육 비용을 낮춘다.

### 5.6 인수조건

- 운영자는 고객사, 공급사, 업무유형, 상태, SLA, 담당자, 예외 사유로 업무를 필터링할 수 있다.
- 운영자는 권한 내 업무를 1건 이상 선택해 일괄 배정, 보류, 재시도, 상태 변경 요청을 수행할 수 있다.
- 고위험 상태 변경, 개인정보 상세 열람, 금액 영향이 큰 일괄 처리는 사유 입력과 승인 흐름을 요구한다.
- SLA 위험/초과 건은 목록, KPI 스트립, 저장 필터에서 동일 기준으로 표시된다.
- 예외 큐의 각 건은 실패 원인, 마지막 재시도 시각, 권장 다음 액션을 보여준다.
- 모든 상태 변경과 개인정보 열람은 감사로그로 남는다.

인당 생산성/마진 기여: DoD를 운영 처리량과 리스크 통제 기준으로 고정해 보기 좋은 화면보다 실제 업무 처리 성능을 우선 검증한다.

## 6. Profitability Dashboard 초안

### 6.1 목적

고객사/공급사/업무유형별 매출, 원가, 마진, 운영 투입량, SLA, 예외율을 한 화면에서 비교해 저마진 원인과 인력 투입 병목을 찾는다.

인당 생산성/마진 기여: 매출이 큰 고객이라도 운영 투입이 과도하면 마진을 훼손한다는 신호를 빠르게 보여줘 인력 배치와 운영 정책을 조정하게 한다.

### 6.2 주요 입력

- CRM Core: 고객사, 공급사, 계약, 담당 조직
- 매출/원가 데이터: 계약 매출, 수수료, 정산 원가, 포인트/결제 관련 비용
- Operations Console: 업무유형별 처리 건수, 처리시간, SLA 초과, 예외 건수, 담당자 투입량
- 권한/RBAC: 집계 범위와 고객사/공급사 열람 범위
- 데이터 품질 플래그: 미수집, 추정값, 정산 대기, 연동 지연

### 6.3 주요 출력

- 전체 매출, 원가, 공헌이익, 마진율
- 고객사/공급사별 수익성 랭킹
- 업무유형별 처리량, 평균 처리시간, 예외율, SLA 초과율
- 고투입/저마진 후보 목록
- Operations Console로 이동하는 원인 업무 드릴다운 링크
- 데이터 신뢰도 및 미확정 지표 표시

### 6.4 핵심 화면 구성

| 영역 | 구성 | 설명 |
|---|---|---|
| 상단 필터 | 기간, 고객사, 공급사, 업무유형, 담당팀, 계약 상태 | 경영진/리더/AM 권한별 기본 범위 적용 |
| 요약 KPI | 매출, 원가, 공헌이익, 마진율, 처리건수, 평균 처리시간 | 수익성과 운영 투입을 같은 행에 표시 |
| 경고 패널 | 저마진 고객, SLA 초과 급증, 예외율 상승, 데이터 품질 낮음 | 경영 의사결정이 필요한 항목 우선 노출 |
| 랭킹 테이블 | 고객사/공급사별 매출, 원가, 마진, 처리량, 예외율 | 정렬/필터/드릴다운 제공 |
| 업무유형 분석 | 업무유형별 처리량, 시간, 단가성 비용, 예외율 | 고비용 업무 후보 식별 |
| 원인 드릴다운 | 선택 지표의 업무 큐로 이동 | 대시보드 수치와 운영 액션 연결 |

결정: Profitability Dashboard는 재무 지표만 보여주지 않고 운영 투입 지표를 같은 맥락에 배치한다.

인당 생산성/마진 기여: 마진 하락 원인을 가격/원가뿐 아니라 처리시간과 예외율까지 연결해 인력 배치 최적화에 직접 기여한다.

### 6.5 지표 초안

| 지표 | 정의 초안 | 확정 필요 |
|---|---|---|
| 매출 | 기간 내 고객사/계약 기준 인식 매출 | 회계 인식 기준 PM/재무 승인 필요 |
| 원가 | 공급사 정산, 포인트/결제 비용, 운영 관련 직접비 | 직접비/간접비 배부 기준 PM 승인 필요 |
| 공헌이익 | 매출 - 직접 원가 | 원가 범위 PM 승인 필요 |
| 마진율 | 공헌이익 / 매출 | 재무 기준 PM 승인 필요 |
| 운영 투입량 | 업무 처리 건수, 평균 처리시간, 예외 처리 건수 | 처리시간 수집 방식 승인 필요 |
| SLA 초과율 | SLA 초과 건수 / 대상 업무 건수 | SLA 정책 A2/A8/PM 승인 필요 |
| 예외율 | 예외 상태 전환 건수 / 접수 건수 | 예외 분류 체계 승인 필요 |

결정: 미확정 재무/운영 지표는 화면에 `산식 검토중` 또는 `데이터 신뢰도 낮음`으로 표시하는 상태를 둔다.

인당 생산성/마진 기여: 불완전한 지표를 확정값처럼 쓰지 않아 잘못된 인력 감축/고객 정책 결정을 방지한다.

### 6.6 인수조건

- 사용자는 기간, 고객사, 공급사, 업무유형, 담당팀 기준으로 수익성 지표를 필터링할 수 있다.
- 권한이 없는 사용자는 전체 회사 지표 또는 비담당 고객사 상세를 볼 수 없다.
- 저마진/고투입 후보는 산식, 기준 기간, 데이터 신뢰도와 함께 표시된다.
- 대시보드의 고객사/업무유형 행에서 관련 Operations Console 필터 결과로 이동할 수 있다.
- 재무 기준이 확정되지 않은 지표는 PM 승인 필요 또는 데이터 품질 상태를 명확히 표시한다.

### 6.7 Profitability Dashboard DoD 요약

| 항목 | 내용 |
|---|---|
| 목적 | 고객사/공급사/업무유형별 수익성과 운영 투입량을 한 화면에서 비교한다 |
| 입력 | CRM Core, 매출/원가 데이터, Operations Console 처리량/SLA/예외 데이터, RBAC, 데이터 품질 플래그 |

| 인수조건 | 권한별 지표 범위가 제한되고, 미확정 지표는 신뢰도/PM 승인 필요 상태로 표시되며, 원인 업무 목록으로 이동할 수 있다 |

인당 생산성/마진 기여: 대시보드 DoD를 재무 숫자와 운영 투입의 연결성으로 잡아 경영 판단이 실제 비용 절감 액션으로 이어지게 한다.

인당 생산성/마진 기여: 낮은 이익의 원인을 즉시 업무 단위로 좁혀 가격, 할인, 배송, 결재 지연에 빠르게 대응한다.

## 6.9 결재라인 UI 초안

결재라인 UI는 견적, 계약, 세금계산서/거래명세표 발행, 매출인식 조정 화면에서 공통 컴포넌트로 사용한다.

| 항목 | UX 기준 |
|---|---|
| 작성자 | 현재 로그인한 임직원 본인으로 자동 지정하고 수정 불가로 표시 |
| 결재자 추가 | 임직원 검색으로 추가하며 소속/이름/권한을 함께 표시 |
| 순서 변경 | 드래그 또는 위/아래 이동 버튼으로 결재 순서 변경 |
| 최종 결재권자 | 마지막 결재자를 시각적으로 구분하고 누락 시 제출 차단 |
| 결재 상태 | 작성중, 상신, 진행중, 반려, 완료, 회수 상태 표시 |
| 이력 | 결재자, 시각, 코멘트, 상태 변경을 타임로그/감사로그로 연결 |
| 결재 버튼 | 결재 상세/처리 화면 진입 버튼으로 표시하고 상태 변경 버튼과 구분 |
| 승인 버튼 | 현재 결재자가 승인하며 다음 결재자 대기 또는 최종 승인 상태로 전환됨을 표시 |
| 반려 버튼 | 반려 사유 필수 입력 후 `rejected`로 전환됨을 표시 |
| 보류 버튼 | 보류 사유 필수 입력 후 `on_hold`로 전환됨을 표시 |

결정: 결재 문건 작성자는 로그인 사용자로 자동 지정하고, 결재라인은 사용자가 임직원 목록에서 추가/순서 변경할 수 있게 한다.

인당 생산성/마진 기여: 결재 누락과 승인자 확인 시간을 줄여 견적/계약/발행/매출인식 지연으로 인한 마진 손실을 낮춘다.

결정: `결재` 버튼은 상태 변경이 아니라 결재 상태와 처리 화면을 여는 버튼으로 정의하고, `승인`, `반려`, `보류`는 결과 상태를 바꾸는 액션 버튼으로 구분한다.

인당 생산성/마진 기여: 버튼 의미 혼동으로 인한 오처리와 재상신을 줄여 결재 처리량과 후속 업무 속도를 높인다.

결정: 결재 버튼 클릭 후 현재 결재 상태, 상신자, 현재 결재자, 다음 결재자, 최종 결재권자, 승인/반려/보류 이력, 반려/보류 사유를 즉시 표시한다.

인당 생산성/마진 기여: 결재 병목 위치와 사유를 즉시 보여줘 담당자가 누구에게 무엇을 확인해야 하는지 빠르게 판단하게 한다.

결정: 메뉴별 로그기록은 각 업무 화면이 아니라 상단 메인 `설정 > 로그기록`에서 탭과 필터로 제공한다.

인당 생산성/마진 기여: 메뉴별 활동을 한 곳에서 추적해 장애 조사, 권한 점검, 외감 대응 시간을 줄인다.

결정: 로그 조회와 로그 상세 조회 자체도 로그 대상으로 표시한다.

인당 생산성/마진 기여: 감사 자료 조회 행위까지 추적해 내부통제 리스크와 사후 확인 비용을 줄인다.

인당 생산성/마진 기여: 비용 입력 권한을 제한해 잘못된 비용값으로 인한 경영 판단 오류와 마진 분석 왜곡을 줄인다.

인당 생산성/마진 기여: 변경 전 영향 범위를 확인하게 해 대시보드 왜곡과 사후 정정 비용을 낮춘다.

## 7. 핵심 사용자 흐름

### F1. 운영자 일일 처리 흐름

1. 운영자가 로그인하면 본인/팀 큐와 SLA 위험 건을 먼저 본다.
2. 저장 필터 `오늘 처리 필요`를 선택한다.
3. 동일 업무유형과 동일 예외 사유 건을 선택한다.
4. 일괄 배정 또는 일괄 재시도를 수행한다.
5. 실패 건은 예외 큐로 남고 성공 건은 완료 또는 진행 상태로 이동한다.
6. 모든 변경은 감사로그에 기록된다.

인당 생산성/마진 기여: 반복 선택과 단건 처리 시간을 줄여 같은 인원이 더 많은 업무를 처리한다.

### F2. SLA 초과 대응 흐름

1. 운영 리더가 SLA 초과 KPI를 클릭한다.
2. 고객사, 업무유형, 담당자별 병목을 확인한다.
3. 대량 재배정 또는 우선순위 변경을 요청한다.
4. 고위험 변경은 승인 대기로 전환된다.
5. 처리 결과는 팀 생산성 지표에 반영된다.

인당 생산성/마진 기여: 병목 업무를 조기에 재배치해 지연으로 인한 CS/정산 재작업 비용을 줄인다.

### F3. 경영진 저마진 원인 확인 흐름

1. 경영진이 Profitability Dashboard에서 기간을 선택한다.
2. 저마진 고객사 랭킹을 확인한다.
3. 특정 고객사의 업무유형별 처리량, 예외율, SLA 초과율을 본다.
4. 원인 지표를 클릭해 Operations Console의 필터된 업무 목록으로 이동한다.
5. 운영 리더에게 정책/배정 조정 또는 고객 조건 재검토를 요청한다.

인당 생산성/마진 기여: 수익성 문제를 추상적 매출 보고가 아니라 실제 운영 투입 업무로 연결해 개선 대상을 좁힌다.

### F4. 개인정보 최소 열람 흐름

1. 운영자가 목록에서 마스킹 정보를 보고 업무를 분류한다.
2. 상세 식별 정보가 필요한 경우 `상세 열람`을 클릭한다.
3. 시스템은 열람 사유를 요구하고 권한을 확인한다.
4. 허용 시 제한 시간 동안 필요한 필드만 표시한다.
5. 열람자, 사유, 시간, 대상 ID가 감사로그에 기록된다.

인당 생산성/마진 기여: 개인정보 노출 리스크를 낮춰 사후 보안 대응과 감사 비용을 줄인다.

### F5. 견적 결재라인 지정 흐름

1. 일반 사용자가 견적 문건을 작성한다.
2. 작성자는 로그인 사용자 본인으로 자동 지정된다.
3. 사용자가 임직원 목록에서 결재자를 추가하고 순서를 조정한다.
4. 최종 결재권자가 포함되지 않으면 상신 버튼이 비활성화된다.
5. 상신 후 결재 상태와 변경 이력이 타임로그/감사로그에 남는다.

인당 생산성/마진 기여: 승인자 누락과 결재 순서 오류를 줄여 견적 발행 지연과 매출 기회 손실을 낮춘다.

### F5-1. 결재 버튼 상태 확인 흐름

1. 사용자가 견적, 계약, 발행, 매출인식 조정 목록에서 결재 상태 배지를 확인한다.
2. `결재` 버튼을 클릭한다.
3. 결재 상세 패널에서 현재 결재 상태, 현재 결재자, 다음 결재자, 최종 결재권자를 확인한다.
4. 반려 또는 보류 상태라면 사유와 이력을 즉시 확인한다.
5. 현재 사용자가 결재자이면 `승인`, `반려`, `보류` 버튼과 각 버튼의 결과 상태 설명을 본다.

인당 생산성/마진 기여: 결재 진행 상태 확인 문의를 줄이고 승인 병목을 빠르게 해소해 매출/계약 처리 지연을 낮춘다.

### F5-3. 입사등록 결재 승인 흐름

1. HR/관리자가 입사등록 상세에서 대상자 정보, 입사 예정일, 소속/부서, 직무/권한 후보를 입력한다.
2. 결재라인을 설정하고 상신 사유를 입력한다.
3. 결재상태 배지와 결재 타임라인에서 현재 결재자, 다음 결재자, 최종 결재권자를 확인한다.
4. 반려 또는 보류 시 사유를 확인하고 보완한다.
5. 최종 승인 후에만 `employee_activation_pending` 또는 활성화 후보 상태를 표시한다.
6. 최종 승인 전에는 계정 활성화 완료 또는 권한 부여 완료로 표시하지 않는다.

인당 생산성/마진 기여: 입사등록과 계정 활성화 사이의 승인 게이트를 명확히 해 승인 없는 계정 생성과 권한 오류를 줄인다.

### F5-2. 임직원 다중 거래처 배정 흐름

1. 관리자가 임직원 관리 상세에서 담당 거래처 편집을 연다.
2. 거래처를 검색해 여러 개 선택한다.
3. 각 거래처에 주담당, 부담당, 승인담당, 참조담당 역할과 대표 담당 여부를 지정한다.
4. 저장 전 변경 요약과 배정 사유를 확인한다.
5. 저장 후 임직원 상세에는 담당 거래처 목록이, 거래처 상세에는 담당자 목록과 대표 담당자가 표시된다.

인당 생산성/마진 기여: 담당 거래처를 한 번에 배정하고 양방향으로 확인하게 해 관리자 수작업 매칭과 담당자 확인 시간을 줄인다.

### F6. 배송/입출고 예외 처리 흐름

1. 관리자가 배송/입출고 화면에서 지연 또는 미출고 상태를 필터링한다.
2. 송장번호, 택배사, 현재 위치, 마지막 갱신 시각을 확인한다.
3. 연동 실패 건은 재조회 큐로 보내거나 수동 송장을 입력한다.
4. 배송 지연, 오배송, 반송은 Operations Console 예외 큐로 전환된다.
5. 예외 처리 결과가 고객/주문/배송 타임로그에 남는다.

인당 생산성/마진 기여: 배송 상태 문의를 단건 추적하지 않고 예외 큐로 처리해 운영자의 반복 확인 시간을 줄인다.

### F7. 메뉴별 로그기록 조회 흐름

1. 관리자 또는 감사 권한 사용자가 상단 메인 `설정 > 로그기록`에 진입한다.
2. 메뉴별 로그 탭을 선택한다.
3. 메뉴명, 기간, 사용자, 권한, 이벤트 유형, 결과, 대상 엔티티로 필터링한다.
4. 로그 상세를 열어 이벤트 결과와 사유 코드를 확인한다.
5. 로그 조회와 상세 조회 이력도 감사로그로 남는다.

인당 생산성/마진 기여: 메뉴별 로그 검색을 UI에서 처리해 개발자/DB 조회 의존을 줄이고 장애·감사 대응 시간을 낮춘다.

### F8. 수익성 비용 입력 흐름

1. `Master` 또는 `ProfitCostInputManager`가 상단 메인 `설정 > 수익성 비용 입력`에 진입한다.
2. 현재 산식 버전, 마지막 변경자, 마지막 변경 시각을 확인한다.
3. 제원원가, 판관비, 일반관리비를 입력하고 적용 범위를 선택한다.
4. 저장 전 변경 전후 값, 예상 영향 범위, 적용일, 변경 사유를 확인한다.
5. 저장 후 산식 버전과 영업이익 대시보드의 마지막 갱신 시각이 갱신된다.
6. 권한 없는 사용자는 메뉴가 숨겨지거나 접근 시 차단 사유와 로그를 본다.

인당 생산성/마진 기여: 비용 입력과 영향 확인을 표준화해 수익성 지표 신뢰도를 높이고 재검산 시간을 줄인다.

| E2E-UX-18 | 권한 없는 사용자가 수익성 비용 입력에 접근한다 | 메뉴가 숨겨지거나 차단 사유가 표시되고 권한 차단 로그가 남는다 |

결정: E2E 검증은 단순 화면 렌더링보다 권한, 감사로그, 일괄 처리 결과, 대시보드-운영 콘솔 드릴다운을 우선 확인한다.

인당 생산성/마진 기여: 실제 운영 병목과 규제 리스크가 발생하는 흐름을 먼저 검증해 재작업 가능성을 낮춘다.

## 10. PM 승인 필요 항목

1. Windows/iOS 지원을 초기에는 반응형 웹 또는 PWA로 가정해도 되는가?
2. 개인정보 상세 열람 대상 필드, 마스킹 규칙, 열람 사유 분류를 어떤 범위로 둘 것인가?
3. 고위험/고금액 업무의 승인 기준 금액과 승인자 역할은 무엇인가?
4. 수익성 지표의 매출/원가/마진 산식과 직접비/간접비 배부 기준은 무엇인가?
5. SLA 정책의 업무유형별 목표 시간과 에스컬레이션 기준은 무엇인가?
6. CSV/Excel 반입·반출 허용 범위와 파일 내 개인정보 정책은 무엇인가?
7. 외부 연동 실패 재시도 횟수, 수동 보정 권한, 재처리 책임자는 누구인가?
8. 영업이익 MVP 산식을 원가 50%, 판매관리비/일반관리비 50% 고정 기준으로 반영해도 되는가?
9. 택배사 실시간 위치 연동의 API, 비용, 계약 조건을 확정하기 전까지 수동 송장 입력과 재조회 큐로 설계해도 되는가?
10. 슈퍼바이저가 열람 가능한 영업이익, 로그, 임직원정보 범위는 어디까지인가?
11. 결재라인의 대리결재, 최종 결재권자 기준, 결재 회수/반려 정책은 무엇인가?
12. 상품 판매가격과 할인 정보 수정 권한 및 승인 기준은 무엇인가?
13. 거래처별 대표 담당자를 1명으로 제한하고 담당 역할을 주담당/부담당/승인담당/참조담당으로 시작해도 되는가?
14. 담당자 배정 변경 권한을 관리자 이상으로 제한해도 되는가?
15. `결재` 버튼을 상태 변경이 아닌 결재 상세/처리 화면 진입 버튼으로 정의해도 되는가?
16. `보류`를 공식 결재 상태로 두고 보류 사유 필수 입력을 요구해도 되는가?
17. 입사등록을 결재 필수 업무로 두고 최종 승인 후 계정 활성화는 자동 처리할 것인가, 관리자 확인 후 처리할 것인가?
18. 입사등록 결재라인 기본 템플릿을 둘 것인가?
19. 메뉴 진입 로그까지 필수로 남기고 메뉴별 로그 보존기간을 전체 감사로그와 동일하게 둘 것인가?
20. 로그 반출 권한을 슈퍼바이저와 감사 담당으로 제한할 것인가?
21. `제원원가`의 정확한 회계 의미를 제조원가/상품원가/기타 원가 중 무엇으로 볼 것인가?
22. 수익성 비용 입력 권한을 `Master`만 허용할 것인가, 별도 `ProfitCostInputManager` 권한도 둘 것인가?
23. 비용 입력 변경을 항상 결재 대상으로 둘 것인가?

인당 생산성/마진 기여: 승인 게이트를 명확히 하면 민감정보, 재무 기준, 운영 정책을 임의 확정해 생기는 비용과 리스크를 줄인다.
