# A3 프론트 초안: Operations Console / Profitability Dashboard

## 1. 문서 목적

이 문서는 이제너두 전사 CRM OS의 P0 모듈 중 A3가 담당하는 Operations Console과 Profitability Dashboard의 초기 화면, 사용자 흐름, 권한 차이, 인수조건을 정의한다.

본 문서는 개발 확정안이 아니라 프론트 UX/UI 초안이며, Windows/iOS 지원 방식, 개인정보 처리범위, 외부계약, 아키텍처 확정은 PM 김권일 승인 후 확정한다.

인당 생산성/마진 기여: 운영자가 한 화면에서 조회, 필터, 일괄처리, 예외 대응을 수행하고 경영진이 저마진 원인을 빠르게 식별하게 해 동일 인력의 처리량과 의사결정 속도를 높인다.

## 2. PRD 기준 P0 범위

| P0 모듈 | A3 화면 책임 | 연결 모듈 | KPI 영향 |
|---|---|---|---|
| Operations Console | 업무 큐, 검색, 필터, 배정, 상태 변경, SLA, 예외 큐, 일괄 처리 | CRM Core, Security & Audit Baseline, Settlement & Point Ops | 담당자 1인당 처리 건수 증가, 평균 처리시간 감소 |
| Profitability Dashboard | 고객사/공급사/업무유형별 매출, 원가, 마진, 운영 투입량 시각화 | CRM Core, 데이터/지표 정의, 정산/포인트 | 저마진 고객/업무 식별, 인력 배치 최적화 |

결정: A3 초안은 P0의 운영 처리 화면과 경영 지표 화면에 집중하고, Supplier Portal과 Customer Success Workspace는 P2/P2 후속으로 분리한다.

인당 생산성/마진 기여: 초기 화면 범위를 반복 처리량과 수익성 가시화에 제한해 낮은 ROI 화면 개발을 줄인다.

## 3. 공통 UX 원칙

1. 목록 우선: 운영자는 상세 화면 진입 전 목록에서 상태, SLA, 예외 사유, 담당자, 고객사, 금액 영향도를 확인한다.
2. 필터 저장: 자주 쓰는 조건은 개인/팀 저장 필터로 제공한다.
3. 일괄 처리 기본: 동일 조건의 업무는 선택 후 배정, 보류, 완료, 재시도, 반려 요청을 일괄 수행한다.
4. 개인정보 최소 노출: 목록에는 마스킹된 식별자와 업무상 필요한 최소 필드만 노출한다.
5. 감사 가능성: 상태 변경, 담당자 변경, 개인정보 열람, 일괄 작업은 모두 사유 입력과 로그 보존을 전제로 한다.
6. 경영 지표 드릴다운: 대시보드 수치에서 Operations Console의 원인 업무 목록으로 이동할 수 있어야 한다.

결정: 기본 화면은 반응형 웹/PWA를 가정하되 Windows 데스크톱과 iOS 태블릿/모바일 최적화는 PM 승인 필요로 둔다.

인당 생산성/마진 기여: 네이티브 앱보다 웹 우선으로 초기 운영 접근성을 확보하면 배포/교육 비용을 낮추고 현장 처리 속도를 빠르게 검증할 수 있다.

인당 생산성/마진 기여: 별도 화면을 과다하게 만들지 않으면서도 권한 리스크와 교육 비용을 줄인다.

## 5. Operations Console 초안

### 5.1 목적

운영 업무를 접수, 배정, 처리, 보류, 완료, 반려, 실패/재시도 상태로 표준화하고, 담당자가 검색/필터/일괄 처리로 업무 처리량을 높일 수 있게 한다.

인당 생산성/마진 기여: 상태와 액션을 표준화하면 수기 확인, 메신저 확인, 엑셀 재정렬 시간을 줄여 담당자 1인당 처리 건수를 늘린다.

### 5.2 주요 입력

- CRM Core: 고객사, 공급사, 임직원, 계약, 담당자, 활동 이력 ID
- 업무 접수 이벤트: CS, 포인트, 정산, 신청/심사, 연동 실패, 수동 보정 요청
- SLA 정책: 업무유형별 목표 처리시간, 우선순위, 에스컬레이션 기준
- 권한/RBAC: 사용자 역할, 소속 팀, 접근 가능 고객사/공급사 범위
- 감사 기준: 상태 변경 사유, 개인정보 열람 사유, 일괄 처리 로그

### 5.3 주요 출력

- 업무 큐 목록 및 저장 필터
- 업무 상세 패널과 처리 이력
- 일괄 처리 결과와 실패 사유
- SLA 위험/초과 목록
- 예외 큐와 재처리/수동 보정 요청
- 개인정보 접근 및 상태 변경 감사로그

### 5.4 핵심 화면 구성

| 영역 | 구성 | 설명 |
|---|---|---|
| 상단 검색 | 통합 검색, 저장 필터, 날짜 범위, 고객사/공급사 선택 | 고객사명, 공급사명, 계약 ID, 업무 ID, 마스킹 식별자로 검색 |
| KPI 스트립 | 신규, 진행중, SLA 위험, SLA 초과, 예외, 오늘 완료 | 팀 또는 개인 기준 운영량을 즉시 확인 |
| 필터 패널 | 업무유형, 상태, 우선순위, 담당자, SLA, 예외 사유, 금액 영향도 | 고반복 업무를 빠르게 분리 |
| 업무 테이블 | 체크박스, 상태, SLA 배지, 고객사, 업무유형, 담당자, 금액 영향도, 최근 이벤트 | 일괄 처리와 스캔 속도 중심 |
| 상세 드로어 | 입력값, 관련 엔티티, 처리 액션, 이력, 첨부/증적 | 페이지 이동 없이 검토와 처리 수행 |
| 일괄 액션 바 | 배정, 상태 변경, 보류, 재시도, 승인 요청, CSV 내보내기 요청 | 선택 건에 대한 대량 처리 |

결정: Operations Console은 테이블+상세 드로어 구조를 기본으로 하며, 처리 액션은 목록 선택 후 상단 일괄 액션 또는 상세 드로어에서 수행한다.

인당 생산성/마진 기여: 페이지 왕복을 줄이고 다건 처리 흐름을 기본값으로 만들어 동일 시간 내 처리량을 높인다.

### 5.5 상태 모델 초안

| 상태 | 의미 | 허용 액션 | 감사/승인 |
|---|---|---|---|
| `new` | 접수 후 미배정 | 배정, 보류, 반려 요청 | 배정자 로그 |
| `assigned` | 담당자 지정 | 처리 시작, 재배정, 보류 | 담당자 변경 로그 |
| `in_progress` | 처리 중 | 완료, 보류, 승인 요청, 예외 전환 | 변경 사유 |
| `pending_approval` | 고위험/금액/권한 사유로 승인 대기 | 승인, 반려, 보완 요청 | 승인자 로그 필수 |
| `blocked` | 외부 자료/연동/고객 확인 대기 | 보류 해제, 재배정, 반려 요청 | 보류 사유 |
| `exception` | 자동 처리 실패 또는 정책 외 케이스 | 재시도, 수동 보정, 에스컬레이션 | 예외 사유 |
| `completed` | 처리 완료 | 재오픈 요청 | 완료 근거 |
| `rejected` | 처리 불가/반려 | 재오픈 요청 | 반려 사유 |

결정: 상태명은 영문 식별자를 사용하고 화면 표기는 한국어로 제공한다.

인당 생산성/마진 기여: 상태 식별자는 연동/로그/분석과 일관성을 유지하고, 화면 표기는 현장 교육 비용을 낮춘다.

### 5.6 인수조건

- 운영자는 고객사, 공급사, 업무유형, 상태, SLA, 담당자, 예외 사유로 업무를 필터링할 수 있다.
- 운영자는 권한 내 업무를 1건 이상 선택해 일괄 배정, 보류, 재시도, 상태 변경 요청을 수행할 수 있다.
- 고위험 상태 변경, 개인정보 상세 열람, 금액 영향이 큰 일괄 처리는 사유 입력과 승인 흐름을 요구한다.
- SLA 위험/초과 건은 목록, KPI 스트립, 저장 필터에서 동일 기준으로 표시된다.
- 예외 큐의 각 건은 실패 원인, 마지막 재시도 시각, 권장 다음 액션을 보여준다.
- 모든 상태 변경과 개인정보 열람은 감사로그로 남는다.

### 5.7 Operations Console DoD 요약

| 항목 | 내용 |
|---|---|
| 목적 | 운영 업무 큐를 단일 콘솔에서 조회, 배정, 처리, 예외 대응하게 한다 |
| 입력 | CRM Core 엔티티, 업무 접수 이벤트, SLA 정책, RBAC, 감사 기준 |
| 출력 | 필터된 업무 목록, 처리 결과, 예외 큐, SLA 위험/초과 목록, 감사로그 |
| 인수조건 | 필터/검색/일괄처리/권한차단/감사로그/SLA 표시가 정상 동작한다 |
| 의존성 | A1/A2 CRM Core, A7/A9 RBAC/감사, A6 연동 실패 코드, A8 자동화 후보 |
| 담당 | A3 주관, A2/A7/A8 협업 |
| KPI 영향 | 담당자 1인당 처리 건수 증가, 평균 처리시간 감소, 예외 재처리 시간 감소 |

인당 생산성/마진 기여: DoD를 운영 처리량과 리스크 통제 기준으로 고정해 보기 좋은 화면보다 실제 업무 처리 성능을 우선 검증한다.

## 6. Profitability Dashboard 초안

### 6.1 목적

고객사/공급사/업무유형별 매출, 원가, 마진, 운영 투입량, SLA, 예외율을 한 화면에서 비교해 저마진 원인과 인력 투입 병목을 찾는다.

인당 생산성/마진 기여: 매출이 큰 고객이라도 운영 투입이 과도하면 마진을 훼손한다는 신호를 빠르게 보여줘 인력 배치와 운영 정책을 조정하게 한다.

### 6.2 주요 입력

- CRM Core: 고객사, 공급사, 계약, 담당 조직
- 매출/원가 데이터: 계약 매출, 수수료, 정산 원가, 포인트/결제 관련 비용
- Operations Console: 업무유형별 처리 건수, 처리시간, SLA 초과, 예외 건수, 담당자 투입량
- 권한/RBAC: 집계 범위와 고객사/공급사 열람 범위
- 데이터 품질 플래그: 미수집, 추정값, 정산 대기, 연동 지연

### 6.3 주요 출력

- 전체 매출, 원가, 공헌이익, 마진율
- 고객사/공급사별 수익성 랭킹
- 업무유형별 처리량, 평균 처리시간, 예외율, SLA 초과율
- 고투입/저마진 후보 목록
- Operations Console로 이동하는 원인 업무 드릴다운 링크
- 데이터 신뢰도 및 미확정 지표 표시

### 6.4 핵심 화면 구성

| 영역 | 구성 | 설명 |
|---|---|---|
| 상단 필터 | 기간, 고객사, 공급사, 업무유형, 담당팀, 계약 상태 | 경영진/리더/AM 권한별 기본 범위 적용 |
| 요약 KPI | 매출, 원가, 공헌이익, 마진율, 처리건수, 평균 처리시간 | 수익성과 운영 투입을 같은 행에 표시 |
| 경고 패널 | 저마진 고객, SLA 초과 급증, 예외율 상승, 데이터 품질 낮음 | 경영 의사결정이 필요한 항목 우선 노출 |
| 랭킹 테이블 | 고객사/공급사별 매출, 원가, 마진, 처리량, 예외율 | 정렬/필터/드릴다운 제공 |
| 업무유형 분석 | 업무유형별 처리량, 시간, 단가성 비용, 예외율 | 고비용 업무 후보 식별 |
| 원인 드릴다운 | 선택 지표의 업무 큐로 이동 | 대시보드 수치와 운영 액션 연결 |

결정: Profitability Dashboard는 재무 지표만 보여주지 않고 운영 투입 지표를 같은 맥락에 배치한다.

인당 생산성/마진 기여: 마진 하락 원인을 가격/원가뿐 아니라 처리시간과 예외율까지 연결해 인력 배치 최적화에 직접 기여한다.

### 6.5 지표 초안

| 지표 | 정의 초안 | 확정 필요 |
|---|---|---|
| 매출 | 기간 내 고객사/계약 기준 인식 매출 | 회계 인식 기준 PM/재무 승인 필요 |
| 원가 | 공급사 정산, 포인트/결제 비용, 운영 관련 직접비 | 직접비/간접비 배부 기준 PM 승인 필요 |
| 공헌이익 | 매출 - 직접 원가 | 원가 범위 PM 승인 필요 |
| 마진율 | 공헌이익 / 매출 | 재무 기준 PM 승인 필요 |
| 운영 투입량 | 업무 처리 건수, 평균 처리시간, 예외 처리 건수 | 처리시간 수집 방식 승인 필요 |
| SLA 초과율 | SLA 초과 건수 / 대상 업무 건수 | SLA 정책 A2/A8/PM 승인 필요 |
| 예외율 | 예외 상태 전환 건수 / 접수 건수 | 예외 분류 체계 승인 필요 |

결정: 미확정 재무/운영 지표는 화면에 `산식 검토중` 또는 `데이터 신뢰도 낮음`으로 표시하는 상태를 둔다.

인당 생산성/마진 기여: 불완전한 지표를 확정값처럼 쓰지 않아 잘못된 인력 감축/고객 정책 결정을 방지한다.

### 6.6 인수조건

- 사용자는 기간, 고객사, 공급사, 업무유형, 담당팀 기준으로 수익성 지표를 필터링할 수 있다.
- 권한이 없는 사용자는 전체 회사 지표 또는 비담당 고객사 상세를 볼 수 없다.
- 저마진/고투입 후보는 산식, 기준 기간, 데이터 신뢰도와 함께 표시된다.
- 대시보드의 고객사/업무유형 행에서 관련 Operations Console 필터 결과로 이동할 수 있다.
- 재무 기준이 확정되지 않은 지표는 PM 승인 필요 또는 데이터 품질 상태를 명확히 표시한다.

### 6.7 Profitability Dashboard DoD 요약

| 항목 | 내용 |

| 목적 | 고객사/공급사/업무유형별 수익성과 운영 투입량을 한 화면에서 비교한다 |
| 입력 | CRM Core, 매출/원가 데이터, Operations Console 처리량/SLA/예외 데이터, RBAC, 데이터 품질 플래그 |
| 출력 | 매출, 원가, 공헌이익, 마진율, 처리건수, 평균 처리시간, 예외율, 저마진 후보, 드릴다운 링크 |
| 인수조건 | 권한별 지표 범위가 제한되고, 미확정 지표는 신뢰도/PM 승인 필요 상태로 표시되며, 원인 업무 목록으로 이동할 수 있다 |
| 의존성 | A4 수익성 지표 정의, A1/A2 기준 데이터, A7/A9 권한, 재무/PM 산식 승인 |
| 담당 | A3 주관, A4/A7/PM 협업 |
| KPI 영향 | 저마진 고객/업무 식별 시간 감소, 인력 배치 최적화, 운영 투입 대비 마진 개선 |

인당 생산성/마진 기여: 대시보드 DoD를 재무 숫자와 운영 투입의 연결성으로 잡아 경영 판단이 실제 비용 절감 액션으로 이어지게 한다.

## 7. 핵심 사용자 흐름

### F1. 운영자 일일 처리 흐름

1. 운영자가 로그인하면 본인/팀 큐와 SLA 위험 건을 먼저 본다.
2. 저장 필터 `오늘 처리 필요`를 선택한다.
3. 동일 업무유형과 동일 예외 사유 건을 선택한다.
4. 일괄 배정 또는 일괄 재시도를 수행한다.
5. 실패 건은 예외 큐로 남고 성공 건은 완료 또는 진행 상태로 이동한다.
6. 모든 변경은 감사로그에 기록된다.

인당 생산성/마진 기여: 반복 선택과 단건 처리 시간을 줄여 같은 인원이 더 많은 업무를 처리한다.

### F2. SLA 초과 대응 흐름

1. 운영 리더가 SLA 초과 KPI를 클릭한다.
2. 고객사, 업무유형, 담당자별 병목을 확인한다.
3. 대량 재배정 또는 우선순위 변경을 요청한다.
4. 고위험 변경은 승인 대기로 전환된다.
5. 처리 결과는 팀 생산성 지표에 반영된다.

인당 생산성/마진 기여: 병목 업무를 조기에 재배치해 지연으로 인한 CS/정산 재작업 비용을 줄인다.

### F3. 경영진 저마진 원인 확인 흐름

1. 경영진이 Profitability Dashboard에서 기간을 선택한다.
2. 저마진 고객사 랭킹을 확인한다.
3. 특정 고객사의 업무유형별 처리량, 예외율, SLA 초과율을 본다.
4. 원인 지표를 클릭해 Operations Console의 필터된 업무 목록으로 이동한다.
5. 운영 리더에게 정책/배정 조정 또는 고객 조건 재검토를 요청한다.

인당 생산성/마진 기여: 수익성 문제를 추상적 매출 보고가 아니라 실제 운영 투입 업무로 연결해 개선 대상을 좁힌다.

### F4. 개인정보 최소 열람 흐름

1. 운영자가 목록에서 마스킹 정보를 보고 업무를 분류한다.
2. 상세 식별 정보가 필요한 경우 `상세 열람`을 클릭한다.
3. 시스템은 열람 사유를 요구하고 권한을 확인한다.
4. 허용 시 제한 시간 동안 필요한 필드만 표시한다.
5. 열람자, 사유, 시간, 대상 ID가 감사로그에 기록된다.

인당 생산성/마진 기여: 개인정보 노출 리스크를 낮춰 사후 보안 대응과 감사 비용을 줄인다.

| 검증 ID | 시나리오 | 기대 결과 |

결정: E2E 검증은 단순 화면 렌더링보다 권한, 감사로그, 일괄 처리 결과, 대시보드-운영 콘솔 드릴다운을 우선 확인한다.

인당 생산성/마진 기여: 실제 운영 병목과 규제 리스크가 발생하는 흐름을 먼저 검증해 재작업 가능성을 낮춘다.

## 10. PM 승인 필요 항목

1. Windows/iOS 지원을 초기에는 반응형 웹 또는 PWA로 가정해도 되는가?
2. 개인정보 상세 열람 대상 필드, 마스킹 규칙, 열람 사유 분류를 어떤 범위로 둘 것인가?
3. 고위험/고금액 업무의 승인 기준 금액과 승인자 역할은 무엇인가?
4. 수익성 지표의 매출/원가/마진 산식과 직접비/간접비 배부 기준은 무엇인가?
5. SLA 정책의 업무유형별 목표 시간과 에스컬레이션 기준은 무엇인가?
6. CSV/Excel 반입·반출 허용 범위와 파일 내 개인정보 정책은 무엇인가?
7. 외부 연동 실패 재시도 횟수, 수동 보정 권한, 재처리 책임자는 누구인가?

인당 생산성/마진 기여: 승인 게이트를 명확히 하면 민감정보, 재무 기준, 운영 정책을 임의 확정해 생기는 비용과 리스크를 줄인다.
