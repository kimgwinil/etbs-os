# Operations Console 상세 화면 스펙

## 1. 목적

Operations Console은 이제너두 전사 CRM OS의 P0 운영 업무 처리 화면이다. 운영자는 업무 접수, 검색, 필터, 배정, 상태 변경, SLA 대응, 예외 처리, 일괄 처리를 단일 콘솔에서 수행한다.

본 문서는 프론트 화면/흐름 스펙이며 백엔드 아키텍처, 개인정보 처리범위, 외부 연동 구현 방식은 확정하지 않는다. 관련 확정은 PM 김권일 승인 필요.

인당 생산성/마진 기여: 단일 콘솔에서 반복 업무를 대량 처리하게 해 담당자 1인당 처리 건수를 높이고 평균 처리시간을 줄인다.

## 2. 범위

### 포함

- 운영 업무 큐 목록
- 통합 검색과 고급 필터
- 저장 필터와 기본 뷰
- 업무 상세 드로어
- 일괄 배정/상태 변경/재시도/보류/승인 요청
- SLA 위험/초과 표시
- 예외 큐와 수동 보정 흐름
- 역할별 화면/액션 차이
- 개인정보 최소 노출 및 열람 로그 UX
- Profitability Dashboard 드릴다운 연동 지점
- 모든 목록 화면의 고정 필드 헤더
- 설정 메뉴 옆 사용자 정보 표시
- 고객 신규/수정 저장 흐름
- 판매상품 판매가격 강조
- 결재라인 UI
- 임직원 관리의 다중 거래처 선택과 거래처 담당자 표시
- 결재 버튼 클릭 후 결재 상태/현재 결재자/다음 결재자/반려·보류 사유 표시
- 입사등록 상세의 결재상태 배지, 결재 타임라인, 결재라인 설정, 최종 승인 전 계정 활성화 표시 금지
- 설정 메뉴 로그기록의 메뉴별 로그 탭과 필터
- 설정 메뉴의 수익성 비용 입력 UI와 권한 통제
- 슈퍼바이저 대시보드 진입점
- 배송/입출고 상태 화면과 예외 큐 연결

### 제외

- 정산/포인트 상세 회계 처리 로직
- 외부 연동 어댑터 구현
- 공급사/고객사 포털 화면
- AI 자동 의사결정
- 네이티브 Windows/iOS 앱

결정: 초기 범위는 운영자가 매일 쓰는 큐와 처리 액션에 집중하고, 전문 도메인 상세 처리는 후속 모듈 상세 화면으로 위임한다.

인당 생산성/마진 기여: 콘솔의 핵심 반복 작업을 먼저 표준화해 화면 과확장으로 인한 개발비와 교육 비용을 줄인다.

## 3. 사용자와 권한

| 역할 | 기본 진입 뷰 | 허용 액션 | 제한 사항 |
|---|---|---|---|
| 운영 담당자 | `내 업무`, `팀 업무`, `SLA 위험` | 처리 시작, 보류, 완료 요청, 재시도, 본인 메모 | 타팀/비권한 고객사 제한, 고위험 완료 승인 필요 |
| 운영 리더 | `팀 전체`, `SLA 초과`, `예외 큐` | 배정, 재배정, 우선순위 변경, 승인/반려 | 개인정보 상세 열람 사유 필수 |
| 재무/정산 담당자 | `정산/포인트 큐`, `증적 필요` | 정산 관련 확인, 증적 요청, 보류/완료 요청 | 임직원 민감정보 제한 |
| 보안/개인정보 담당자 | `접근 로그`, `권한 예외` | 접근 로그 조회, 권한 위반 표시, 감사 코멘트 | 업무 처리 상태 직접 변경 제한 |
| 경영진/PM | `운영 요약`, `병목/예외` | 집계 조회, 드릴다운, 지시 메모 | 개별 개인정보 상세 제한 |
| AM/영업 | `담당 고객사 이슈` | 담당 고객사 업무 조회, 코멘트, 후속 요청 | 전체 큐/수익성 상세 제한 |
| 일반 | `내 영업활동`, `내 파이프라인`, `견적`, `주문`, `내 결재함` | 본인 업무 작성/상신/조회 | 전사 영업이익, 전사 로그, 권한 관리 제한 |
| 관리자 | `고객`, `상품`, `주문`, `출고`, `배송/입출고`, `팀 업무` | 팀 운영 처리, 고객/상품/주문 관리 | 영업이익 산식/권한 변경 제한 |
| 슈퍼바이저 | `전사 대시보드`, `영업이익`, `로그`, `설정`, `권한 관리` | 전사 지표, 예외 분석, 승인된 로그 조회 | 승인되지 않은 개인정보 상세 제한 |

결정: 동일 화면 컴포넌트를 사용하되 역할별 기본 뷰, 데이터 범위, 액션 가능 여부를 권한으로 분기한다.

인당 생산성/마진 기여: 화면을 역할별로 완전히 분리하지 않아 개발/유지보수 비용을 낮추고, 권한 기반 통제로 규제 리스크를 줄인다.

결정: 권한별 메뉴는 `일반`, `관리자`, `슈퍼바이저`, `경영진/PM` 기준으로 1차 분기하고, 세부 데이터 범위는 RBAC로 제한한다.

인당 생산성/마진 기여: 역할별로 필요한 메뉴만 노출해 반복 업무 탐색 시간을 줄이고 민감 지표 노출 리스크를 낮춘다.

### 3.1 권한별 메뉴 및 사용자 컨텍스트 보강

`/specs/frontend/role-menu-user-context.md`를 기준으로 R23, R27, R28을 다음처럼 적용한다.

| 요구 ID | 항목 | UX 기준 | 인수조건 |
|---|---|---|---|
| R27 | 권한별 메뉴 차등 | 일반, 관리자, 슈퍼바이저, 경영자/PM은 서로 다른 메뉴와 업무 진행 메뉴를 본다 | 권한별 로그인 시 표시 메뉴가 다르고 API 권한과 일치한다 |
| R28 | 설정 옆 사용자 정보 표시 | 전역 헤더의 설정 메뉴 옆에 소속, 이름, 권한명을 표시한다 | 세션 갱신 또는 재로그인 후 변경된 권한이 메뉴와 사용자 정보에 반영된다 |
| R23 | 설정 메뉴 로그기록 확인 | 설정 하위에 `로그기록` 메뉴를 둔다 | 권한 있는 사용자는 로그 목록을 보고 권한 없는 접근은 차단 로그가 남는다 |
| R34 | 설정 메뉴 단일화 | 설정 진입점은 상단 메인 `설정` 하나만 유지하고 각 업무 화면 우측 상단 개별 설정 버튼은 제거한다 | 업무 화면 우측 상단에 시스템 설정 버튼이 있으면 QA 반려 |

표시 형식:

- 데스크톱: `소속 / 이름 / 권한명`을 설정 메뉴 왼쪽 또는 오른쪽 인접 영역에 표시한다.
- 좁은 화면: 이름과 권한 배지를 우선 표시하고, 소속은 사용자 메뉴 안에서 확인한다.
- 권한 변경: 세션 갱신 또는 재로그인 시 메뉴, 사용자 정보, 액션 버튼이 함께 갱신된다.

결정: 사용자 정보 표시는 단순 프로필 UI가 아니라 현재 메뉴/업무 권한을 이해시키는 컨텍스트 영역으로 본다.

인당 생산성/마진 기여: 로그인 사용자와 권한 범위를 즉시 확인해 대리 처리 착오와 불필요한 권한 문의를 줄인다.

결정: 권한 없는 메뉴 접근은 UI에서 숨기는 것을 원칙으로 하되, 직접 URL 접근 등 차단 이벤트는 감사로그 대상으로 남긴다.

인당 생산성/마진 기여: 화면 노출을 줄이는 동시에 우회 접근을 추적해 보안 사고 대응 비용을 낮춘다.

결정: 시스템 설정 진입점은 전역 헤더의 상단 메인 `설정` 메뉴 하나만 유지한다.

인당 생산성/마진 기여: 설정 위치를 하나로 고정해 사용자의 탐색 혼란과 중복 UI 관리 비용을 줄인다.

결정: 각 업무 메뉴, 목록, 상세 화면의 오른쪽 상단 개별 시스템 설정 버튼은 제거 대상으로 명시한다.

인당 생산성/마진 기여: 화면별 중복 설정 버튼을 없애 업무 화면의 시각적 밀도를 낮추고 처리 액션에 집중하게 한다.

### 3.2 설정 메뉴 로그기록 UI

`/specs/audit/menu-log-records.md`를 기준으로 상단 메인 `설정 > 로그기록`에서 메뉴별 로그를 조회한다.

| 영역 | 필수 요소 | 인수조건 |
|---|---|---|
| 메뉴별 로그 탭 | 전체, Operations, 고객, 임직원, 입사등록, 상품, 견적/계약, 주문/배송, 결재, 대시보드, 설정 | 메뉴별 탭을 선택하면 해당 메뉴 ID/라우트 ID 기준 로그만 표시된다 |
| 필터 바 | 메뉴명, 기간, 사용자, 권한, 이벤트 유형, 결과, 대상 엔티티, 사유 코드 | 복수 필터 조합으로 로그 목록이 갱신된다 |
| 이벤트 유형 | `menu_opened`, `list_viewed`, `detail_viewed`, `created`, `updated`, `deleted`, `approved`, `rejected`, `on_hold`, `export_requested`, `filter_saved`, `permission_denied` | 이벤트 유형별 필터링과 집계가 가능하다 |
| 로그 목록 | 시각, 메뉴명, 사용자, 권한, 대상 엔티티, 이벤트 유형, 결과, 사유 코드 | 개인정보 포함 값은 기본 마스킹된다 |
| 로그 상세 | 메뉴 ID, 라우트 ID, 대상 ID, 변경 요약, 결과, 사유, 관련 업무 ID | 로그 상세 조회 자체도 감사로그로 남는다 |

결정: 메뉴별 로그기록은 각 업무 화면에 분산하지 않고 상단 메인 `설정 > 로그기록`에서 탭과 필터로 제공한다.

인당 생산성/마진 기여: 메뉴별 활동 이력을 한 곳에서 추적해 장애 조사, 권한 점검, 외감 대응 시간을 줄인다.

결정: 메뉴 진입, 조회, 생성, 수정, 삭제, 결재, 반출, 필터 저장, 권한 차단 이벤트는 메뉴 ID와 함께 기록된다는 전제로 UI를 설계한다.

인당 생산성/마진 기여: 메뉴 단위 로그를 표준화해 반복 오류와 권한 이슈를 빠르게 찾아 교육/권한 정비 비용을 낮춘다.

결정: 로그 조회와 로그 상세 조회 자체도 로그 대상으로 표시하며, 개인정보 포함 로그는 기본 마스킹한다.

인당 생산성/마진 기여: 감사 자료 접근까지 추적해 내부통제 리스크와 사후 확인 비용을 낮춘다.

### 3.3 수익성 비용 입력 UI

`/specs/settings/profit-cost-permission.md`를 기준으로 상단 메인 `설정 > 수익성 비용 입력`에서 제원원가, 판관비, 일반관리비를 입력한다.

| 영역 | 필수 요소 | 인수조건 |
|---|---|---|
| 접근 권한 | `Master`, `ProfitCostInputManager` | 두 권한만 입력/수정/삭제 가능하고 권한 없는 사용자는 메뉴 숨김 또는 차단 사유를 본다 |
| 비용 입력 | 제원원가, 판관비, 일반관리비 | 각 비용 항목은 금액 또는 매출 대비 비율 후보로 입력된다 |
| 적용 범위 | 전사, 상품, 고객, 기간 | 저장 전 적용 범위를 명확히 표시한다 |
| 산식 정보 | 현재 산식 버전, 마지막 변경자, 마지막 변경 시각 | 입력 화면과 저장 확인 화면에 산식 버전을 표시한다 |
| 저장 전 확인 | 변경 전 값, 변경 후 값, 예상 영향 범위, 적용일, 변경 사유 | 저장 전 확인 없이는 반영하지 않는다 |
| 저장 후 반영 | 변경 로그, 감사로그, 대시보드 산식 버전, 마지막 갱신 시각 | 저장 후 영업이익 대시보드에 같은 산식 버전이 표시된다 |

결정: 수익성 비용 입력은 상단 메인 `설정 > 수익성 비용 입력`에서만 접근하고 각 업무 화면이나 대시보드 내부 편집으로 제공하지 않는다.

인당 생산성/마진 기여: 영업이익 산식에 영향을 주는 비용 입력을 중앙 통제해 임의 변경과 재검산 시간을 줄인다.

결정: 제원원가, 판관비, 일반관리비 입력/수정/삭제는 `Master` 또는 `ProfitCostInputManager`만 가능하게 설계한다.

인당 생산성/마진 기여: 수익성 지표에 직접 영향을 주는 입력 권한을 제한해 잘못된 비용 입력으로 인한 경영 판단 오류를 줄인다.

결정: 저장 전 영향 범위와 변경 전후 값, 적용일, 변경 사유, 산식 버전을 표시하고 사용자가 확인해야 저장할 수 있다.

인당 생산성/마진 기여: 비용 변경의 영향을 사전에 확인해 대시보드 왜곡과 사후 정정 비용을 낮춘다.

결정: 비용 입력 변경이 결재 대상인 경우 최종 승인 전에는 영업이익 대시보드에 적용하지 않는 상태를 표시한다.

인당 생산성/마진 기여: 미승인 비용 변경이 경영 지표에 반영되는 것을 막아 수익성 판단 신뢰도를 유지한다.

### 4.2 화면 레이아웃

| 영역 | 필수 요소 | 동작 |
|---|---|---|
| 전역 헤더 | 현재 메뉴, 검색, 알림, 설정, 사용자 정보 | 설정 메뉴 옆에 소속/이름/권한 표시 |
| 화면 헤더 | 페이지명, 기본 뷰 탭, 새로고침, 내 저장 필터, 보기 설정 후보 | 현재 권한과 필터 범위를 표시하며 시스템 설정 버튼은 두지 않음 |
| KPI 스트립 | 신규, 미배정, 진행중, SLA 위험, SLA 초과, 예외, 오늘 완료 | 클릭 시 해당 필터 적용 |
| 검색/필터 바 | 통합 검색, 날짜, 고객사, 공급사, 업무유형, 상태, 담당자 | 필터 변경 시 목록 갱신 |
| 목록 테이블 | 고정 필드 헤더, 다중 선택, 정렬, 컬럼 표시/숨김, 페이지네이션 | 대량 처리와 빠른 스캔 지원 |

| 상세 드로어 | 업무 요약, 관련 엔티티, 입력값, 액션, 이력, 로그 | 목록 맥락을 유지한 채 처리 |

결정: 상세는 별도 페이지가 아니라 우측 드로어를 기본으로 한다.

인당 생산성/마진 기여: 목록 맥락을 유지해 다음 건으로 이동하는 시간을 줄이고 운영자의 연속 처리 흐름을 끊지 않는다.

결정: 모든 목록 테이블은 세로 스크롤 시 필드 헤더를 상단 고정하고, 고객명/상품명/업무 ID 같은 핵심 식별 컬럼은 가로 스크롤 시 고정 후보로 둔다.

인당 생산성/마진 기여: 긴 목록에서 필드 의미와 대상 식별자를 계속 보이게 해 오처리와 재확인 시간을 줄인다.

결정: 전역 헤더의 설정 메뉴 옆에는 `소속`, `이름`, `권한`을 표시하고, 권한별 메뉴 차등 결과를 사용자가 즉시 인지하게 한다.

인당 생산성/마진 기여: 사용자의 처리 범위 착오를 줄여 권한 오류와 내부 문의 시간을 낮춘다.

### 4.2.1 업무 화면 우측 상단 설정 버튼 제거

| 대상 화면 | 제거 대상 | 허용 대체 |
|---|---|---|
| Operations 목록/상세 | 시스템 설정처럼 보이는 우측 상단 설정 버튼 | 저장 필터, 필터 저장, 보기 설정 |
| 고객/임직원/상품 목록 | 컬럼/정렬 변경을 시스템 설정으로 보이게 하는 버튼 | 보기 설정, 컬럼 표시/숨김 |
| 견적/계약/주문/배송 화면 | 업무 설정으로 오해되는 톱니바퀴/설정 버튼 | 화면별 작업 버튼, 필터 저장 |
| 결재함/상신 문건 | 결재 설정 버튼 | 결재라인 편집, 보기 설정 |
| Profitability/Supervisor Dashboard | 대시보드 시스템 설정 버튼 | 기간/지표 보기 설정, 필터 저장 |

`보기 설정`은 현재 화면의 컬럼, 밀도, 정렬 기본값처럼 보기 범위만 조정한다. 권한 관리, 로그기록, 사용자 정보, 슈퍼바이저 설정 같은 시스템 설정은 상단 메인 `설정` 메뉴 하위에서만 접근한다.

결정: 화면별 보기 옵션은 `보기 설정` 또는 `필터 저장`으로 분리하고, 시스템 설정처럼 보이는 톱니바퀴 단독 아이콘이나 `설정` 명칭을 사용하지 않는다.

인당 생산성/마진 기여: 화면별 개인화와 시스템 설정을 구분해 운영자가 실제 처리 버튼과 설정 버튼을 혼동하는 시간을 줄인다.

결정: QA는 업무 화면 우측 상단에 시스템 설정 버튼이 보이면 R34 위반으로 반려한다.

인당 생산성/마진 기여: 반려 기준을 명확히 해 중복 UI가 재유입되는 것을 막고 리뷰 시간을 줄인다.

인당 생산성/마진 기여: 화면별 목록 사용법을 통일해 학습 비용을 줄이고 대량 데이터 처리 중 컬럼 혼동을 낮춘다.

결정: 가로 드래그 목록은 첫 식별 컬럼과 현재 컬럼명을 유지해 필드값의 종류를 계속 식별할 수 있게 한다.

인당 생산성/마진 기여: 드래그 중 잘못된 컬럼값을 읽고 처리하는 오류를 줄여 정정 비용과 처리 지연을 낮춘다.

### 4.5 임직원-거래처 담당 배정 화면

`/specs/employee/customer-assignment.md`를 기준으로 임직원 관리와 거래처 화면에 다대다 담당 배정 UX를 적용한다.

| 화면 | 입력 | 출력 | 인수조건 |
|---|---|---|---|
| 임직원 상세 > 담당 거래처 | 거래처 검색어, 다중 선택 거래처, 담당 역할, 대표 담당 여부, 배정 기간, 배정 사유 | 임직원별 담당 거래처 목록 | 임직원 한 명에게 거래처 여러 개를 배정할 수 있다 |
| 거래처 상세 > 담당자 | 임직원 검색어, 다중 선택 임직원, 담당 역할, 대표 담당 여부, 배정 기간, 배정 사유 | 거래처별 담당자 목록 | 거래처 하나에 담당자 여러 명을 배정할 수 있다 |
| 거래처 목록 | 거래처, 대표 담당자, 담당자 수, 담당 역할 요약 | 대표 담당자 컬럼과 담당자 수 | 거래처 목록에서 대표 담당자를 확인할 수 있다 |
| 배정 변경 확인 | 추가/변경/종료 대상, 배정 사유 | 변경 요약, 타임로그 | 저장 전 변경 내용을 확인하고 저장 후 로그가 남는다 |

담당 역할 기본값:

- `primary_owner`: 주담당
- `secondary_owner`: 부담당
- `approval_owner`: 승인담당
- `reference_owner`: 참조담당

결정: 임직원과 거래처는 1:1이 아니라 `employee_customer_assignment` 관계를 전제로 한 다대다 배정 UI로 설계한다.

인당 생산성/마진 기여: 한 직원이 여러 거래처를 관리하고 한 거래처에 여러 담당자가 붙는 현실을 반영해 담당 공백과 중복 문의를 줄인다.

결정: 거래처 상세과 거래처 목록에는 대표 담당자, 담당자 수, 담당 역할을 명확히 표시한다.

인당 생산성/마진 기여: 거래처 화면에서 책임자를 즉시 확인해 업무 배정, 문의 응대, 승인 요청 시간을 줄인다.

결정: 담당자 배정, 변경, 종료는 저장 전 변경 요약을 보여주고 저장 후 타임로그 대상으로 남긴다.

인당 생산성/마진 기여: 조직 변경과 인수인계 상황에서 누가 언제 담당을 바꿨는지 추적해 재확인 시간을 줄인다.

| 금액 영향도 | 없음, 낮음, 중간, 높음 | 전체 |
| 예외 사유 | 연동 실패, 증적 부족, 정책 외, 데이터 불일치 | 전체 |

### 6.3 저장 필터

필수 기본 저장 필터:

- `내 오늘 처리`
- `팀 SLA 위험`
- `미배정 신규`
- `예외 재시도 필요`
- `승인 대기`
- `고금액 영향`

결정: 저장 필터는 개인 필터와 팀 공용 필터를 모두 지원하되, 팀 공용 필터 생성/수정은 운영 리더 이상으로 제한한다.

인당 생산성/마진 기여: 반복 조건 설정 시간을 줄이고 팀 단위 업무 기준을 표준화해 처리 편차를 낮춘다.

## 7. 상태 변경

### 7.1 상태 전이

| From | To | 수행자 | 필수 입력 | 승인 |
|---|---|---|---|---|
| `new` | `assigned` | 운영 리더, 자동 배정 정책 | 담당자 | 없음 |
| `assigned` | `in_progress` | 담당자 | 없음 | 없음 |
| `in_progress` | `completed` | 담당자 | 완료 사유/증적 | 조건부 |
| `in_progress` | `blocked` | 담당자 | 보류 사유, 해제 조건 | 없음 |
| `blocked` | `in_progress` | 담당자/리더 | 보류 해제 사유 | 없음 |
| `in_progress` | `pending_approval` | 담당자/리더 | 승인 요청 사유 | 필수 |
| `pending_approval` | `completed` | 승인자 | 승인 코멘트 | 필수 |
| `pending_approval` | `rejected` | 승인자 | 반려 사유 | 필수 |
| `in_progress` | `exception` | 시스템/담당자 | 예외 사유 | 없음 |
| `exception` | `in_progress` | 담당자/리더 | 조치 계획 | 조건부 |
| `exception` | `completed` | 담당자/승인자 | 수동 보정 근거 | 조건부 |

결정: 모든 상태 변경은 단건/일괄 모두 같은 전이 규칙을 사용한다.

인당 생산성/마진 기여: 단건과 일괄 처리의 정책 차이를 없애 오류와 재작업을 줄인다.

### 7.2 상태 변경 UX

- 상태 변경 버튼은 현재 상태와 권한에 따라 노출한다.
- 위험 액션은 버튼 클릭 후 확인 모달을 표시한다.
- 고금액/개인정보/정산 영향 업무는 승인 요청으로 전환한다.
- 일괄 상태 변경 시 성공/실패/승인 대기 전환 건수를 결과 패널에 표시한다.
- 실패 건은 실패 사유별로 그룹화해 재시도 또는 예외 큐 이동을 제안한다.

인당 생산성/마진 기여: 실패 결과를 그룹화하면 운영자가 같은 원인의 문제를 한 번에 처리해 반복 확인 시간을 줄인다.

## 8. 일괄 처리

### 8.1 일괄 액션

| 액션 | 설명 | 제한 |
|---|---|---|
| 일괄 배정 | 선택 업무를 특정 담당자/팀에 배정 | 운영 리더 이상 또는 정책 허용 |
| 일괄 재배정 | 담당자 변경 | 기존/신규 담당자 로그 필요 |
| 일괄 보류 | 동일 사유로 보류 처리 | 보류 사유 필수 |
| 일괄 재시도 | 연동 실패/자동 처리 실패 재시도 | 재시도 가능 상태만 허용 |
| 일괄 승인 요청 | 고위험 업무를 승인 큐로 이동 | 승인 사유 필수 |
| 일괄 완료 요청 | 처리 완료 상태로 이동 또는 승인 요청 | 조건부 승인 |
| CSV/Excel 내보내기 요청 | 필터 결과 반출 요청 | 개인정보/권한 정책 PM 승인 필요 |

결정: 일괄 처리는 선택 건 전체에 바로 적용하지 않고, 적용 가능/불가/승인 필요 건수를 미리 보여주는 확인 단계를 둔다.

인당 생산성/마진 기여: 대량 처리 오류를 사전에 차단해 복구 작업과 고객 영향 비용을 줄인다.

### 8.2 일괄 처리 결과

결과 패널 필수 표시:

- 요청 건수
- 성공 건수
- 실패 건수
- 승인 대기 전환 건수
- 실패 사유 그룹
- 감사 로그 ID
- 후속 액션 버튼

인당 생산성/마진 기여: 처리 결과를 즉시 요약해 운영자가 실패 건만 다시 다루게 하므로 반복 검증 시간을 줄인다.

## 9. SLA

### 9.1 SLA 표시

| 상태 | 표시 | 기준 |
|---|---|---|
| 정상 | 회색/기본 배지 | 목표시간까지 충분 |
| 위험 | 주의 배지 | 목표시간 임박 |
| 초과 | 경고 배지 | 목표시간 초과 |
| 제외 | 보류/승인 대기 등 정책상 제외 | SLA 정책 PM 승인 필요 |

정확한 임박 기준, 보류 중 SLA 정지 여부, 업무유형별 목표시간은 PM 승인 필요.

인당 생산성/마진 기여: SLA 위험 업무를 조기에 식별해 지연으로 인한 문의, 보상, 재처리 비용을 줄인다.

### 9.2 SLA 흐름

1. KPI 스트립의 `SLA 위험` 또는 `SLA 초과`를 클릭한다.
2. 목록은 SLA 기준으로 정렬된다.
3. 운영 리더는 담당자/업무유형/고객사 기준 병목을 확인한다.
4. 재배정, 우선순위 변경, 보류 사유 확인 중 하나를 수행한다.
5. 처리 결과는 감사로그와 팀 KPI에 반영된다.

인당 생산성/마진 기여: 병목을 담당자 개인의 기억이 아니라 큐 데이터로 관리해 팀 전체 처리량을 안정화한다.

인당 생산성/마진 기여: 중복 고객 생성을 줄이되 과도한 차단으로 신규 영업 등록이 지연되는 비용을 피한다.

인당 생산성/마진 기여: 고객정보 오수정과 사후 복구 비용을 줄이고 개인정보/영업정보 통제 비용을 낮춘다.

인당 생산성/마진 기여: 판매가격 오입력과 할인 누락을 줄여 마진 훼손을 예방한다.

인당 생산성/마진 기여: 과거 견적/주문 금액이 임의 변경되는 위험을 막아 정산 오류와 고객 분쟁 비용을 줄인다.

## 13. 결재라인 UI

결재라인은 견적, 계약, 세금계산서/거래명세표 발행, 매출인식 조정에서 공통으로 사용한다.

| 항목 | 입력 | 출력 | 인수조건 |
|---|---|---|---|
| 작성자 자동 지정 | 로그인 사용자 | 작성자 필드 고정 | 사용자가 작성자를 임의 변경할 수 없다 |
| 결재자 추가 | 임직원 검색, 소속, 이름, 권한 | 결재라인 목록 | 중복 결재자를 경고한다 |
| 순서 변경 | 드래그 또는 이동 버튼 | 변경된 결재 순서 | 최종 결재권자가 마지막 단계로 표시된다 |
| 상신 | 결재 문건, 결재라인, 코멘트 | 결재 진행 상태 | 최종 결재권자 누락 시 상신 차단 |
| 반려/회수 | 사유 | 상태 변경, 타임로그 | 결재 이력과 감사로그가 남는다 |

결정: 결재 문건 작성자는 현재 로그인한 임직원 본인으로 자동 지정하고, 결재라인은 임직원 목록에서 추가/순서 변경하도록 한다.

인당 생산성/마진 기여: 결재자 지정 오류와 승인 대기 누락을 줄여 견적/계약/발행/매출인식 리드타임을 단축한다.

결정: 중요 업무의 결재 상태는 Operations Console의 `pending_approval` 상태와 연결한다.

인당 생산성/마진 기여: 결재 대기 업무를 운영 큐에서 함께 관리해 승인 지연으로 인한 매출 인식 지연을 낮춘다.

### 13.1 결재 버튼과 액션 의미

`/specs/workflow/approval-action-semantics.md`를 기준으로 결재 관련 버튼의 의미와 결과 상태를 화면에 명확히 표시한다.

| 버튼 | 화면 설명 | 결과 상태 | 필수 입력 | 표시 위치 |
|---|---|---|---|---|
| 결재 | 결재 상태와 처리 화면을 연다. 이 버튼 자체는 상태를 변경하지 않는다. | 상태 변경 없음 또는 결재 처리 화면 진입 | 없음 | 목록 행, 상세 상단, 결재함 |
| 승인 | 현재 결재자가 문건을 승인한다. 다음 결재자가 있으면 다음 결재자 대기로 이동한다. | `approved` 또는 다음 결재자 대기 | 승인 의견 선택 | 결재 처리 패널 |
| 반려 | 현재 결재자가 문건을 반려한다. 상신자 또는 작성자가 수정해야 한다. | `rejected` | 반려 사유 필수 | 결재 처리 패널 |
| 보류 | 현재 결재자가 추가 확인을 위해 처리를 보류한다. | `on_hold` | 보류 사유 필수 | 결재 처리 패널 |
| 회수 | 상신자가 최종 승인 전 문건을 회수한다. | `withdrawn` | 회수 사유 후보 | 상신 문건 상세 |

결정: `결재`는 결재 상세/처리 화면 진입 버튼이고, `승인`, `반려`, `보류`, `회수`는 상태 변경 버튼으로 분리한다.

인당 생산성/마진 기여: 버튼 의미를 구분해 잘못된 클릭으로 인한 오처리, 재상신, 승인 지연을 줄인다.

결정: 승인/반려/보류 버튼 옆에는 클릭 시 결과 상태와 후속 업무 영향 설명을 짧게 표시한다.

인당 생산성/마진 기여: 사용자가 버튼 클릭 전 업무 상태 변화를 이해해 결재 오류와 후속 문의를 줄인다.

### 13.2 결재 상태 즉시 표시

결재 버튼 클릭 후 결재 상세 패널 또는 모달에서 다음 정보를 즉시 확인할 수 있어야 한다.

| 정보 | 표시 기준 |
|---|---|
| 현재 결재 상태 | 작성중, 상신, 진행중, 다음 결재자 대기, 승인 완료, 반려, 보류, 회수 |
| 상신자 | 로그인 사용자 기반 상신자 |
| 현재 결재자 | 지금 승인/반려/보류를 처리할 담당자 |
| 다음 결재자 | 승인 후 이어받을 결재자, 없으면 최종 승인 예정 표시 |
| 최종 결재권자 | 결재라인 마지막 결재자 |
| 반려 사유 | `rejected` 상태 또는 반려 이력이 있을 때 노출 |
| 보류 사유 | `on_hold` 상태 또는 보류 이력이 있을 때 노출 |
| 승인/반려/보류 이력 | 처리자, 시각, 의견, 사유, 상태 변경 |
| 대상 업무 영향 | 견적, 계약, 발행, 매출인식 조정의 후속 가능 상태 |

결정: 결재 상태 패널은 현재 결재자와 다음 결재자를 동시에 보여준다.

인당 생산성/마진 기여: 승인 병목이 현재 누구에게 있는지 바로 파악해 확인 연락과 대기 시간을 줄인다.

결정: 반려와 보류는 사유 없이는 처리할 수 없고, 사유는 결재 타임라인과 원 업무 상세에 함께 표시한다.

인당 생산성/마진 기여: 반려/보류 원인을 즉시 확인하게 해 재상신과 보완 처리 시간을 줄인다.

### 13.3 업무별 결재 영향 표시

| 대상 업무 | 최종 승인 시 화면 표시 | 반려 시 화면 표시 | 보류 시 화면 표시 |
|---|---|---|---|
| 견적 | 계약 전환 가능 | 견적 수정 필요 | 견적 검토 대기 |
| 계약 | 주문 등록 가능 | 계약 수정 필요 | 계약 검토 대기 |
| 세금계산서/거래명세표 | 발행 진행 가능 | 발행 요청 반려 | 발행 보류 |
| 매출인식 조정 | 매출 조정 반영 가능 | 조정 요청 반려 | 조정 검토 대기 |

결정: 최종 승인, 반려, 보류가 원 업무의 다음 가능 상태를 어떻게 바꾸는지 결재 패널에 표시한다.

인당 생산성/마진 기여: 결재 결과와 후속 업무 가능 여부를 연결해 매출/발행/계약 처리 지연을 줄인다.

### 13.4 입사등록 결재 승인상태 UI

`/specs/hr/employee-onboarding-approval.md`를 기준으로 입사등록 상세의 `승인상태`를 결재문건 상태와 연결한다.

| 영역 | 입력 | 출력 | 인수조건 |
|---|---|---|---|
| 입사등록 상세 상단 | 입사등록 문건, 결재문건 상태 | 결재상태 배지 | 입사등록 승인상태는 연결된 결재문건 상태와 일치한다 |
| 결재 타임라인 | 상신, 승인, 반려, 보류, 최종 승인, 활성화 대기/완료 이벤트 | 시간순 결재 이력 | 승인/반려/보류 처리자, 시각, 사유가 표시된다 |
| 결재자 패널 | 결재라인, 현재 순번 | 현재 결재자, 다음 결재자, 최종 결재권자 | 결재 버튼 클릭 시 세 결재자 정보를 즉시 확인할 수 있다 |
| 결재라인 설정 | 임직원 검색, 순서, 최종 결재권자 | 결재라인 | 결재라인이 없으면 상신이 차단된다 |
| 반려/보류 처리 | 반려 사유, 보류 사유 | `rejected`, `on_hold` 상태와 사유 | 사유 없이는 반려/보류 처리되지 않는다 |
| 계정 활성화 표시 | 최종 승인 상태 | `employee_activation_pending`, `activated` | 최종 승인 전에는 계정 활성화 완료 또는 권한 부여 완료로 표시하지 않는다 |

상태 배지:

- `draft`: 입사등록 초안
- `submitted`: 결재 상신 완료
- `in_review`: 결재 진행 중
- `on_hold`: 추가 확인 보류
- `rejected`: 반려
- `approved`: 최종 결재 승인
- `employee_activation_pending`: 계정 활성화 대기
- `activated`: 입사등록 최종 반영

결정: 입사등록 상세의 결재상태 배지는 입사등록 저장 여부가 아니라 연결된 결재문건 상태를 기준으로 표시한다.

인당 생산성/마진 기여: 입사 승인 기준을 결재라인으로 표준화해 승인 누락과 계정 권한 오부여를 줄인다.

결정: 최종 결재권자 승인 전에는 임직원 계정 활성화 완료 또는 권한 부여 완료 상태를 화면에 표시하지 않는다.

인당 생산성/마진 기여: 승인 없는 계정 활성화 착오를 차단해 보안 리스크와 계정 정정 비용을 낮춘다.

결정: 입사등록 상세에서도 공통 결재 버튼/승인/반려/보류 의미와 결재라인 설정 UI를 그대로 사용한다.

인당 생산성/마진 기여: 업무별 결재 UX 차이를 줄여 HR/관리자의 교육 비용과 오처리 가능성을 낮춘다.

## 17. E2E 검증 기준

### E2E-OC-01: 저장 필터 기반 일괄 배정

- Given: 운영 리더가 `팀 SLA 위험` 저장 필터를 연다.
- When: 미배정 10건을 선택하고 담당자를 지정한다.
- Then: 적용 가능 건은 `assigned`로 변경되고, 불가 건은 사유와 함께 제외되며, 일괄 처리 로그 ID가 표시된다.

인당 생산성/마진 기여: 리더가 병목 업무를 빠르게 재배치해 SLA 초과로 인한 후속 비용을 줄인다.

### E2E-OC-02: 개인정보 상세 열람 차단

- Given: 운영 담당자가 권한 없는 고객사의 업무 상세에 접근한다.
- When: 임직원 상세 정보를 열람하려 한다.
- Then: 열람이 차단되고 차단 사유가 표시되며, 권한 차단 로그가 남는다.

인당 생산성/마진 기여: 불필요한 개인정보 접근을 차단해 보안 리스크와 감사 대응 비용을 줄인다.

### E2E-OC-03: 예외 재시도와 실패 그룹화

- Given: 예외 큐에 `integration_failed` 업무가 여러 건 있다.
- When: 운영자가 재시도 가능 건을 일괄 재시도한다.
- Then: 성공 건은 다음 상태로 이동하고 실패 건은 실패 사유별로 그룹화되어 표시된다.

인당 생산성/마진 기여: 동일 실패 원인을 묶어 처리해 반복 확인과 수동 분류 시간을 줄인다.

### E2E-OC-04: 고위험 일괄 완료 승인 전환

- Given: 선택 업무 중 고금액 영향 업무가 포함되어 있다.
- When: 운영자가 일괄 완료 요청을 한다.
- Then: 일반 건은 완료되고 고위험 건은 `pending_approval`로 전환되며 승인 요청 로그가 생성된다.

인당 생산성/마진 기여: 대량 처리 속도를 유지하면서 금전 리스크가 큰 업무의 오류 비용을 줄인다.

### E2E-OC-05: 대시보드 드릴다운

- Given: Profitability Dashboard에서 특정 고객사의 예외율 상승 지표를 본다.
- When: 사용자가 원인 업무 보기를 클릭한다.
- Then: Operations Console이 동일 기간, 고객사, 업무유형, 예외 상태 필터로 열린다.

인당 생산성/마진 기여: 수익성 문제를 실제 처리 업무로 연결해 분석 후 조치까지 걸리는 시간을 줄인다.

### E2E-OC-06: 고정 헤더 목록 검증

- Given: 사용자가 고객/상품/주문/업무 목록을 스크롤한다.
- When: 세로 또는 가로 스크롤을 수행한다.
- Then: 필드 헤더가 상단에 고정되고 핵심 식별 컬럼이 유지된다.

인당 생산성/마진 기여: 긴 목록 처리 중 컬럼 의미를 잃지 않아 오처리와 확인 시간을 줄인다.

### E2E-OC-07: 고객 신규/수정 저장 구분

- Given: 사용자가 고객 신규 등록 또는 고객 상세 수정 화면에 있다.
- When: 신규 저장 또는 수정 저장을 수행한다.
- Then: 신규 저장은 고객 생성 로그를 남기고, 수정 저장은 기존 고객 ID 유지와 변경 완료 로그를 남긴다.

인당 생산성/마진 기여: 고객 중복 생성과 변경 이력 누락으로 인한 후속 정정 비용을 줄인다.

### E2E-OC-08: 결재라인 상신

- Given: 사용자가 견적 문건을 작성한다.
- When: 결재자를 추가하고 순서를 변경한 뒤 상신한다.
- Then: 작성자는 로그인 사용자로 고정되고 결재라인/상태/타임로그가 저장된다.

인당 생산성/마진 기여: 승인자 누락과 순서 오류를 줄여 매출 전 단계의 대기 시간을 줄인다.

### E2E-OC-09: 배송/입출고 예외 전환

- Given: 배송/입출고 화면에 배송 지연 건이 있다.
- When: 사용자가 예외 큐 전환을 실행한다.
- Then: Operations Console에 배송 예외 업무가 생성되고 원 주문/송장/상태가 연결된다.

인당 생산성/마진 기여: 배송 예외를 운영 큐에서 처리해 수동 추적과 고객 문의 대응 시간을 줄인다.

### E2E-OC-10: 슈퍼바이저 대시보드 권한

- Given: 슈퍼바이저와 일반 사용자가 각각 로그인한다.
- When: 영업이익 대시보드와 로그 메뉴에 접근한다.
- Then: 슈퍼바이저는 승인된 범위의 영업이익/로그를 보고 일반 사용자는 제한된다.

인당 생산성/마진 기여: 민감 지표는 통제하면서 슈퍼바이저의 이익 개선 판단 속도를 높인다.

### E2E-OC-11: 정렬/필터/저장 뷰 표시

- Given: 사용자가 고객, 임직원, 매출, 상품 목록 중 하나를 연다.
- When: 정렬 가능한 컬럼을 클릭하고 필터를 적용한 뒤 저장 뷰를 선택한다.
- Then: 정렬 방향, 필터 조건, 저장 뷰명이 헤더 또는 상단 영역에 표시된다.

인당 생산성/마진 기여: 사용자가 현재 목록 조건을 즉시 이해해 반복 검색과 잘못된 대상 처리 시간을 줄인다.

### E2E-OC-12: 설정 로그기록 접근

- Given: 관리자 또는 슈퍼바이저가 설정 메뉴를 연다.
- When: `로그기록` 메뉴에 접근한다.
- Then: 권한 있는 사용자는 로그 목록을 보고 권한 없는 사용자는 차단되며 차단 로그가 남는다.

인당 생산성/마진 기여: 로그 확인 경로를 표준화해 감사 대응과 원인 추적 시간을 줄인다.

### E2E-OC-12-1: R34 설정 진입점 단일화

- Given: 사용자가 Operations, 고객, 임직원, 상품, 견적, 주문, 배송, 결재, 대시보드 화면을 순회한다.
- When: 각 화면의 오른쪽 상단 영역을 확인한다.
- Then: 시스템 설정 버튼은 보이지 않고, 설정 관련 기능은 상단 메인 `설정` 메뉴에서만 접근 가능하다.
- And: 화면별 보기 옵션이 필요한 경우 `보기 설정` 또는 `필터 저장`으로 표시되며 시스템 설정처럼 보이지 않는다.

인당 생산성/마진 기여: 중복 설정 진입점을 제거해 설정 위치 혼동과 화면별 UI 검토 비용을 줄인다.

### E2E-OC-13: 임직원 다중 거래처 배정

- Given: 관리자가 임직원 상세의 담당 거래처 편집 화면에 있다.
- When: 거래처 여러 개를 선택하고 각 거래처의 담당 역할, 대표 담당 여부, 배정 기간, 사유를 입력해 저장한다.
- Then: 임직원 상세에는 담당 거래처 목록이 표시되고, 거래처 상세/목록에는 담당자와 대표 담당자가 표시되며, 변경 타임로그가 남는다.

인당 생산성/마진 기여: 임직원과 거래처 담당 관계를 양방향으로 확인해 담당 공백과 중복 문의를 줄인다.

### E2E-OC-14: 결재 버튼 상태 확인과 액션 의미

- Given: 결재 대기 중인 견적, 계약, 발행, 매출인식 조정 문건이 있다.
- When: 사용자가 `결재` 버튼을 클릭한다.
- Then: 현재 결재 상태, 상신자, 현재 결재자, 다음 결재자, 최종 결재권자, 반려/보류 사유, 결재 타임라인이 즉시 표시된다.
- And: `승인`, `반려`, `보류` 버튼은 각각 결과 상태 설명을 표시하고, 반려/보류는 사유 없이는 처리되지 않는다.

인당 생산성/마진 기여: 결재 병목과 버튼 결과를 즉시 이해하게 해 오처리, 재상신, 상태 확인 문의를 줄인다.

### E2E-OC-15: 입사등록 결재 승인상태

- Given: HR/관리자가 입사등록 상세를 작성한다.
- When: 결재라인을 설정하고 상신한 뒤 결재 상태를 확인한다.
- Then: 결재상태 배지, 결재 타임라인, 현재 결재자, 다음 결재자, 최종 결재권자가 표시된다.
- And: 최종 승인 전에는 계정 활성화 완료 또는 권한 부여 완료 상태가 표시되지 않는다.

인당 생산성/마진 기여: 입사등록 승인 게이트를 UI에서 검증해 승인 없는 계정 활성화와 권한 오부여를 줄인다.

### E2E-OC-16: 메뉴별 로그기록 탭과 필터

- Given: 관리자 또는 감사 권한 사용자가 상단 메인 `설정 > 로그기록`을 연다.
- When: 메뉴별 로그 탭을 선택하고 메뉴명, 기간, 사용자, 권한, 이벤트 유형, 결과, 대상 엔티티 필터를 적용한다.
- Then: 해당 메뉴 ID/라우트 ID 기준 로그 목록과 로그 상세가 표시되고, 로그 상세 조회도 감사로그로 남는다.

인당 생산성/마진 기여: 메뉴별 로그 검색을 표준화해 장애 조사, 권한 점검, 외감 대응 시간을 줄인다.

### E2E-OC-17: 수익성 비용 입력 저장

- Given: `Master` 또는 `ProfitCostInputManager`가 상단 메인 `설정 > 수익성 비용 입력`을 연다.
- When: 제원원가, 판관비, 일반관리비와 적용 범위, 적용일, 변경 사유를 입력한다.
- Then: 저장 전 영향 범위와 변경 전후 값, 산식 버전이 표시되고 확인 후 저장된다.
- And: 저장 후 영업이익 대시보드의 산식 버전과 마지막 갱신 시각이 갱신된다.

인당 생산성/마진 기여: 비용 입력 전 영향을 확인해 수익성 대시보드 왜곡과 재검산 비용을 줄인다.

### E2E-OC-18: 수익성 비용 입력 권한 차단

- Given: 일반 또는 관리자 권한 사용자가 수익성 비용 입력 메뉴 또는 직접 URL에 접근한다.
- When: 메뉴 조회 또는 저장 액션을 시도한다.
- Then: 메뉴가 숨겨지거나 차단 사유가 표시되고 `permission_denied` 로그가 남는다.

인당 생산성/마진 기여: 권한 없는 비용 변경을 차단해 영업이익 지표 신뢰도를 유지한다.

## 18. 반응형 웹/PWA 고려

초기 설계는 반응형 웹 또는 PWA를 가정한다. Windows 데스크톱에서는 고밀도 테이블과 키보드 중심 처리를 우선하고, iOS에서는 조회, 승인, 코멘트, 제한적 상태 변경을 우선한다. 이 방향은 PM 승인 필요.

| 환경 | 우선 UX | 제한/검토 |
|---|---|---|
| Windows 데스크톱 | 고밀도 테이블, 다중 선택, 키보드 탐색, 대량 처리 | 브라우저 호환성 기준 필요 |
| iOS 태블릿 | 필터, 상세 드로어, 승인/코멘트 | 대량 처리 UX 검토 |
| iOS 모바일 | SLA/승인/알림 중심 경량 처리 | 개인정보 상세 열람과 반출 제한 권고 |

결정: 모바일은 모든 대량 처리 기능을 동일하게 제공하기보다 승인, 알림, 조회 중심으로 제한하는 안을 우선 검토한다.

인당 생산성/마진 기여: 모바일에서 위험한 대량 처리를 줄이고 현장 승인/확인 업무만 빠르게 처리하게 해 오류 비용을 낮춘다.

## 20. 오픈 이슈

1. 업무유형별 SLA 목표시간과 보류 중 SLA 정지 여부는 확정되지 않았다. PM 승인 필요.
2. 개인정보 원문 검색 허용 여부는 확정되지 않았다. 기본 금지로 설계한다. PM 승인 필요.
3. CSV/Excel 반출 기능은 운영 효율에 중요하지만 개인정보 리스크가 크다. 반출 범위와 승인 흐름은 PM 승인 필요.
4. 수익성 지표에서 Operations Console로 전달할 필터 파라미터 표준은 A4와 합의 필요.
5. 예외 사유 코드는 A6 연동 실패 유형과 A8 자동화 후보 분류를 받은 뒤 보정 필요.
6. 영업이익 고정 산식과 슈퍼바이저 열람 범위는 PM 승인 필요.
7. 택배사 실시간 위치 연동은 API/비용/계약 확인 전까지 수동 송장 입력과 재조회 큐를 기준으로 둔다. PM 승인 필요.
8. 결재라인의 대리결재, 회수, 최종 결재권자 기준은 PM 승인 필요.
9. 거래처별 대표 담당자를 1명으로 제한할지, 담당 역할을 주담당/부담당/승인담당/참조담당으로 시작할지는 PM 승인 필요.
10. 담당자 배정 변경 권한을 관리자 이상으로 제한할지는 PM 승인 필요.
11. `결재` 버튼을 상태 변경이 아닌 결재 상세/처리 화면 진입 버튼으로 정의할지는 PM 승인 필요.
12. `보류`를 공식 결재 상태로 둘지는 PM 승인 필요.
13. 화면별 보기 옵션이 필요한 경우 이를 시스템 설정이 아닌 `보기 설정` 또는 `필터 저장`으로 분리하는 기준은 A3/A8 검증 필요.
14. 입사등록을 결재 필수 업무로 둘지, 최종 승인 후 계정 활성화를 자동 처리할지 관리자 확인 후 처리할지는 PM 승인 필요.
15. 입사등록 결재라인 기본 템플릿을 둘지는 PM 승인 필요.
16. 메뉴 진입 로그까지 필수로 남길지, 메뉴별 로그 보존기간을 전체 감사로그와 동일하게 둘지는 PM 승인 필요.
17. 로그 반출 권한을 슈퍼바이저와 감사 담당으로 제한할지는 PM 승인 필요.
18. `제원원가`의 정확한 회계 의미와 수익성 비용 입력 권한을 `Master`만 둘지 별도 `ProfitCostInputManager`도 둘지는 PM 승인 필요.
19. 비용 입력 변경을 항상 결재 대상으로 둘지는 PM 승인 필요.

인당 생산성/마진 기여: 오픈 이슈를 승인/합의 대상으로 분리해 빠른 초안 검토와 안정적인 후속 구현을 가능하게 한다.
