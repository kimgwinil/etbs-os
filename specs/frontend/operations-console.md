# Operations Console 상세 화면 스펙

## 1. 목적

Operations Console은 이제너두 전사 CRM OS의 P0 운영 업무 처리 화면이다. 운영자는 업무 접수, 검색, 필터, 배정, 상태 변경, SLA 대응, 예외 처리, 일괄 처리를 단일 콘솔에서 수행한다.

본 문서는 프론트 화면/흐름 스펙이며 백엔드 아키텍처, 개인정보 처리범위, 외부 연동 구현 방식은 확정하지 않는다. 관련 확정은 PM 김권일 승인 필요.

인당 생산성/마진 기여: 단일 콘솔에서 반복 업무를 대량 처리하게 해 담당자 1인당 처리 건수를 높이고 평균 처리시간을 줄인다.

## 2. 범위

### 포함

- 운영 업무 큐 목록
- 통합 검색과 고급 필터
- 저장 필터와 기본 뷰
- 업무 상세 드로어
- 일괄 배정/상태 변경/재시도/보류/승인 요청
- SLA 위험/초과 표시
- 예외 큐와 수동 보정 흐름
- 역할별 화면/액션 차이
- 개인정보 최소 노출 및 열람 로그 UX
- Profitability Dashboard 드릴다운 연동 지점

### 제외

- 정산/포인트 상세 회계 처리 로직
- 외부 연동 어댑터 구현
- 공급사/고객사 포털 화면
- AI 자동 의사결정
- 네이티브 Windows/iOS 앱

결정: 초기 범위는 운영자가 매일 쓰는 큐와 처리 액션에 집중하고, 전문 도메인 상세 처리는 후속 모듈 상세 화면으로 위임한다.

인당 생산성/마진 기여: 콘솔의 핵심 반복 작업을 먼저 표준화해 화면 과확장으로 인한 개발비와 교육 비용을 줄인다.

## 3. 사용자와 권한

| 역할 | 기본 진입 뷰 | 허용 액션 | 제한 사항 |
|---|---|---|---|
| 운영 담당자 | `내 업무`, `팀 업무`, `SLA 위험` | 처리 시작, 보류, 완료 요청, 재시도, 본인 메모 | 타팀/비권한 고객사 제한, 고위험 완료 승인 필요 |
| 운영 리더 | `팀 전체`, `SLA 초과`, `예외 큐` | 배정, 재배정, 우선순위 변경, 승인/반려 | 개인정보 상세 열람 사유 필수 |
| 재무/정산 담당자 | `정산/포인트 큐`, `증적 필요` | 정산 관련 확인, 증적 요청, 보류/완료 요청 | 임직원 민감정보 제한 |
| 보안/개인정보 담당자 | `접근 로그`, `권한 예외` | 접근 로그 조회, 권한 위반 표시, 감사 코멘트 | 업무 처리 상태 직접 변경 제한 |
| 경영진/PM | `운영 요약`, `병목/예외` | 집계 조회, 드릴다운, 지시 메모 | 개별 개인정보 상세 제한 |
| AM/영업 | `담당 고객사 이슈` | 담당 고객사 업무 조회, 코멘트, 후속 요청 | 전체 큐/수익성 상세 제한 |

결정: 동일 화면 컴포넌트를 사용하되 역할별 기본 뷰, 데이터 범위, 액션 가능 여부를 권한으로 분기한다.

인당 생산성/마진 기여: 화면을 역할별로 완전히 분리하지 않아 개발/유지보수 비용을 낮추고, 권한 기반 통제로 규제 리스크를 줄인다.

## 4. 정보 구조

### 4.1 내비게이션

- `Operations`
  - `내 업무`
  - `팀 업무`
  - `SLA 위험`
  - `예외 큐`
  - `승인 대기`
  - `완료/이력`
- `Dashboard`
  - Profitability Dashboard에서 선택 조건을 받아 필터링된 Operations Console로 진입

인당 생산성/마진 기여: 운영자가 매일 쓰는 진입점을 업무 상태 중심으로 나눠 탐색 시간을 줄인다.

### 4.2 화면 레이아웃

| 영역 | 필수 요소 | 동작 |
|---|---|---|
| 헤더 | 페이지명, 기본 뷰 탭, 새로고침, 내 저장 필터 | 현재 권한과 필터 범위를 표시 |
| KPI 스트립 | 신규, 미배정, 진행중, SLA 위험, SLA 초과, 예외, 오늘 완료 | 클릭 시 해당 필터 적용 |
| 검색/필터 바 | 통합 검색, 날짜, 고객사, 공급사, 업무유형, 상태, 담당자 | 필터 변경 시 목록 갱신 |
| 목록 테이블 | 다중 선택, 정렬, 컬럼 표시/숨김, 페이지네이션 | 대량 처리와 빠른 스캔 지원 |
| 일괄 액션 바 | 배정, 재배정, 상태 변경, 보류, 재시도, 승인 요청 | 선택 건이 있을 때 고정 표시 |
| 상세 드로어 | 업무 요약, 관련 엔티티, 입력값, 액션, 이력, 로그 | 목록 맥락을 유지한 채 처리 |

결정: 상세는 별도 페이지가 아니라 우측 드로어를 기본으로 한다.

인당 생산성/마진 기여: 목록 맥락을 유지해 다음 건으로 이동하는 시간을 줄이고 운영자의 연속 처리 흐름을 끊지 않는다.

## 5. 업무 데이터 필드 초안

|---|---|---|---|
| `task_id` | 업무 고유 ID | 표시 | 비개인정보 |
| `task_type` | CS, 포인트, 정산, 신청/심사, 연동 실패 등 | 표시 | 비개인정보 |
| `status` | 현재 상태 | 표시 | 비개인정보 |
| `priority` | 우선순위 | 표시 | 비개인정보 |
| `sla_due_at` | SLA 목표 시각 | 표시 | 비개인정보 |
| `client_id`, `client_name` | 고객사 | 표시 | 고객사 권한 적용 |
| `supplier_id`, `supplier_name` | 공급사 | 조건부 표시 | 공급사 권한 적용 |
| `employee_ref` | 임직원 참조값 | 마스킹 표시 | 상세 열람 사유 필요 |
| `contract_id` | 계약 참조 | 표시 | 권한 적용 |
| `amount_impact` | 금액 영향도 | 조건부 표시 | 재무 권한 적용 |
| `assignee_id`, `assignee_name` | 담당자 | 표시 | 내부 정보 |
| `exception_reason` | 예외 사유 | 표시 | 사유 표준화 필요 |
| `last_event_at` | 마지막 이벤트 시각 | 표시 | 비개인정보 |
| `audit_required` | 감사/승인 필요 여부 | 표시 | 통제 플래그 |

결정: 목록에는 `employee_ref`를 마스킹 참조값으로만 표시하고, 실제 개인정보 상세는 사유 입력 후 제한적으로 열람한다.

인당 생산성/마진 기여: 업무 분류에 필요한 정보는 유지하면서 개인정보 노출 리스크와 감사 대응 비용을 낮춘다.

## 6. 검색과 필터

### 6.1 통합 검색

검색 대상:

- 업무 ID
- 고객사명/고객사 ID
- 공급사명/공급사 ID
- 계약 ID
- 마스킹 임직원 참조값
- 외부 연동 참조 ID

개인정보 원문 검색은 기본 금지로 가정하며, 필요 여부와 허용 범위는 PM 승인 필요.

인당 생산성/마진 기여: 식별자를 몰라도 고객사/업무/연동 참조로 빠르게 찾게 해 문의 대응 시간을 줄인다.

### 6.2 필터

| 필터 | 옵션 예시 | 기본값 |
|---|---|---|
| 기간 | 접수일, SLA 목표일, 마지막 이벤트일 | 최근 7일 |
| 업무유형 | CS, 포인트, 정산, 신청/심사, 연동 실패 | 전체 |
| 상태 | 신규, 배정, 진행중, 승인 대기, 보류, 예외, 완료, 반려 | 활성 상태 |
| SLA | 정상, 위험, 초과 | 전체 |
| 담당자 | 나, 팀원, 미배정 | 역할별 기본 |
| 고객사 | 권한 내 고객사 | 전체 |
| 공급사 | 권한 내 공급사 | 전체 |
| 금액 영향도 | 없음, 낮음, 중간, 높음 | 전체 |
| 예외 사유 | 연동 실패, 증적 부족, 정책 외, 데이터 불일치 | 전체 |

### 6.3 저장 필터

필수 기본 저장 필터:

- `내 오늘 처리`
- `팀 SLA 위험`
- `미배정 신규`
- `예외 재시도 필요`
- `승인 대기`
- `고금액 영향`

결정: 저장 필터는 개인 필터와 팀 공용 필터를 모두 지원하되, 팀 공용 필터 생성/수정은 운영 리더 이상으로 제한한다.

인당 생산성/마진 기여: 반복 조건 설정 시간을 줄이고 팀 단위 업무 기준을 표준화해 처리 편차를 낮춘다.

## 7. 상태 변경

### 7.1 상태 전이

| From | To | 수행자 | 필수 입력 | 승인 |
|---|---|---|---|---|
| `new` | `assigned` | 운영 리더, 자동 배정 정책 | 담당자 | 없음 |
| `assigned` | `in_progress` | 담당자 | 없음 | 없음 |
| `in_progress` | `completed` | 담당자 | 완료 사유/증적 | 조건부 |
| `in_progress` | `blocked` | 담당자 | 보류 사유, 해제 조건 | 없음 |
| `blocked` | `in_progress` | 담당자/리더 | 보류 해제 사유 | 없음 |
| `in_progress` | `pending_approval` | 담당자/리더 | 승인 요청 사유 | 필수 |
| `pending_approval` | `completed` | 승인자 | 승인 코멘트 | 필수 |
| `pending_approval` | `rejected` | 승인자 | 반려 사유 | 필수 |
| `in_progress` | `exception` | 시스템/담당자 | 예외 사유 | 없음 |
| `exception` | `in_progress` | 담당자/리더 | 조치 계획 | 조건부 |
| `exception` | `completed` | 담당자/승인자 | 수동 보정 근거 | 조건부 |

결정: 모든 상태 변경은 단건/일괄 모두 같은 전이 규칙을 사용한다.

인당 생산성/마진 기여: 단건과 일괄 처리의 정책 차이를 없애 오류와 재작업을 줄인다.

### 7.2 상태 변경 UX

- 상태 변경 버튼은 현재 상태와 권한에 따라 노출한다.
- 위험 액션은 버튼 클릭 후 확인 모달을 표시한다.
- 고금액/개인정보/정산 영향 업무는 승인 요청으로 전환한다.
- 일괄 상태 변경 시 성공/실패/승인 대기 전환 건수를 결과 패널에 표시한다.
- 실패 건은 실패 사유별로 그룹화해 재시도 또는 예외 큐 이동을 제안한다.

인당 생산성/마진 기여: 실패 결과를 그룹화하면 운영자가 같은 원인의 문제를 한 번에 처리해 반복 확인 시간을 줄인다.

## 8. 일괄 처리

### 8.1 일괄 액션

| 액션 | 설명 | 제한 |
|---|---|---|
| 일괄 배정 | 선택 업무를 특정 담당자/팀에 배정 | 운영 리더 이상 또는 정책 허용 |
| 일괄 재배정 | 담당자 변경 | 기존/신규 담당자 로그 필요 |
| 일괄 보류 | 동일 사유로 보류 처리 | 보류 사유 필수 |
| 일괄 재시도 | 연동 실패/자동 처리 실패 재시도 | 재시도 가능 상태만 허용 |
| 일괄 승인 요청 | 고위험 업무를 승인 큐로 이동 | 승인 사유 필수 |
| 일괄 완료 요청 | 처리 완료 상태로 이동 또는 승인 요청 | 조건부 승인 |
| CSV/Excel 내보내기 요청 | 필터 결과 반출 요청 | 개인정보/권한 정책 PM 승인 필요 |

결정: 일괄 처리는 선택 건 전체에 바로 적용하지 않고, 적용 가능/불가/승인 필요 건수를 미리 보여주는 확인 단계를 둔다.

인당 생산성/마진 기여: 대량 처리 오류를 사전에 차단해 복구 작업과 고객 영향 비용을 줄인다.

### 8.2 일괄 처리 결과

결과 패널 필수 표시:

- 요청 건수
- 성공 건수
- 실패 건수
- 승인 대기 전환 건수
- 실패 사유 그룹
- 감사 로그 ID
- 후속 액션 버튼

인당 생산성/마진 기여: 처리 결과를 즉시 요약해 운영자가 실패 건만 다시 다루게 하므로 반복 검증 시간을 줄인다.

## 9. SLA

### 9.1 SLA 표시

| 상태 | 표시 | 기준 |
|---|---|---|
| 정상 | 회색/기본 배지 | 목표시간까지 충분 |
| 위험 | 주의 배지 | 목표시간 임박 |
| 초과 | 경고 배지 | 목표시간 초과 |
| 제외 | 보류/승인 대기 등 정책상 제외 | SLA 정책 PM 승인 필요 |

정확한 임박 기준, 보류 중 SLA 정지 여부, 업무유형별 목표시간은 PM 승인 필요.

인당 생산성/마진 기여: SLA 위험 업무를 조기에 식별해 지연으로 인한 문의, 보상, 재처리 비용을 줄인다.

### 9.2 SLA 흐름

1. KPI 스트립의 `SLA 위험` 또는 `SLA 초과`를 클릭한다.
2. 목록은 SLA 기준으로 정렬된다.
3. 운영 리더는 담당자/업무유형/고객사 기준 병목을 확인한다.
4. 재배정, 우선순위 변경, 보류 사유 확인 중 하나를 수행한다.
5. 처리 결과는 감사로그와 팀 KPI에 반영된다.

인당 생산성/마진 기여: 병목을 담당자 개인의 기억이 아니라 큐 데이터로 관리해 팀 전체 처리량을 안정화한다.

## 10. 예외 처리

### 10.1 예외 사유 초안

| 예외 사유 | 설명 | 권장 액션 | 의존 |
|---|---|---|---|
| `integration_failed` | 외부 API/파일 연동 실패 | 재시도, A6 확인 요청 | A6 |
| `data_mismatch` | CRM/정산/포인트 데이터 불일치 | 원천 데이터 확인, 수동 보정 | A1/A4 |
| `missing_evidence` | 증적 또는 첨부 부족 | 보완 요청, 보류 | A2/A7 |
| `policy_out_of_scope` | 정책 외 케이스 | 승인 요청, PM 검토 | PM |
| `permission_blocked` | 권한 부족으로 처리 불가 | 리더/보안 검토 | A7/A9 |
| `high_amount_risk` | 금액 영향 큰 업무 | 승인 요청 | PM/재무 |

결정: 예외 사유는 자유 텍스트가 아니라 표준 코드+보조 메모로 입력한다.

인당 생산성/마진 기여: 예외를 분류 가능한 데이터로 남겨 자동화 후보와 반복 병목을 찾을 수 있다.

### 10.2 예외 큐 화면

필수 컬럼:

- 예외 사유
- 업무유형
- 고객사/공급사
- 금액 영향도
- 마지막 실패 메시지 요약
- 마지막 재시도 시각
- 재시도 가능 여부
- 권장 다음 액션
- 담당자
- SLA 영향

필수 액션:

- 재시도
- 수동 보정 요청
- 보류
- 승인 요청
- 담당자 변경
- 관련 로그 보기

인당 생산성/마진 기여: 재시도 가능한 예외와 사람 판단이 필요한 예외를 분리해 고숙련 인력의 시간을 아낀다.

## 11. 개인정보 및 감사 UX

### 11.1 기본 원칙

- 목록에서는 개인정보 원문을 표시하지 않는다.
- 상세 열람은 권한, 목적, 사유 입력을 통과해야 한다.
- 열람 세션은 제한 시간과 필드 범위를 가진다.
- 개인정보가 포함된 CSV/Excel 반출은 기본 비활성으로 가정한다.
- 반출 정책, 마스킹 규칙, 보관기간은 PM 승인 필요.

인당 생산성/마진 기여: 개인정보 노출을 최소화해 보안 사고와 감사 대응에 드는 비용을 줄인다.

### 11.2 감사로그 대상

- 로그인 후 큐 조회 범위
- 개인정보 상세 열람
- 상태 변경
- 담당자 변경
- 일괄 처리
- 승인/반려
- CSV/Excel 반출 요청
- 권한 차단 이벤트

결정: 사용자가 직접 인지해야 하는 고위험 액션은 감사로그 생성 사실과 로그 ID를 결과 화면에 보여준다.

인당 생산성/마진 기여: 운영자가 사후 추적 가능성을 알고 처리하게 해 무분별한 고위험 액션을 줄인다.

## 13. E2E 검증 기준

### E2E-OC-01: 저장 필터 기반 일괄 배정

- Given: 운영 리더가 `팀 SLA 위험` 저장 필터를 연다.
- When: 미배정 10건을 선택하고 담당자를 지정한다.
- Then: 적용 가능 건은 `assigned`로 변경되고, 불가 건은 사유와 함께 제외되며, 일괄 처리 로그 ID가 표시된다.

인당 생산성/마진 기여: 리더가 병목 업무를 빠르게 재배치해 SLA 초과로 인한 후속 비용을 줄인다.

### E2E-OC-02: 개인정보 상세 열람 차단

- Given: 운영 담당자가 권한 없는 고객사의 업무 상세에 접근한다.
- When: 임직원 상세 정보를 열람하려 한다.
- Then: 열람이 차단되고 차단 사유가 표시되며, 권한 차단 로그가 남는다.

인당 생산성/마진 기여: 불필요한 개인정보 접근을 차단해 보안 리스크와 감사 대응 비용을 줄인다.

### E2E-OC-03: 예외 재시도와 실패 그룹화

- Given: 예외 큐에 `integration_failed` 업무가 여러 건 있다.
- When: 운영자가 재시도 가능 건을 일괄 재시도한다.
- Then: 성공 건은 다음 상태로 이동하고 실패 건은 실패 사유별로 그룹화되어 표시된다.

인당 생산성/마진 기여: 동일 실패 원인을 묶어 처리해 반복 확인과 수동 분류 시간을 줄인다.

### E2E-OC-04: 고위험 일괄 완료 승인 전환

- Given: 선택 업무 중 고금액 영향 업무가 포함되어 있다.
- When: 운영자가 일괄 완료 요청을 한다.
- Then: 일반 건은 완료되고 고위험 건은 `pending_approval`로 전환되며 승인 요청 로그가 생성된다.

인당 생산성/마진 기여: 대량 처리 속도를 유지하면서 금전 리스크가 큰 업무의 오류 비용을 줄인다.

### E2E-OC-05: 대시보드 드릴다운

- Given: Profitability Dashboard에서 특정 고객사의 예외율 상승 지표를 본다.
- When: 사용자가 원인 업무 보기를 클릭한다.
- Then: Operations Console이 동일 기간, 고객사, 업무유형, 예외 상태 필터로 열린다.

인당 생산성/마진 기여: 수익성 문제를 실제 처리 업무로 연결해 분석 후 조치까지 걸리는 시간을 줄인다.

## 14. 반응형 웹/PWA 고려

초기 설계는 반응형 웹 또는 PWA를 가정한다. Windows 데스크톱에서는 고밀도 테이블과 키보드 중심 처리를 우선하고, iOS에서는 조회, 승인, 코멘트, 제한적 상태 변경을 우선한다. 이 방향은 PM 승인 필요.

| 환경 | 우선 UX | 제한/검토 |
|---|---|---|
| Windows 데스크톱 | 고밀도 테이블, 다중 선택, 키보드 탐색, 대량 처리 | 브라우저 호환성 기준 필요 |
| iOS 태블릿 | 필터, 상세 드로어, 승인/코멘트 | 대량 처리 UX 검토 |
| iOS 모바일 | SLA/승인/알림 중심 경량 처리 | 개인정보 상세 열람과 반출 제한 권고 |

결정: 모바일은 모든 대량 처리 기능을 동일하게 제공하기보다 승인, 알림, 조회 중심으로 제한하는 안을 우선 검토한다.

인당 생산성/마진 기여: 모바일에서 위험한 대량 처리를 줄이고 현장 승인/확인 업무만 빠르게 처리하게 해 오류 비용을 낮춘다.

## 16. 오픈 이슈

1. 업무유형별 SLA 목표시간과 보류 중 SLA 정지 여부는 확정되지 않았다. PM 승인 필요.
2. 개인정보 원문 검색 허용 여부는 확정되지 않았다. 기본 금지로 설계한다. PM 승인 필요.
3. CSV/Excel 반출 기능은 운영 효율에 중요하지만 개인정보 리스크가 크다. 반출 범위와 승인 흐름은 PM 승인 필요.
4. 수익성 지표에서 Operations Console로 전달할 필터 파라미터 표준은 A4와 합의 필요.
5. 예외 사유 코드는 A6 연동 실패 유형과 A8 자동화 후보 분류를 받은 뒤 보정 필요.

인당 생산성/마진 기여: 오픈 이슈를 승인/합의 대상으로 분리해 빠른 초안 검토와 안정적인 후속 구현을 가능하게 한다.
