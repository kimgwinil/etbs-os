# 배송/입출고 택배사 연동 스펙 초안

## 1. 목적

출고 이후 배송/입출고 현황을 택배사와 연동해 현재 위치와 상태를 확인하고, 실패 시 수동 보정 큐로 운영자가 처리할 수 있게 한다.

인당 생산성/마진 기여: 배송 문의와 지연 대응 시간을 줄이고 반품/오배송으로 인한 마진 손실을 빠르게 식별한다.

## 2. 입력

- 주문 ID
- 출고 ID
- 택배사 코드
- 송장번호
- 배송조회 요청 시각
- 재조회 사유
- 요청 주체 사용자/시스템 ID

인당 생산성/마진 기여: 배송조회에 필요한 최소 입력을 고정해 수동 조회와 재입력을 줄인다.

## 3. 출력

- 배송상태
- 현재 위치
- 최종 조회 시각
- 택배사 이벤트 시각
- 예외 여부
- 실패 사유
- 수동 보정 필요 여부
- 다음 재조회 예정 시각

인당 생산성/마진 기여: 배송 상태와 예외를 업무 큐에 연결해 담당자가 먼저 처리할 건을 빠르게 찾는다.

## 4. 연동 원칙

- 택배사 API 계약, 비용, 인증 방식은 PM 승인 전 확정하지 않는다.
- 모든 조회 요청은 멱등키 또는 요청 ID를 가진다.
- 실패 시 재시도 큐로 이동한다.
- 반복 실패 또는 데이터 불일치 시 수동 보정 큐로 이동한다.
- 배송 지연, 오배송, 반송, 미출고는 운영 콘솔 예외 큐로 표시한다.
- 현재 위치는 택배사가 제공한 배송 이벤트 단위의 표준 위치만 저장한다.
- 외부 응답 원문, 정밀 주소, GPS 좌표, 수취인 개인정보 저장은 PM 승인 전 확정하지 않는다.

인당 생산성/마진 기여: 외부 연동 실패를 표준 처리해 장애 대응과 문의 대응 인력을 줄인다.

## 5. 배송상태 표준값

| 내부 상태 | 의미 | 예외 여부 | 운영 큐 전환 기준 |
|---|---|---|---|
| `shipment_pending` | 송장번호 또는 택배사 코드 등록 전 | 조건부 | 출고 완료 후 송장 미등록 SLA 초과 시 배송 예외 운영 큐 |
| `tracking_registered` | 송장번호와 택배사 코드 등록 완료 | N | 다음 조회 예약 |
| `pickup_ready` | 집하 예정 또는 접수 대기 | N | 장기 미집하 시 배송 예외 운영 큐 |
| `picked_up` | 택배사 집하 완료 | N | 이동중 조회 예약 |
| `in_transit` | 터미널/허브 이동 중 | N | 장기 미갱신 시 재시도 큐 |
| `out_for_delivery` | 배송 출발 | N | 당일 미완료 시 배송 예외 운영 큐 |
| `delivered` | 배송 완료 | N | 수동 보정 시 감사로그 필수 |
| `delivery_delayed` | 배송 지연 | Y | 배송 예외 운영 큐 |
| `misdelivered` | 오배송 의심 또는 오배송 확정 | Y | 배송 예외 운영 큐 |
| `returned` | 반송 진행 또는 반송 완료 | Y | 배송 예외 운영 큐 |
| `lost_or_damaged` | 분실/파손 의심 또는 확정 | Y | 배송 예외 운영 큐 |
| `tracking_check_required` | 조회 실패 또는 상태 불명확 | Y | 재시도 큐 또는 수동 보정 큐 |

인당 생산성/마진 기여: 택배사별 상태값을 내부 표준 상태로 맞춰 배송 예외를 자동 분류하고 담당자 판단 시간을 줄인다.

## 6. 현재 위치 저장 범위

| 저장 항목 | 저장 기준 | PM 승인 필요 여부 |
|---|---|---|
| 택배사 코드 | 내부 표준 코드로 저장 | N |
| 송장번호 | 전체 저장, 화면/로그 일부 마스킹 | 마스킹 정책 승인 필요 |
| 내부 배송상태 | 표준 상태값 저장 | N |
| 택배사 원본 상태 코드 | 상태 매핑 검증용으로 저장 | 보존기간 승인 필요 |
| 현재 위치 요약 | 택배사 제공 터미널/허브/지역명 수준 저장 | N |
| 위치 이벤트 시각 | 택배사 이벤트 발생 시각 저장 | N |
| 최종 조회 시각 | CRM OS 조회 완료 시각 저장 | N |
| 배송 이벤트 타임라인 | 상태, 위치 요약, 이벤트 시각, 조회 시각 저장 | 보존기간 승인 필요 |
| 외부 응답 원문 | 기본 비저장 또는 마스킹 저장 | PM 승인 필요 |
| 정밀 주소/GPS 좌표 | 기본 비저장 | PM 승인 필요 |
| 수취인 이름/전화번호/상세주소 | 배송조회 저장 범위에서 제외, 필요한 경우 원천 주문 데이터 참조 | 개인정보 처리범위 PM 승인 필요 |

인당 생산성/마진 기여: 위치 저장 범위를 업무 판단에 필요한 수준으로 제한해 개인정보 리스크와 로그 보관 비용을 줄인다.

## 7. 큐 운영 기준

### 7.1 재시도 큐

| 항목 | 기준 |
|---|---|
| 목적 | 일시적 택배사 API 실패 또는 응답 지연 건 자동 재조회 |
| 진입 조건 | 네트워크 오류, 5xx, 타임아웃, 일시적 조회 실패, 배송완료 전 장기 미갱신 |
| 재시도 횟수 | 기본 3회 |
| 재시도 간격 | 5분, 30분, 2시간 |
| 성공 시 | 배송상태와 현재 위치 갱신 후 큐 종료 |
| 실패 초과 시 | 수동 보정 큐 또는 배송 예외 운영 큐로 이동 |
| PM 승인 필요 | 택배사별 호출 한도, 비용, 재조회 주기 |

인당 생산성/마진 기여: 일시 장애를 자동 복구해 운영자의 단건 조회 시간을 줄인다.

### 7.2 수동 보정 큐

| 항목 | 기준 |
|---|---|
| 목적 | 자동 조회로 해결되지 않는 송장/택배사/배송상태 오류 보정 |
| 진입 조건 | 송장번호 누락/오류, 택배사 코드 불일치, 상태 코드 미매핑, 반복 조회 실패, 외부 관리자 확인 필요 |
| 운영자 입력 | 보정 상태, 보정 사유, 증빙, 외부 확인 경로, 담당자 |
| 승인 조건 | 배송완료, 반송, 분실/파손 보정은 권한자 승인 필요 |
| 완료 조건 | 변경 전후 상태와 증적이 감사로그에 남아야 함 |
| 금지 사항 | 증적 없는 배송완료 처리, 확인되지 않은 반송/분실 확정 |

인당 생산성/마진 기여: 수동 보정 기준을 고정해 배송 문의 처리 편차와 감사 추적 비용을 줄인다.

### 7.3 배송 예외 운영 큐

| 예외 유형 | 진입 기준 초안 | 담당 | 처리 목표 | PM 승인 필요 |
|---|---|---|---|---|
| 미출고 | 출고 지시 후 송장번호 미등록 SLA 초과 | 운영/물류 | 영업일 내 확인 | SLA 기준 |
| 장기 미집하 | 송장 등록 후 집하 이벤트 미수신 SLA 초과 | 운영/공급사 | 영업일 내 확인 | 택배사/공급사 책임 기준 |
| 장기 미갱신 | 배송완료 전 마지막 위치 이벤트가 기준 시간 초과 | 운영 | 30분 내 확인 | 기준 시간 |
| 배송 지연 | 약속 납기 또는 표준 배송기한 초과 | 운영/CS | 30분 내 확인 | 고객 안내 기준 |
| 오배송 | 택배사 상태 또는 고객 문의로 오배송 의심 | 운영/CS | 즉시 확인 | 보상/회수 정책 |
| 반송 | 반송 이벤트 수신 또는 반송 의심 | 운영/CS | 30분 내 확인 | 환불/재배송 정책 |
| 분실/파손 | 택배사 사고 코드 또는 수동 확인 | 운영/재무/CS | 즉시 확인 | 비용 부담/보상 정책 |

인당 생산성/마진 기여: 배송 예외를 마진 손실 가능성 기준으로 큐잉해 제한된 운영 인력을 고위험 건에 집중시킨다.

## 8. 인수조건

1. 주문/출고 건에 송장번호와 택배사 코드가 연결되어야 한다.
2. 배송 상태와 현재 위치를 저장할 수 있어야 한다.
3. 연동 실패 시 재시도 또는 수동 보정 큐가 생성되어야 한다.
4. 배송 예외는 운영 콘솔에서 식별 가능해야 한다.
5. 외부 응답 원문 저장 여부는 PM 승인 전 확정하지 않아야 한다.
6. 재시도 큐, 수동 보정 큐, 배송 예외 운영 큐의 진입/종료 기준이 구분되어야 한다.
7. 현재 위치 저장은 터미널/허브/지역명 수준의 위치 요약으로 제한되어야 한다.
8. 수동 보정은 보정 사유, 증빙, 담당자, 변경 전후 상태를 감사로그에 남겨야 한다.

인당 생산성/마진 기여: 인수조건을 예외 대응 중심으로 잡아 실시간 연동 실패가 업무 중단으로 이어지지 않게 한다.

## 10. PM 승인 항목

1. 택배사 API 계약/비용 확인 전까지 수동 보정 큐 기준으로 진행해도 되는가?
2. 현재 위치 정보 저장 범위와 보존기간을 별도 승인으로 둘 것인가?
3. 배송 예외를 영업이익 저하 원인 KPI에 포함할 것인가?
4. 택배사별 API 호출 한도, 재조회 주기, 초과 호출 비용을 승인할 것인가?
5. 외부 응답 원문, 정밀 주소, GPS 좌표 저장을 금지하고 위치 요약만 저장하는 정책을 승인할 것인가?
6. 배송 지연/오배송/반송/분실·파손의 고객 안내, 보상, 비용 부담 기준을 승인할 것인가?

인당 생산성/마진 기여: 승인 항목을 계약/비용/개인정보/보상 정책으로 분리해 확정 전 개발 낭비와 운영 리스크를 줄인다.
